# usable-ui:review: 4 つの観点で UI を点検する

**このスキルではリポジトリのファイルを変えない。** 直すのは、ユーザーが頼んだあと。

基準は `${CLAUDE_PLUGIN_ROOT}/references/checklist.md`。最初に読む。

## 1. 対象を決める

- 引数がファイル・ディレクトリなら、その画面。
- 引数が画像なら、その画像（あればコードの場所も探す）。会話に貼られただけでパスのない画像は、ファイルに保存してもらうか、パスを尋ねる（サブエージェントに渡せないため）。
- 引数がなければ、`git diff` と `git diff --staged`（なければ `git diff <base>...HEAD`）から UI のファイル（画面・部品・文言・スタイル）を選ぶ。
- UI の差分がないとき、または「総点検」を頼まれたときは、画面の一覧を出し、どれを見るかを尋ねる。多ければ、主要な流れの 1〜3 個に絞ることを勧める。

見た目も確かめられるなら確かめる。対象が URL か、単体で開ける HTML のファイルで、**すでに使える** Playwright（MCP の道具か、入っているもの）があれば、ライトとダーク、狭い幅（390px）と広い幅（1280px）でスクリーンショットを撮る。Playwright を入れない。サーバーを勝手に起動しない。画像と撮るためのスクリプトはスクラッチのフォルダ（なければ一時フォルダ）に置き、リポジトリには書かない。撮れないときは、見た目の指摘がコードからの推測になることを報告に書く。

画面が複数なら、画面ごとに分ける。

## 2. 前提を決める

合格基準は前提で決まる。次の順に探す（`feature-docs/config.json` があれば、その `paths` の置き場所に従う）:

1. `docs/product/ui-context.md` のこの画面の節
2. `docs/product/overview.md`、`docs/product/principles.md`、`actors.yaml`、仕様・要件（`docs/specs/`、`docs/requirements/`、`docs/design/`）

- `ui-context.md` の節が `状態: 仮` なら、報告の前提に「仮」と書き、合っているかを 1 回だけ確かめる。
- 見つからない項目は、AskUserQuestion の 1 回の呼び出しにまとめて尋ねる。画面が複数なら、主要ユーザーと方針は画面のあいだで使い回し、画面ごとに尋ねるのは目的だけにする。
- 「任せる」と言われたら、画面と文書から **仮の前提** を作り、報告に仮と書く。前提なしでは点検しない。

## 3. 別の目に任せる

サブエージェント `usable-ui:ui-reviewer` に任せる（見つからなければ、`general-purpose` に `${CLAUDE_PLUGIN_ROOT}/agents/ui-reviewer.md` の本文を指示として渡す）。画面が複数なら、画面ごとに並べて走らせる。渡すのは次だけ:

- 対象（ファイルのパス、画像のパス、撮ったスクリーンショットのパス）
- 前提（主要ユーザー・目的・方針と、決めたトレードオフ）
- checklist のパス: `${CLAUDE_PLUGIN_ROOT}/references/checklist.md`

**作ったときの意図や会話の経緯は渡さない。** 作り手の「自分にはわかる」を持ち込まないためにコンテキストを分けている。

## 4. 結果を確かめて見せる

返ってきた指摘を、種類に合った方法で確かめる。

- コードにあることの指摘: `path:line` を開き、書かれたとおりのコードがあるか。
- 何かが **ない** ことの指摘（処理中の表示がない、エラーの扱いがないなど）: その状態の扱いが本当にどこにもないかを Grep で確かめる。
- 画像の指摘: 画像を見て、その場所に書かれたとおりのものがあるか。

確かめられなかった指摘は「確かめきれなかったこと」に移し、**移したあとで件数と判定を数え直す**。確かめきれなかった必須問題・目的を妨げる問題が残るときは、判定を「合格」にせず「保留（人が確かめる）」にする。

次の形で見せる。画面が複数なら、画面ごとにこの形で出し、最初に一覧（画面と判定）を置く。全体は、すべての画面が合格のときだけ合格。

```markdown
## 判定: 合格 / 不合格 / 保留（目的を妨げる問題 N 件・必須問題 M 件・確かめきれなかったもの K 件）

## 前提
- 主要ユーザー / 目的 / 方針（仮なら「仮」と書く）

## 目的を妨げる問題（4 つの観点の外でも、操作しても目的が果たせない不具合）
1. `path:line` — <不具合>
   - 誰が何に困るか: …
   - 案: …

## 必須問題（目的の達成に関わる。人が責任を持って確かめる）
### A. シグニファイア
1. `path:line` — <問題>
   - 誰が何に困るか: <主要ユーザーが、どの場面で、どう迷う・誤解する>
   - 案: <直し方>
### B. フィードバック
### C. UX ライティング
### D. 情報設計

## 人が決めること（トレードオフ）
- <選択肢と、どちらを選ぶと誰が何に困るか>

## 応用問題（目的に影響しない。AI に任せてよい）
- `path:line` — …

## 範囲外のメモ（合否に数えない）
- …

## 確かめたこと / 確かめきれなかったこと
- …
```

該当のない節は「なし」と書く。目的を妨げる問題と必須問題が 0 件なら合格（checklist の 5 節）。最後の判断（主要ユーザーが迷わず目的を達成できるか）は人がする、と 1 行添える。

## 5. 直すよう頼まれたら

- 直すのは目的を妨げる問題と必須問題。応用問題は、頼まれたものだけ。人が決めることは、決まった選択肢のとおりに直す。決まったトレードオフは `ui-context.md` にあれば書き足す。
- 直したあとの確かめは、`usable-ui:ui-reviewer` に **前回の指摘と、直した箇所・その修正で影響を受けた箇所（確かめる範囲）** を渡して見てもらう。新しい観点を足して範囲を広げない。
- 「もう一度全部レビューして」と言われたら、くり返すと別の指摘が出続けて終わらないことを伝える。それでも求められたら行う。
