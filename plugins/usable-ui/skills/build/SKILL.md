# usable-ui:build: 迷わず使える UI を作る

AI は短い時間で見た目の整った画面を作れるが、前提を渡さないと、出せるデータを全部出し、どれが主要な操作かわからない画面になりやすい（80 点）。このスキルは、**作る前に前提を決め、作りながら 4 つの観点を守り、最後に人が判断できる形で渡す**。

基準は `${CLAUDE_PLUGIN_ROOT}/references/checklist.md`。最初に読む。

## 1. 前提を決める（作る前に）

### 1-1. 先に読む

質問の前に、リポジトリにある文書から前提を拾う（あるものだけ）:

- `docs/product/ui-context.md`（このスキルが残す前提の記録。この画面の節があれば、それを使う）
- `docs/product/overview.md`、`docs/product/principles.md`、`actors.yaml`
- 仕様・要件（`docs/specs/`、`docs/requirements/`、`docs/design/`）、README
- 同じアプリの近い画面（どんな人が何のために来るかの手がかり）

### 1-2. 下書きを見せて確かめる

この画面の **主要ユーザー・目的・方針**（checklist の 1 節）を下書きし、どの文書のどこから取ったかを添えて見せる。

- 文書から取れたものは、まとめて 1 回で確かめる。
- 取れなかったものは、AskUserQuestion で 1 問ずつ尋ねる。選択肢は、画面や依頼から考えられるものを 2〜4 個出す。
- 「任せる」と言われたら、下書きを **仮の前提** として進め、報告で仮であることを書く。

### 1-3. 記録する

`docs/product/ui-context.md` があれば、この画面の節を足す・直す。なければ、作ってよいかを 1 回だけ尋ねる（review が同じ基準で見られるようになる、と理由を添える）。断られたら作らない。

```markdown
## <画面の名前>（<ファイルのパス>）

- 主要ユーザー: …
- 目的: …
- 方針: …
- 決めたトレードオフ: <あれば。例: 全明細はトップに出さず、明細画面に回す>
```

## 2. 骨組みを決める（コードの前に）

新しい画面や大きな作り直しでは、次を短い表にする。

1. **出す情報の仕分け**: 主要（最初に、最も目立って）／補助（折りたたむ・後ろ・別の画面）／**削る候補**。削る候補には「なくても主要ユーザーが困らない理由」を書く。
2. **主要アクション**: 1 つに決める（多くても 2 つ）。ほかは見た目を弱くする。
3. **状態**: 読み込み中・空・成功・失敗（あり得るならオフライン・権限なし）で何を見せるか。

削る候補や、補助に回すことで誰かが困るものは **トレードオフ** なので、作る前に人に確かめる（checklist の 4 節）。ほかは確かめずに進めてよい。

## 3. 作る

- リポジトリにデザインシステムがあれば（`design-system/`、トークン、部品のライブラリ、文言の決まり）、その部品・トークン・文言に従う。4 つの観点と食い違うときは、勝手に変えずに報告で挙げる。
- 4 つの観点（checklist の 2 節）を守って書く。特に AI が落としやすいもの:
  - 主要アクションと他のボタンの見た目の差
  - 押した直後・処理中・失敗の状態（ハッピーパスだけで終わらせない）
  - エラー・空の状態の文言（原因だけでなく、次にすること）
  - 同じ比重で並んだカードの山（仕分けた主要・補助のとおりに強弱を付ける）

## 4. 1 回だけ点検する

作ったものを checklist の 2 節の順（A → B → C → D）に 1 回だけ見て、**必須問題** と目的を妨げる問題（checklist の 5 節）だけを直す。点検をくり返さない（直すたびに別の指摘が出て終わらなくなる）。応用問題（色合い・余白など、目的に影響しないもの）は直してよいが、点検の対象にはしない。

## 5. 渡す

次の形で報告する。

```markdown
## 前提
- 主要ユーザー / 目的 / 方針（仮なら「仮」と書く）

## 作ったもの
- <ファイル> — <画面の要約>

## 4 つの観点で織り込んだこと
- シグニファイア: …
- フィードバック: …
- UX ライティング: …
- 情報設計: … （削ったもの・補助に回したもの）

## 人が決めること
- <トレードオフ。選択肢と、どちらを選ぶと誰が何に困るか>（なければ「なし」）

## 確かめていないこと
- <動かして見ていない状態、実機で見ていない点など>
```

最後に、作った本人の点検は甘くなりやすいので、大きな画面なら `/usable-ui:review` で別の目に見てもらうことを 1 行で勧める。主要ユーザーが迷わず目的を達成できるかの最終判断は人がする。
