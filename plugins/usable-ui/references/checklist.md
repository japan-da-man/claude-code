# 使える UI のチェックリスト

build と review の両方が使う、合格の基準。考え方は CodeZine の連載「AIの出力に“デザインの視点”をプラスする ──エンジニアのためのUX改善入門」第5回（折原レオナルド賢、2026/10/27、<https://codezine.jp/article/detail/29762>）による。

## 0. 基準は「操作できる」ではなく「迷わず使える」

見た目が整い、データがそろい、仕様どおりに動く画面でも、どこを見ればよいか・何を押せばよいか・押したあと何が起きたかがわからなければ使えない。判定の問いは 1 つだけ:

> **前提に書いた主要ユーザーが、この画面で、迷わず疲れずに目的を達成できるか。**

作った本人（人も AI も）は画面の中身を全部知っているので、情報が多くても負担を感じない。だから「自分にはわかる」は基準にしない。

## 1. 前提（合格基準の土台）

点検の前に、次の 3 つを言葉にする。これがないと優先順位が決まらない（AI は前提がないと、出せるデータを全部出す）。

| 項目 | 書くこと | 例 |
| :- | :- | :- |
| 主要ユーザー | 誰が、どんな場面で使うか。最も重視する人 | 出張の合間にスマホで予約する会社員 |
| 目的 | この画面で達成したいこと（1 つ。多くても 2 つ） | 条件に合う部屋を選んで予約を確定する |
| 方針 | 迷ったときに何を優先するか | 速く確定できることを優先。比較は補助 |

全世代向けのサービスでも、最も重視する人や「誰でも使えることを優先する」といった方針は決められる。

## 2. 4 つの観点（この順に見る）

### A. シグニファイア：操作できることが伝わるか

- 主要アクションは画面に 1 つで、見た目で最も強いか。同じ強さのボタンが並んでいないか。
- 押せるもの（ボタン・リンク・行）が押せるものに見えるか。押せない飾りが押せそうに見えていないか。
- アイコンだけに頼らず、押すと何が起きるか予測できるラベルがあるか。
- 押せない状態（無効）は、なぜ押せないか・どうすれば押せるかがわかるか。
- 押せる範囲が十分か（目安: iOS 44pt、Android 48dp、Web は CSS の 24px 以上。Web をスマホで使うなら viewport の指定があるか）。

### B. フィードバック：操作のあとに何が起きているかわかるか

- 押した直後に反応があるか（押した感、ボタンの状態の変化）。
- 処理中が伝わるか。二重に送れないか。
- 成功したことが伝わるか（何が変わったか、次にどこへ行けばよいか）。
- 失敗したことと、その回復の手段が伝わるか。入力は失った状態にならないか。
- 「反応がない」「止まっている」「押せていない」と誤解される余地がないか。
- 読み込み中・空・エラー・オフライン（あり得るなら）の状態が用意されているか。

### C. UX ライティング：次に行動できる言葉になっているか

- ボタンは結果がわかる動詞か（「OK」「送信」より「予約を確定する」）。
- エラーは「何が起きたか」で終わらず、「次に何をすればよいか」があるか。
- システム都合の言葉（内部の用語、エラーコードだけ、DB の項目名）が出ていないか。
- 空の状態は、次の一歩を示しているか。
- 同じものを同じ言葉で呼んでいるか。

### D. 情報設計：必要な情報が適切な順序で出ているか

- 目的に必要な情報が最初に、最も目立って出ているか。
- 主要な情報と補助の情報が分かれているか（補助は折りたたむ、後ろに回す、別の画面にする）。
- 同じ比重のカードや項目が並び、どこから見ればよいか迷わないか。
- 目線の流れが、上から主要アクションまで途切れずにつながっているか。
- 判断に要る情報（料金・条件・期限など）が、それを使う操作の近くにあるか。
- 主要な情報が読めるか（文字の大きさ、背景とのコントラスト。目安: 本文 4.5:1 以上）。
- **引き算**: 「この情報がないと、主要ユーザーが目的の達成で何に困るか」に答えられない要素は、減らす候補。情報を一つも減らさずに配置だけで整理するのには限界がある。

## 3. 必須問題と応用問題

- **必須問題**: 4 つの観点に関わり、主要ユーザーの目的の達成に影響するもの。落とすと不合格。人が責任を持って確かめる。
- **応用問題**: 色合い・余白・角丸・細かな並びなど、4 つの観点を損なわず、目的の達成にも影響しない調整。点数を伸ばすもの。AI に任せてよい。

線引きは「デザインか実装か」ではなく「**目的の達成に関わるか**」。色や余白でも、見分けられない・押し間違える・読めない（コントラスト不足など）なら必須問題。

## 4. トレードオフは人が決める

情報を減らせば判断材料が減り、全部出せば負担が上がる。どちらが常に正しいとは言えない。改善案どうしがぶつかるとき、前提だけでは決まらないとき（例: 銀行のトップで、全明細を見たい人もいるが、残高と主要な操作より先に全明細を同じ比重で出すと別の人が迷う）は、AI が決めずに、選択肢と「どちらを選ぶと誰が何に困るか」を添えて人に返す。

## 5. 終わる条件

「もう一度レビューして」を繰り返すと、AI は次々に別の指摘を出し、直すたびに別の場所がわかりにくくなる。だから:

- 見る範囲は **4 つの観点と前提の目的** に限る。それ以外の気づきは「範囲外のメモ」に分け、合否に数えない。
- ただし、4 つの観点の外でも **目的の達成を直接妨げるもの**（入力した内容が送られていない、確定しても何も起きないなど、操作しても目的が果たせない不具合）は「目的を妨げる問題」として必須問題より前に出し、残っているあいだは合格にしない。好みや書き方の話はここに入れない。
- **必須問題と目的を妨げる問題が 0 件で合格**。応用問題が残っていても合格。確かめきれなかった必須問題が残るときは、合格にせず保留にして人が確かめる。
- 直したあとの確かめは、直した箇所と、その修正で影響を受けた箇所だけ。新しい観点を足して広げない。
- 最後に、主要ユーザーが迷わず目的を達成できるかを判断するのは人。
