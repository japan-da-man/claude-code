# factory 設計

AI エージェントで機能を作るソフトウェアファクトリーを、Claude Code プラグイン `factory` として作るための設計。まだ実装していない。

- 状態: 設計（2026-10-18 に一問一答で合意。仮置きだった点も確認済み）
- 目標の自律度: **レベル5（ダークファクトリー）**。人が承認するのは仕様と隠しシナリオだけで、コードは読まない
- 最初に対応するプロジェクト: **iOS アプリ**（シミュレーターで検証）

## 1. 考え方

- **正とするのは仕様とシナリオ**。コードは何度でも作り直せる生成物として扱う。
- **品質はコードレビューではなく検証で保証する**。実装役から見えない「隠しシナリオ」で受け入れ判定をする（StrongDM の holdout シナリオと同じ考え方）。テストに合格するためだけの実装（期待値のハードコード、テストの書き換えなど）を、見えない基準で防ぐ。
- **合否は確率で測る**。各シナリオを複数回実行し、「ユーザーが満足しそうな実行の割合（満足度）」で判定する。
- **作る側と試す側を分ける**。シナリオ作成・実装・検証・判定は、それぞれ別のセッション（別コンテキスト）で行う。実装役だけモデルを変えて、死角が重ならないようにする。
- **人が押さえるのは「何が正しいか」**。仕様はインタビューで AI が引き出し、シナリオは人が承認する。

## 2. 決まったこと

| 項目 | 決定 |
| :- | :- |
| 作るもの | 種類を問わない作り。プロジェクトの種類は初回に自動判定し、人が確認して設定に保存する |
| 最初の検証アダプター | iOS（シミュレーター） |
| 自律度 | レベル5のみ。レベル4への切り替えは作らない（設定の `autonomy` は将来のために置くだけ） |
| 投入単位 | 機能1つ。バグ修正・小さな改善も同じラインで流す |
| 入口 | 仕様インタビューは手元のセッション、実装と検証は裏で回す |
| 裏の実行 | 別の Claude Code セッション（ヘッドレス）。worktree で作業する |
| 実行場所 | ローカル（この Mac）のみ。クラウドへの差し替えの仕組みは作らない |
| 同時実行 | ラインは1本。確定した仕様は待ち行列に入れて順番に流す。インタビューは並行してできる |
| 権限 | 許可リスト方式（`dontAsk` モード＋許可する操作を列挙）。リストにない操作は止まらずに拒否される |
| モデル | Claude だけ。インタビュー: Opus / シナリオ作成: Opus / 実装: Sonnet / 検証: Sonnet / 判定: Opus。いずれも別コンテキスト。Pro の枠を考えても割り当ては変えない |
| ラインの進め方 | Node のスクリプトが工程を進め、実装・検証・判定だけを毎回新しい `claude -p` で呼ぶ（12節） |
| 別の会社のモデル | 使わない |
| 仕様の置き場所 | リポジトリ内 `docs/factory/<機能ID>/spec.md`。実装と同じ PR に含める |
| 隠しシナリオの置き場所 | リポジトリの外 `~/.factory/<プロジェクト>/<機能ID>/scenarios/`。実装役にはパスを渡さず、読み取りも禁止する |
| インタビューの終わり方 | 観点リスト（7節）が全部埋まったと AI が判断したら終える。人はいつでも打ち切れる |
| シナリオの本数 | 機能の大きさに応じて AI が決める。目安は5〜15本 |
| インタビューの形 | AskUserQuestion による一問一答（選択肢つき、おすすめを先頭に） |
| シナリオの承認 | 一覧で見せ、直したいものだけ対話で直し、最後に一括で承認する |
| 実装の進め方 | 仕様から TDD（見えるテストは実装役が自分で書く） |
| iOS でのシナリオ実行 | 検証役の Claude が [agent-device](https://github.com/callstackincubator/agent-device) の CLI でシミュレーターを操作する |
| 満足度の測り方 | 各シナリオ3回実行。全体の95%以上、かつ「必須」のシナリオは3回すべて合格 |
| 不合格の伝え方 | 判定役が「ユーザーから見て何が起きたか（症状）」だけを要約して実装役に渡す。手順・期待値・テストデータは渡さない |
| やり直しの上限 | 周回数のみ。初期値5周 |
| 上限で止まったとき | Draft PR と、どこで詰まったかの報告を残して止め、通知する |
| Pro の利用上限に達したとき | 進み具合を保存して一時停止し、枠が戻ったら自動で続きから再開する |
| 自動マージの条件 | 満足度の基準を満たす ＋ ローカルでビルドと全テストが通る（GitHub に CI があればその結果も待つ） ＋ 禁止ファイルを変更していない |
| 禁止ファイル | 初期設定のときに AI が候補を出し、人が承認して設定に保存する。iOS の `project.pbxproj` は新しいファイルを足すたびに変わるので、候補に入れない |
| 機能 ID とブランチ | 機能 ID は `YYYYMMDD-<短い英語名>`（例: `20261018-share-memo`）、ブランチは `factory/<機能ID>` |
| マージ方法 | 機能ごとに PR を作り、レポートをコメントしてから squash マージ |
| 通知 | Mac の通知と、PR へのレポート |
| 外部サービス | 最初は対象外（端末内で完結する機能が主な対象）。外部サービスを再現するモックサーバーは、あとから設定で差し込める口だけ用意する |
| 名前 | `factory`（コマンドは `/factory:start` など） |

## 3. 全体の流れ

```text
[手元のセッション]
  /factory:init            初回だけ。種類の判定・禁止ファイル・設定を作る
  /factory:start <要望>
    1. 仕様インタビュー（Opus, AskUserQuestion で一問一答）
       → docs/factory/<id>/spec.md
    2. シナリオ作成（Opus, 別コンテキストのサブエージェント）
       → ~/.factory/<project>/<id>/scenarios/*.md
    3. シナリオ承認（一覧 → 直したいものだけ対話 → 一括承認、必須の印をつける）
    4. 待ち行列に入れる。ラインが空いていれば起動する
                       │
[裏のライン（1本）]       ▼
    5. worktree を作る（ブランチ factory/<id>）
    6. 実装（Sonnet, TDD）。シナリオは見えない
    7. ローカルでビルドと全テスト
    8. 検証（agent-device でシミュレーターを操作。各シナリオ3回）→ 実行記録
    9. 判定（Opus, 別コンテキスト）→ 満足度と、不合格の症状
       ├ 基準未達で5周未満 → 症状だけを実装役に渡して 6 へ戻る
       ├ 基準未達で5周 → Draft PR と報告を残して停止、通知
       └ 基準を満たす → 10 へ
   10. マージ判定（満足度・テスト・CI・禁止ファイル）
   11. PR を作り、レポートをコメントして squash マージ
   12. 通知。worktree を片づけ、待ち行列の次を流す
```

## 4. 役割

| 役 | 動く場所 | モデル | 見えるもの | 見えないもの |
| :- | :- | :- | :- | :- |
| インタビュー役 | 手元のセッション（メイン） | Opus | 要望、リポジトリ | — |
| シナリオ作成役 | 手元のセッションのサブエージェント | Opus | 仕様、リポジトリ | — |
| 実装役 | 裏の Claude Code セッション（worktree） | Sonnet | 仕様、リポジトリ、前の周の症状 | シナリオ、満足度の内訳 |
| 検証役 | 裏の Claude Code セッション | Sonnet | シナリオ、ビルドしたアプリ | 実装の差分 |
| 判定役 | 裏の Claude Code セッション（新しいコンテキスト） | Opus | シナリオ、実行記録 | 実装の差分 |

検証役は**操作して記録するだけで、合否は決めない**。合否は判定役が、記録とシナリオだけを見て決める。

## 5. 置き場所

```text
<リポジトリ>/
  .factory/config.json             工場の設定（コミットする）
  docs/factory/<id>/spec.md        仕様（PR に含める）

~/.factory/
  queue/                           待ち行列（全プロジェクト共通。1件1ファイル）
  line.lock                        ラインが動いているかどうか（全プロジェクトで1本）
  <project>/
    <id>/
      scenarios/*.md               隠しシナリオ（実装役は読めない）
      runs/<周>/<シナリオ>/<回>/    実行記録（操作ログ、スクリーンショット、画面構造）
      judgements/<周>.json         判定結果（満足度、シナリオごとの結果、症状）
      state.json                   進み具合（周回数、一時停止中か、など）
      report.md                    PR に載せるレポート
```

`<project>` はリポジトリの絶対パスから作る短い名前。`<id>` は `YYYYMMDD-<短い英語名>`（日時は `date` で取る）。

## 6. 設定 `.factory/config.json`

Node の標準機能だけで読めるように JSON にする（YAML は依存パッケージが要るため使わない）。

```json
{
  "type": "ios",
  "ios": {
    "project": "App.xcodeproj",
    "scheme": "App",
    "bundle_id": "com.example.App",
    "device": "iPhone 17"
  },
  "autonomy": 5,
  "models": {
    "interview": "opus",
    "scenario": "opus",
    "implement": "sonnet",
    "verify": "sonnet",
    "judge": "opus"
  },
  "satisfaction": { "runs_per_scenario": 3, "threshold": 0.95 },
  "max_rounds": 5,
  "protected_paths": ["**/*.entitlements", ".github/workflows/**", ".factory/**"],
  "external_services": [],
  "notify": { "mac": true, "pr_report": true }
}
```

- `type` と `ios` は初回に自動判定して、人が確認する。`device` は検証に使うシミュレーター。
- `protected_paths` は初回に AI が候補を出し、人が承認する。
- `external_services` は、将来モックサーバーを差し込むための口。

## 7. 仕様インタビュー

- AskUserQuestion で一問一答。1回に出すのは、答えが前の答えに依存しない質問だけ（最大4問）。おすすめは先頭の選択肢に「(Recommended)」をつける。
- 調べれば分かること（既存の画面、使っている仕組みなど）は質問せず、自分で調べる。
- 次の**観点リスト**がすべて埋まったら終える。人が「もう十分」と言えば、そこで打ち切る。
  - 目的（なぜ必要か）／対象ユーザー
  - 正常系（主な操作の流れ）
  - 異常系・エッジケース（空、上限、通信なし、権限なし、途中で中断）
  - やらないこと
  - 既存機能への影響
  - 画面と操作（どこに何が出るか）
  - データ（何を保存するか、移行は必要か）
- 仕様は `spec.md` に、観点ごとの見出しで書く。末尾にインタビューの問答の要約を残す。

## 8. 隠しシナリオ

形式（1シナリオ1ファイル）:

```markdown
---
id: share-02
title: 共有した相手の一覧に反映される
required: true        # 必須。3回すべて合格が条件
---
## 前提
- メモが1件ある

## ユーザーの操作
1. メモを開いて共有ボタンを押す
2. ...

## 期待する結果（画面で確かめられること）
- ...
```

- 手順と結果は**ユーザーから見える言葉**で書く（コードの名前は書かない）。こうしておくと、実装が変わってもシナリオが壊れにくい。
- 本数は機能の大きさに応じて AI が決める（目安5〜15本）。
- 承認のときに、人が「必須」の印をつける（AI が候補を提案する）。

## 9. 満足度と判定

- 判定役は、1回の実行ごとに「この実行でユーザーは満足しそうか（はい／いいえ）」と、いいえの場合の**症状**を出す。
- 満足度 ＝ 満足した実行の数 ÷ すべての実行の数（シナリオ数 × 3回）。
- 合格の条件は、満足度95%以上、かつ必須シナリオが3回すべて合格。
- 実装役に渡すのは症状の一覧だけ。例：「共有したあと、相手側の一覧に新しいメモが出ない」。シナリオの手順・期待値・テストデータは渡さない。

## 10. iOS の検証アダプター

- ビルド: `xcodebuild`（scheme と simulator は設定から）。全テストも `xcodebuild test` で実行する。
  - シミュレーターは名前から UDID を引いて指定する。同じ名前が複数の iOS にあれば、いちばん新しい iOS のものを使う。ほかに起動中のシミュレーターがあっても取り違えない
  - `project.yml` があれば、先に `xcodegen generate` を実行する（`ios.prebuild` で上書きできる）
  - ビルド結果（DerivedData）はリポジトリの外に置き、実装役が誤ってコミットしないようにする
- 操作: agent-device の CLI。`snapshot -i` でアクセシビリティツリー（`@e5` のような参照つき）を読み、`click @e5` などで操作し、`screenshot` を撮る。
  - 2026-10-18 にサンプルアプリで確かめた：`fill 'id="memo-input"' "milk"` → `click 'id="memo-add"'` で一覧に追加されたことが差分で分かる。初回は操作用のランナーのビルドに数分かかるので、`open` には長めの `--timeout` を付ける
  - 日本語の入力（`fill` に日本語を渡す）は、シミュレーターでは失敗した。シナリオで入力するテストデータは英数字にする
- 検証役は、シナリオを読んで1回ずつ操作し、操作ログ・スクリーンショット・画面構造を `runs/` に残す。
- 毎回アプリを入れ直してから始め、前の実行の状態を持ち越さない。
- この Mac はメモリ 8GB なので、シミュレーターは1台だけ使う（ラインが1本なのはこのため）。

アダプターは「ビルド」「全テスト」「アプリの起動・初期化」「1シナリオの実行と記録」の4つの口を持つ形にする。Web や CLI のアダプターは、この4つを別の方法で実装して足す。

## 11. 権限と隔離

- 裏のセッションは `claude -p --permission-mode dontAsk` で、役ごとに許可する操作を列挙する。
  - 実装役: ファイルの読み書き、`xcodebuild`、`git`（push は除く）など。`gh` は許可しない。
  - 検証役: `agent-device`、`xcrun simctl`、記録先への書き込み。
  - 判定役: シナリオと記録の読み取り、判定結果の書き込み。
- PR の作成とマージ、通知は、モデルではなく**ラインのスクリプトが行う**。
- 実装役からシナリオを隠す方法:
  1. シナリオのパスを渡さない
  2. permissions の deny で `~/.factory/` の読み取りを禁止する
  3. Bash 経由の読み取り（`cat` や `python` など）も防ぐため、サンドボックスで読み取りを禁止する。設定は `--settings` で渡す:
     `{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false, "failIfUnavailable": true, "filesystem": {"denyRead": ["<工場の置き場所>"]}}}`。
     サンドボックスが起動できなければ、実装役のセッションは始まらない
  - 2026-10-18 に Haiku で確かめた結果：隠したフォルダのファイルは、Bash の `cat` では `Operation not permitted`、Read ツールでは「permission settings で拒否」となり、どちらでも読めなかった
  - サンドボックスが効くのは Bash（とその子プロセス）だけで、Read などのツールは permissions の deny で塞ぐ。`dontAsk` モードでは、作業ディレクトリの外の読み取りはもともと拒否される
  - `xcodebuild` はサンドボックスの中だとシミュレーターのサービス（CoreSimulatorService）に繋がらず、`xcodebuild test` が動かない。そこで `xcodebuild` と `xcodegen` だけを `excludedCommands` でサンドボックスの外で動かす。こうしても、`cat` での読み取りは引き続き防げることを確かめた
  - 残る抜け道：実装役がビルドの設定（`project.yml` のスクリプトなど）に読み取りの処理を書き込めば、サンドボックスの外の `xcodebuild` から読める。故意にやらない限り起きないが、完全には防げていない

## 12. ラインの実行方式

ラインは **Node のスクリプトが工程を順に進める**（Stripe の Blueprint と同じ考え方）。worktree の作成、ビルド、テスト、満足度の計算、マージ判定、PR、通知のように手順が決まっている工程はスクリプトが行い、モデルを呼ぶのは実装・検証・判定だけにする。`claude --bg` で監督役のセッションに全部任せる方式は採らない。監督役がシナリオも実装も見られてしまい、役ごとの隔離が崩れるため。

- 手元のセッションは、待ち行列に入れたあと、ラインが止まっていればスクリプトをバックグラウンドで起動する。起動したらすぐ手元に戻る。
- 各工程の役は、`claude -p --model <モデル> --permission-mode dontAsk --allowedTools ... --output-format json` で、毎回新しいセッションとして呼ぶ。
- 工程ごとに `state.json` に記録するので、途中で止まっても続きから再開できる。
- Pro の利用上限に達したら一時停止し、枠が戻る時刻まで待ってから同じ工程をやり直す。この待ち時間は周回数に数えない。
- 進み具合の確認は `/factory:status` で行う（待ち行列、動いている機能、周回数、直近の満足度）。
- worktree とビルド結果は `~/Library/Caches/factory/<project>/` に置く。`~/.factory` の下に置くと実装役から見えなくなり、リポジトリの中に置くと誤ってコミットされるため。
- 仕様は `~/.factory/<project>/<id>/spec.md` から worktree に写し、ブランチの最初のコミットにする。手元のチェックアウトには触らない。
- ビルドか全テストが通らなかった周は、検証と判定を飛ばし、失敗したコマンドとログの末尾を症状として次の周に渡す。禁止ファイルを変更した周も、そのことを症状として渡す。
- GitHub の CI が落ちたときは、その場で止めて通知する（PR は残す）。

## 13. プラグインの構成（案）

```text
plugins/factory/
  .claude-plugin/plugin.json
  skills/
    init/SKILL.md         /factory:init    種類の判定、禁止ファイル、設定、agent-device の確認
    start/SKILL.md        /factory:start   インタビュー → 仕様 → シナリオ → 承認 → 待ち行列
    status/SKILL.md       /factory:status  ラインと待ち行列の状態
  agents/
    scenario-writer.md    シナリオ作成役（model: opus）
  line/
    line.js               ラインのスクリプト
    cli.js                スキルから呼ぶ CLI（new: 機能 ID と置き場所 / submit: 待ち行列とラインの起動 / status）
    claude.js             役ごとの claude -p の呼び出し（隔離と利用上限の待機）
    config.js paths.js queue.js state.js gate.js prompts.js
    adapters/ios.js       iOS アダプター
    prompts/              実装・検証・判定の役に渡すプロンプト
  tests/                  node --test（偽の claude・gh を使った統合テストを含む）
```

## 14. 試運転の記録

### 1回目（2026-10-18、サンプルアプリ「メモの件数を表示」、シナリオ3本・各1回・2周まで）

- 結果: 2周で止まった（満足度 1周目 33%、2周目 0%）。Draft PR が残った。
- **実装は正しくできていた**: 見出しに「N 件」を出す変更と、TDD のテスト2件（追加・削除・空白だけのメモ・開き直し）。1周目の memo-count-01（追加で「1 件」→「2 件」）は合格。
- 落ちた原因は工場の検証の側にあった:
  1. 検証役が複数の操作を `&&` でつないで1回の Bash にしたため、許可リスト（`Bash(agent-device *)`）に合わず拒否された。
  2. 検証役が途中でやめたときにセッションを閉じなかったため、シミュレーターが使用中のまま残り、以降の実行がすべて `DEVICE_IN_USE` になった。
  3. 道具の都合で検証できなかったことまで、症状として実装役に渡っていた。
- 直したこと:
  - ラインが、検証の実行の前後で必ずセッションを閉じる。
  - 検証役のプロンプトに「Bash 1回につき agent-device のコマンド1つ」と書いた。
  - 検証役に `result.json` を書かせ、道具の都合（`blocked_by_tool`）を区別する。その場合は1回やり直し、それでもだめなら工場のエラー（状態 `error`）として止め、実装役には何も渡さない。
  - 工程が変わるたびにログに1行残す。

### 2回目（同じ仕様とシナリオ、機能 ID `20261018-memo-count-2`）

- 結果: **1周目で満足度 100%**（必須3本すべて合格）、ビルドと全テストも通過し、自動マージの条件をすべて満たした。PR #2 は GitHub で squash マージされた。
- かかった時間: 約8分（実装 37秒、ビルドと全テスト 1分半、検証3本 4分半、判定 1分）。
- 最後に1つ失敗した: `gh pr merge --squash --delete-branch` は、マージのあとで手元のチェックアウトを main に切り替えようとし、main が元のチェックアウトで使われているため worktree では失敗した（マージ自体は済んでいた）。
- 直したこと: `--delete-branch` を付けず、リモートのブランチはラインが `git push origin --delete` で消す。マージのコマンドが失敗しても PR がすでに MERGED なら成功とみなし、同じ工程をやり直せるようにした。merge の工程から再開して、マージ済みとして片づけ（リモートのブランチ・worktree・手元のブランチ）まで済むことを確かめた。

### 3回目（プラグインとしてインストールした状態。機能「空白だけのメモに『メモを入力してください』と出す」）

- 別のセッションで、`/factory:init`・`/factory:start`・`/factory:status` をスキルとして実際に呼んだ。3つとも最後まで動き、1周目で満足度100%、PR #3 が自動で squash マージされた（submit から約13分）。
- `${CLAUDE_PLUGIN_ROOT}` はインストール先のパスに、`$ARGUMENTS` は要望の文に置き換わった。`factory:scenario-writer` も呼べた。`/factory:status` は、ヘッドレスの通常の権限モードでも、許可の確認なしに動いた。
- そのセッションは auto モードだったので、`init` と `start` の `allowed-tools` が通常の権限モードで足りているかは確かめていない。
- 見つかった問題と直したこと:
  - 手元の main が origin より遅れていて、シナリオ作成役は古いコードを読んだ（ラインは origin/HEAD から始めるので、前提が食い違う）。→ `/factory:start` の最初に `git fetch` し、遅れていれば pull してよいか尋ねる。
  - シナリオ承認の「直すシナリオ」と「必須にするシナリオ」は、答えが互いに関係しないので、1回の質問にまとめた。
  - `line.log` に毎回 ExperimentalWarning が出ていた。→ ラインを `--disable-warning=ExperimentalWarning` で起動する。

## 15. リスクと未解決の点

- **判定役も LLM**。作る側と採点する側が同じ種類の技術なので、評価が循環する。最初のうちは、判定結果と、人が実際にアプリを触った感想が一致するかを見る。
- **Pro の利用枠**。1機能でシナリオ10本なら、1周の検証と判定で30回の実行が要る。何機能を流せるかは、実際に回して測る。
- **agent-device はまだ初期段階**の道具。不具合があれば XcodeBuildMCP（UI 操作の機能あり）に差し替える。
- **シナリオの隠し方**。同じユーザー権限で動くので、サンドボックスがなければ完全には隠せない。
- **症状からシナリオが推測できる**。症状だけでも、繰り返すうちにシナリオの中身が伝わることはある。
- **8GB の Mac**。ラインが動いている間は、ビルドとシミュレーターで Mac の普段使いが重くなる。
