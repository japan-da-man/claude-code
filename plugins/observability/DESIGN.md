# observability の設計

アプリの「何が起きているかを知る」仕組み（障害の確認・ログ・計測と分析・SLO・リリースの健全性）を、**観点ごとに AI と壁打ちして決め、その決定どおりの基盤をコードと運用文書として置く** ためのプラグイン。言語やフレームワーク（iOS・Android・Expo・Flutter・Web・Node・Python・Go・Rails・JVM）ごとの定番は `references/stacks/` に持ち、リポジトリから見つけたスタックに合わせて選択肢を出す。

## なぜ「壁打ち」なのか

ログや計測の基盤は、道具を入れるだけなら 1 時間で終わる。難しいのは「何のために、何を、どこまで取るか」で、ここを決めずに入れると、誰も見ないダッシュボード、意味の揃わないイベント、個人情報の混じったログ、毎月の請求だけが残る。だから init は、道具の前に **目的（守りたい体験と KPI）** を決め、そこから観点ごとに「取るもの・取らないもの・見る人・見るタイミング」を決める。AI は選択肢を並べるだけでなく、おすすめと理由、費用やプライバシーの危うさ、前の答えとの矛盾を指摘する。

## 観点

| # | 観点 | id | 決めること | 置くもの |
| - | - | - | - | - |
| 1 | 目的と範囲 | `scope` | 守りたい体験（クリティカルな流れ）、KPI、規模とチーム、データの置き場所の制約、予算 | README の「目的」 |
| 2 | 障害の検知と確認 | `incident` | エラー・クラッシュの監視、アラートの条件と通知先、重要度、誰が対応するか、runbook | エラー監視の初期化、`alerts.yaml`、`runbooks/` |
| 3 | ログ | `logging` | 構造化の形、レベルの使い分け、必須の項目、相関 ID、送り先と保持期間、モバイルのログをどこまで送るか | ロガー、`logging.md` |
| 4 | 計測と分析 | `analytics` | 答えたい問い、道具、イベントの命名、トラッキングプラン、利用者 ID のつなぎ方 | 型つきの計測ラッパー、`events.yaml` |
| 5 | メトリクス・トレース・SLO | `metrics` | SLI と SLO、RED / USE のメトリクス、分散トレースを入れるか、ダッシュボード | 計測の初期化、`alerts.yaml` の `slos` |
| 6 | リリースの健全性 | `release` | クラッシュのない割合、リリースどうしの比較、dSYM・ソースマップ・mapping のアップロード、段階リリース | CI の設定、リリースの識別子 |
| 7 | プライバシーとコスト | `privacy` | 送ってはいけない項目、マスキング、同意（ATT・Cookie）、保持期間と削除の依頼、量とサンプリング | マスキングの処理、`logging.md` と `events.yaml` の決まり |
| 8 | 運用 | `operations` | 誰がいつ何を見るか（週次の振り返り）、障害の記録とポストモーテム、決まりの見直し | README の「運用」、`incidents/` |

観点の中身・質問・おすすめは `references/perspectives.md`。決めた観点は `observability/config.json` の `progress` に id を足していく。途中で止めても、足りない観点から再開できる。

## アプリのリポジトリに置くもの

| ファイル | 中身 | 正本 |
| --- | --- | --- |
| `observability/README.md` | 観点ごとの決定と理由、使う道具、見る場所（ダッシュボードの URL など）、運用 | 決定の記録 |
| `observability/config.json` | スタック、道具、決めた観点、チェッカーの設定 | 機械が読む設定 |
| `observability/logging.md` | レベル、必須の項目、書いてはいけないもの、例 | ログの決まり |
| `observability/events.yaml` | トラッキングプラン（イベント・プロパティ・共通のプロパティ） | 計測の決まり |
| `observability/alerts.yaml` | SLO とアラート（条件・重要度・通知先・runbook） | アラートの決まり |
| `observability/runbooks/*.md` | アラートごとの確かめ方・切り分け・対処・エスカレーション。`_triage.md` は共通の切り分け | 対応の手順 |
| `observability/incidents/*.md` | 障害の記録とポストモーテム | 履歴 |
| `observability/check.mjs` | チェッカー（プラグインがなくても CI で動く） | — |

ダッシュボードやアラートそのものは、道具の側（Sentry・Datadog・Grafana など）にある。リポジトリの `alerts.yaml` は「何を、なぜ、誰に」の正本で、道具の設定がずれたら直すのは道具の側。Terraform などでアラートをコードにしているなら、それを `alerts.yaml` から作る（init で決める）。

アプリのコードに置くもの（ロガー、エラー監視の初期化、計測のラッパー、相関 ID、マスキング）は、スタックの決まった場所に、そのリポジトリの書き方で置く。値はコードに書かず、環境変数と `.env.example`（名前だけ）を置き、値の設定は人に頼む。クライアント（アプリ・ブラウザ）に入れた値は、ビルド設定や環境変数を通しても、誰でも取り出せるので、クライアントに入れてよいのは **送信にしか使えない値**（エラー監視の DSN、計測の書き込み用のキーなど）だけ。ソースマップのアップロード用のトークン、管理用の API キー、計測の secret は **CI とサーバーにだけ** 置く。エラー監視の「既定で個人情報を送る」設定（Sentry の `sendDefaultPii` など）は false のままにする。

## チェッカー（scripts/check.mjs）

feature-docs と同じく、アプリのリポジトリの `observability/check.mjs` に写して、CI でもプラグインなしで動かす。依存はなく、YAML は小さな読み込みで読む（feature-docs と同じもの）。

- `events.yaml`：名前の形（既定は `object_action` の snake_case）と重複、`description`・`owner`・`status`（`planned` / `active` / `deprecated`）、プロパティの型（`enum` は `values`）、**個人情報らしいプロパティ名**（email・phone・address など。`pii_reviewed` に理由を書けば通す）。
- `alerts.yaml`：id の形と重複、重要度、SLO の目標（0〜100）と期間、アラートが指す SLO と runbook があること、runbook に必要な節があること、どのアラートからも指されない runbook（警告）。
- `incidents/`：重要度と状態。`resolved` はポストモーテムの節が必要。
- コード：`config.code` の正規表現で、**計測の呼び出しにあるイベント名がトラッキングプランにあるか**（ないものは誤り、`active` なのにコードにないもの・`deprecated` を呼んでいるものは警告）と、**禁止の書き方**（`console.log`・`print` の直書き、ログに token を出すなど。ロガー自身などの許可したパスは除く）を調べる。正規表現はスタックごとの例が `references/stacks/` にあり、init でラッパーの形に合わせて書く。

正規表現でコードを読むのは、言語を問わず動かすため。正確さより「計測の呼び出しを型つきのラッパーに寄せる」ことで漏れを減らす（ラッパーの外で計測を呼ぶ書き方を禁止の書き方に入れる）。

## スキル

| スキル | 役割 |
| --- | --- |
| `init` | リポジトリを調べ（`cli.mjs detect`）、観点ごとに壁打ちで決め、計画の承認をもらってから、基盤のコードと運用文書を置く。再実行すると、決めていない観点か、選んだ観点だけをやり直す |
| `event` | 計測のイベントを足す・変える。答えたい問いから決め、`events.yaml` とラッパーと呼び出しを直す |
| `triage` | 障害の確認。症状かアラートから、runbook に沿って影響と時間を確かめ、ログ・エラー・デプロイの履歴から切り分け、`incidents/` に記録する。実行するのは読むだけの操作（一覧・取得・ログの表示）に限り、ロールバック・フラグ・監視の道具の ack や mute・インフラの操作・通知は、人の手順として渡す（人がその操作を「実行して」と言ったときだけ 1 つ実行する）。記録には個人情報と秘密の値を貼らない |
| `check` | チェッカーの結果と、観点の進み具合を見せる。直さない |

## ほかのプラグインとの関係

- **feature-docs**：イベントの定義は `observability/events.yaml` に 1 か所だけ置き、feature-docs の `tracking/F-xxx.yaml` には名前と KPI だけを書く（feature-docs の `design` と `build` は、`observability/events.yaml` があればそうする）。init で、すでに `tracking/*.yaml` に定義があれば events.yaml に移し、tracking には名前と KPI だけを残す。
- **dev-flow**：基盤のコードを入れるときは、あれば `dev-flow:tdd` の進め方で、マスキングとラッパーにテストを書く。
- **blast-radius**：`triage` が提案するロールバックなどのコマンドは、人が実行するときにも止まる。
