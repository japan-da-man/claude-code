# 観点と壁打ちの進め方

`/observability:init` が観点ごとに読む。各観点は「調べること → 聞くこと → 突っ込むこと → 決まったら書くもの」の順。

## 壁打ちの姿勢

- **選択肢を並べるだけにしない**。おすすめを 1 つ決め、理由を 1〜2 行で言う。理由は「このリポジトリで見つけたこと」か「前の観点で決めたこと」に結びつける。
- **前の答えとの矛盾を指摘する**。例：「目的で『決済の失敗を 5 分で知りたい』と言ったのに、サーバーのログを 1 日 1 回しか見ない運用です」。
- **費用・プライバシー・運用の重さを先に言う**。「全部のログを送る」「全画面を自動で計測する」「全リクエストをトレースする」は、量と請求と個人情報で後から困る。
- **小さく始める**。最初に入れるのは、目的に直結する最小のもの。残りは README の「あとでやること」に書く。
- **調べれば分かることは聞かない**。今のロガー、エラー処理、計測の呼び出し、デプロイ先はコードと CI から読む。
- 答えが「わからない」「おまかせ」なら、おすすめで決めて、理由と「あとで見直す条件」を記録に書く。

## 1. 目的と範囲（scope）

調べる：README・`docs/product/`・feature-docs の `docs/product/overview.md` があれば KPI。画面のルート、決済・認証・同期などのクリティカルそうな流れ。

聞く：

- 守りたい体験はどれか（クリティカルな流れを 3 つまで）。選択肢はコードから見つけた流れで作る（ログイン、決済、投稿、同期…）
- 何が分かれば成功か：障害に早く気づく / 原因を早く突き止める / 機能が使われているか知る / リリースの品質を比べる（複数選択）
- 規模とチーム：利用者数の桁、見る人（開発者だけ / CS も / PM も）、オンコールの有無
- 制約：データの置き場所（国内リージョン必須か）、使える予算（無料枠の範囲 / 月 数万円 / 制約なし）、すでに会社で契約している道具

突っ込む：「全部大事」は決めていないのと同じ。3 つに絞ってもらう。見る人がいないなら、アラートより週次の振り返りから始める。

書く：README の「目的と範囲」。

## 2. 障害の検知と確認（incident）

調べる：今のエラー監視の SDK、グローバルなエラーハンドラ（`ErrorBoundary`・`Thread.setDefaultUncaughtExceptionHandler`・`FlutterError.onError`・フレームワークの例外ハンドラ）、握りつぶしている `catch`、ヘルスチェックのエンドポイント。

聞く：

- エラー・クラッシュの監視の道具（スタックの定番から。会社の契約を優先）
- 通知先：Slack のチャンネル / PagerDuty・Opsgenie / メール。夜間に起こすか
- 重要度の定義（sev1〜sev3 の例と、誰がいつまでに動くか）。おすすめの既定：sev1 = 主要な流れが全員で失敗・データの損失（すぐ）、sev2 = 一部の利用者か主要でない流れ（営業時間内に当日）、sev3 = 不便だが回避できる（次のスプリント）
- 最初のアラート：目的のクリティカルな流れごとに 1 つ。「新しい種類のエラーが出た」「エラー率がいつもの N 倍」「クラッシュのない割合が X% を下回った」から選ぶ
- 外形監視（Uptime の監視）とステータスページが要るか

突っ込む：アラートの数を絞る（最初は 3〜5 個）。鳴っても誰も動かないアラートは作らない。runbook を書けないアラートは、まだ条件が決まっていない。握りつぶしている `catch` は、ここで直すか、あとでやることに入れる。

書く：エラー監視の初期化コード、グローバルなエラーハンドラ、`alerts.yaml` の `alerts`、アラートごとの runbook（`template runbook`）、README の重要度の表。

## 3. ログ（logging）

調べる：今のロガー（`console.log`・`print`・`NSLog`・`Log.d` の直書きの数）、ログの出力先（標準出力・ファイル・クラウドのログ）、リクエスト ID やトレース ID があるか。

聞く：

- 形：JSON の構造化ログ (Recommended、サーバー) / プラットフォームの標準（OSLog・Logcat）に出し、エラー監視のパンくずに残す (Recommended、モバイル)
- 送り先と保持期間：クラウドの標準（CloudWatch・Cloud Logging）/ Datadog・Grafana Loki・Axiom など / 送らない。保持は 7・30・90 日
- 必ず付ける項目（`logging.md` の表から足し引き）と、相関 ID のつなぎ方（モバイル → API にヘッダーで `traceparent` か `x-request-id` を渡す）
- 本番で出すレベル（info 以上が既定）。debug を本番で一時的に上げる手段が要るか

突っ込む：モバイルのログを全部サーバーに送るのは高くつき、個人情報も混じる。送るのはエラーの前後（パンくず）だけにするのが定番。`message` に値を埋め込むと検索も集計もできない。

書く：ロガー（マスキングつき）、リクエスト / トレース ID のミドルウェア、`logging.md`、`config.code.forbidden` に直書きの禁止。

## 4. 計測と分析（analytics）

調べる：今の計測の SDK と呼び出し（`track(`・`logEvent(`・`capture(`）、イベント名の揺れ、画面の一覧、ログインの処理（利用者 ID をどこでつなぐか）。

聞く：

- 答えたい問い（3〜5 個）。例：登録の完了率、主要な機能の利用率、継続率、課金への転換。**イベントは問いから作る**
- 道具：スタックの定番と、目的・予算から（Firebase Analytics・Amplitude・PostHog・Mixpanel、自前で BigQuery など）
- 命名：`object_action` の過去形 snake_case (Recommended) / 既存の名前に合わせる
- 利用者 ID：ログインで `identify` する / しない。ログイン前とのつなぎ方。ID はアプリ内部の ID（メールは使わない）
- 自動計測（画面表示・タップの自動収集）を使うか：使わない (Recommended、意味が揃わない) / 画面表示だけ使う

突っ込む：「とりあえず全部取る」は、後で誰も読めないイベントが溜まるだけ。問いに答えないイベントは作らない。同じことを別の名前で 2 つ送らない（`signup_done` と `register_completed`）。プロパティに自由な入力（検索語）を入れるなら、個人情報にならないか確かめる。

書く：型つきの計測ラッパー（イベント名とプロパティを型にする。ラッパーの外で SDK を呼ばない）、`events.yaml` の最初のイベント（問いに答える分だけ）、`config.code.event_calls` と、SDK の直接の呼び出しの禁止。

## 5. メトリクス・トレース・SLO（metrics）

調べる：サーバーがあるか、ホスティング（Vercel・Cloud Run・ECS・Kubernetes）、今のメトリクス（Prometheus・CloudWatch・APM）、外部 API やキュー。

聞く：

- SLO を置く流れ（目的のクリティカルな流れから）と SLI（可用性：成功した割合 / レイテンシ：p95 が X ms 以下）、目標（99.0・99.5・99.9）、期間（30d が既定）
- メトリクス：RED（Rate・Errors・Duration）をリクエストごとに / USE（Utilization・Saturation・Errors）を資源ごとに。ホスティングの標準で足りるか
- 分散トレース：入れない / OpenTelemetry で入れる（サンプリング率）/ APM の SDK で入れる。サービスが 1 つなら、まず入れなくてよい
- ダッシュボード：1 枚（目的の流れの SLO と RED）から始める

突っ込む：99.99% は月 4 分しか止められない。チームの対応速度と合っているか。SLO を置くなら、エラーバジェットを使い切ったときに何をするか（リリースを止めるか）も決める。モバイルだけのアプリなら、SLO はクラッシュのない割合と主要な API の成功率で足りることが多い。

書く：`alerts.yaml` の `slos`、メトリクス・トレースの初期化、README のダッシュボードの URL（作るのは人。手順を書く）。

## 6. リリースの健全性（release）

調べる：リリースの仕組み（Xcode Cloud・fastlane・EAS・Codemagic・GitHub Actions・Vercel）、バージョンの付け方、フィーチャーフラグ、段階リリース。

聞く：

- リリースの識別子：アプリのバージョン＋ビルド番号 / git の SHA。エラー監視とログと計測に同じ値を付ける
- シンボル：dSYM（iOS）・mapping.txt（Android の R8）・ソースマップ（JS・Hermes）・`--split-debug-info`（Flutter）を CI でアップロードする
- 良し悪しの基準：クラッシュのない利用者の割合（例：99.5% 以上）、新しいエラーの数。段階リリースを止める条件
- OTA 更新（EAS Update など）があるなら、その更新にも識別子を付けるか

突っ込む：シンボルがないとスタックトレースが読めず、2 の監視が役に立たない。止める条件を決めていない段階リリースは、ただ遅いだけ。

書く：CI のシンボルのアップロード、リリースの識別子の設定、README の基準。

## 7. プライバシーとコスト（privacy）

調べる：プライバシーポリシーの場所、同意の UI（ATT・Cookie バナー）、iOS の `PrivacyInfo.xcprivacy`、Google Play のデータセーフティ、ログと計測に出している項目。

聞く：

- 送らないもの（`logging.md` の「書いてはいけないもの」に足し引き）。マスキングはキー名で伏せる (Recommended) / 送る前に許可した項目だけ残す（より安全、手間が多い）
- 同意：計測は同意の後だけ / 同意なしでも匿名で送る。iOS の ATT が要るか（他社のアプリやサイトのデータと結びつけてトラッキングするとき。広告の効果測定の SDK やデータブローカーに渡すのも含み、IDFA を使うかどうかでは決まらない）
- 保持期間と削除：削除の依頼があったら、計測とエラー監視のどこから消すか（各道具の削除 API）
- 量と費用：エラー監視のサンプリング（エラーは全部・パフォーマンスは 10% など）、ログの量の上限、月の予算を超えたら気づく仕組み

突っ込む：SDK を入れると、プライバシーマニフェストとストアの申告も変わる。エラー監視の「リクエストの本文を送る」「画面の録画（Session Replay）」は既定でオフにして、要るなら理由を書く。

書く：マスキングの処理とテスト、`events.yaml` の `pii_reviewed` の運用、README の保持期間と費用。プライバシーマニフェストやストアの申告で変えるべき点は、人がやることとして一覧にする。

## 8. 運用（operations）

聞く：

- 誰がいつ何を見るか：アラートは受けた人がすぐ / エラー監視の新しいエラーは毎朝 / 計測とSLOは週次の振り返り
- 障害の記録：sev2 以上は `incidents/` に記録し、sev1 はポストモーテムを書く (Recommended)
- 見直し：アラートが鳴りすぎ・鳴らなすぎを月に 1 回見直す。使われないイベントを deprecated にする
- CI：`observability/check.mjs` を PR ごとに動かすか

突っ込む：見る人と時間が決まっていない仕組みは、障害の日まで誰も開かない。週次の 15 分を決めるだけで十分なことが多い。

書く：README の「運用」、CI、CLAUDE.md への案内。
