# self-improve

Claude Codeが同じ失敗を二度しないようにするためのプラグインです。

失敗と作業中の気づきを記録し、改善候補としてためます。件数の重なった候補は、決めた日時に仕組みが自分で検討し、試用のルールやSkillとして追加・編集します。結果は次のセッション開始時に報告します。定着させるかどうか、自分専用にするかチームへ出すかは、人が決めます。

設計の全体は [DESIGN.md](./DESIGN.md)（自己改善ハーネス 設計書）を参照してください。このREADMEは使い方だけを書きます。

**2.0 から、user 単位で動きます。** プラグインを入れるだけで、すべてのgitリポジトリで動きます（リポジトリごとの `init` は要りません）。失敗票、設定、自分専用のルールは `~/.claude/self-improve/` に置き、リポジトリには置きません。1.x から移るときは、下の「1.x からの移行」を見てください。

いま入っているのは、設計書11章のステップ1（記録・ガード・検証・振り返り）とステップ2（自動改善と確認）までです。棚卸し（`harness-prune`）は**未実装（ステップ4）**です。実機でまだ確かめていない点は、DESIGN.md の14章「実機で確かめること」にまとめています。

## 前提

- Claude Code（端末、またはデスクトップアプリのローカルのセッション）
- Node.js 22以降（hookのスクリプトと `harness-note` コマンドが `.mjs` のため。外部のパッケージは使わず、ネットワークにも出ません）
- 作業する場所がgitリポジトリであること（gitリポジトリでない場所では、何もしません）
- 日時で動かす場合は、Claudeデスクトップアプリ（[SCHEDULING.md](./SCHEDULING.md)）

このプラグインは `bin/` にコマンド（`harness-note`）を持ちます。公式ドキュメントによると、直下に `bin/` を持つプラグインは、claude.ai と Cowork ではインストールされません。

## インストール

```bash
claude plugin marketplace add japan-da-man/claude-code
claude plugin install self-improve@japan-da-man
```

まとめてインストール用の bundle（`japan-da-man-mods`）には入っていないので、上のように個別に入れます。bundle の依存に入れると、claude.ai と Cowork で bundle ごと読み込めなくなるおそれがあるためです（上の `bin/` の制約）。

ユーザースコープで入れてください。入れた時点から、すべてのgitリポジトリで動きます。

## どこで動くか

| 場所 | 動き |
| --- | --- |
| gitリポジトリの中（worktreeを含む） | 動く。`init` は要らない |
| gitリポジトリでない場所 | 何も記録せず、何も止めない |
| `~/.claude/self-improve/config.json` の `exclude` に書いた場所と、その下のリポジトリ | 何も記録せず、何も止めない（ガードも効かない） |
| ホームディレクトリそのもの（ホームをgitで管理している場合）、`node_modules` の中 | 組み込みで除外してある |

止めたい場所は、`exclude` に書きます。書くのは、絶対パスか `~/` で始まるパスです。そのパスと、その下にあるリポジトリが、すべて外れます。

```json
{
  "exclude": ["~/work/client-x", "~/src/someone-elses-repo"]
}
```

- 判定は、実体のパスで行います（リンク経由で開いても、同じ結果になります）。worktreeは、本体のリポジトリが除外されていれば、外れます。
- **セッションを始めたリポジトリで決めます。** 除外したリポジトリで始めたセッションは、途中で別のリポジトリへ `cd` しても、最後まで止まったままです。除外していないリポジトリで始めたセッションは、途中で除外した場所へ移っても、もとのリポジトリのセッションとして動き続けます。
- 書き間違い（相対パス、文字列でない値、配列でない `exclude`）は、設定が読めないものとして扱います（下の「設定が読めないとき」）。書いたパスが見つからないときは、セッション開始時に知らせます（除外そのものは効かせます）。
- その場だけ止めるなら、`HARNESS_DISABLE=1 claude` で起動します。

## 使い方

### 1. `init` する（任意。1人につき1回）

```text
/self-improve:init
```

`init` をしなくても動きます。`init` は、設定を手元に置いて変えられるようにし、`harness-note` を確認なしで呼べるようにするためのものです。

| すること | 中身 |
| --- | --- |
| `~/.claude/self-improve/config.json` を作る | user の設定（全リポジトリに効く）。すでにあれば触らない |
| `~/.claude/self-improve/incidents/` を作る | 失敗票の置き場所（全リポジトリの分） |
| `~/.claude/settings.json` に許可ルールを足す | `Bash(harness-note *)`。これがないと、改善候補を記録するたびに確認が出る。書き込みには確認が出る |
| 検証コマンドを使うか尋ねる | **使うと答えたときだけ**、いまのリポジトリに `harness/config.json`（中身は `verify` だけ）を作る |
| 止めたい場所を尋ねる | あれば `exclude` に足す |

リポジトリには、ほかに何も作りません。1.x の名残（`harness/incidents/` の失敗票など）があれば、移し方を案内します。

### 2. 普段どおり作業する

何もしなくても、次のことが自動で起きます。

| いつ | 何が起きるか | 作業を止めるか |
| --- | --- | --- |
| セッション開始時 | 試用ルールと、自分専用のルールを読み込む。自動改善の結果や、未確認の件数を知らせる（確認するか、閉じるまで）。1日1回、古い記録を掃除する | 止めない |
| ツールが失敗したとき、訂正したとき | 信号を記録する | 止めない |
| 禁止操作をしようとしたとき | 拒否する | 止める |
| ハーネスのファイルや `.env` を書き換えようとしたとき | 確認を出す | 確認を待つ |
| ターン終了時（変更があったとき） | リポジトリの `harness/config.json` の `verify` を実行する。失敗したら直させる | 失敗時だけ続けさせる |
| ターン終了時（信号があったとき） | 事象メモを作る。Claudeに「書き残す気づきがあれば記録する」よう頼む（エラーではなく、hookからの案内として表示されます）。あれば、改善候補を1行で記録する | 1ターンに1回だけ続けさせる |

信号は、ツールの失敗、人の訂正、ガードの拒否、検証の失敗の4つです。**信号のないターンでは、ターン終了時の確認はしません**（すべてのリポジトリで動くので、トークンと待ち時間を抑えるためです）。信号がなくても気づきを残したいときは、Claudeに「いまの気づきを改善候補に記録して」と頼みます。

記録されるものは2種類です。どちらもリポジトリの外（プラグインのデータ領域）に置かれます。

- **事象メモ**：スクリプトが機械的に作る証拠です。依頼文、起きたこと、Claudeの最後の応答が入ります。90日で消えます。
- **改善候補**：Claudeが書く1行の気づきです。カテゴリと原因キー（`cause_key`）が付きます。1つのセッションが記録できるのは、24時間に3件までです。

改善候補のカテゴリは次の5つです（user の設定で変えられます）。

| カテゴリ | 中身 | 数え方 | 自動改善の扱い |
| --- | --- | --- | --- |
| `dev/bug` | 作業中に気づいた実装のバグ | リポジトリごと | 対象外。報告に一覧が載る |
| `dev/cause` | バグが起きた原因 | リポジトリごと | 対象 |
| `dev/mistake` | よくある開発時のミス | リポジトリごと | 対象 |
| `dev/other` | 上に当たらない気づき | リポジトリごと | 対象外。報告に件数が載る |
| `behavior/preference` | 好み、選びがちな選択肢 | **user 単位（全リポジトリで数える）** | 対象外。3セッション以上で重なったら、セッション開始時に1行で知らせ、確認のうえ `~/.claude/CLAUDE.md` へ |

候補を見たいときは、Claudeに「改善候補を見せて」と頼みます。`harness-note` コマンドは、Claudeの中からしか呼べません。

- 件数は、同じ原因キーを記録した**異なるセッションの数**で数えます。1つのセッションで何度書いても1件です。数えるのは、このプラグインのhookが見たセッションだけです（`--session` に実在しないIDを書いても、件数は増えません）。
- 同じキーの記録が10分以内に続いたときは、二重には記録しません（同じセッションからの記録と、別のセッションからの同じ文面の記録）。
- 似た原因キーが既にあるときは、記録のときに警告が出ます。まとめ直すときは、Claudeに頼むか `/self-improve:review` を使います。
- 訂正として拾う言い回し（「違う」「戻して」など）は、user の設定の `correction_words` で足せます。「何が違う？」のような質問の文は、訂正に数えません。
- 好みの候補は、あなたに付くものなので、リポジトリをまたいで数えます。知らせも、リポジトリごとではなく、1つにまとめます（どこかで1回閉じれば、ほかのリポジトリでも出ません）。

### 3. 候補がたまったら、自動改善を有効にする

**自動改善はリポジトリごとに動き、既定では止めてあります。** 同じ原因キーの候補が、異なるセッションで2件以上たまると、セッション開始時に知らせます。

```text
自動改善の対象になる原因ができました（route-placement）。有効にしますか。
```

この知らせは、`/self-improve:review` を開くか、Claudeに「self-improve の知らせを閉じて」と頼むまで、セッションを始めるたびに出ます（閉じなくても、7日で出なくなります）。

有効にするには、`auto.interval_days` を7にし、[SCHEDULING.md](./SCHEDULING.md) の手順でスケジュール済みタスクを設定します。1つのリポジトリだけ有効にするなら `~/.claude/self-improve/repos/<名前>/config.json` に、すべてのリポジトリで有効にするなら `~/.claude/self-improve/config.json` に書きます（スケジュール済みタスクは、リポジトリごとに要ります）。まず `/self-improve:auto-improve` を手動で1回呼んで、中身を確かめるのがおすすめです。

タスクを設定しない場合や、実行を逃した場合は、間隔（`auto.interval_days`）を過ぎた時点でセッション開始時に知らせます。その場で `/self-improve:auto-improve` を呼べます。二重に実行されないよう、前回の実行から間隔の半分（7日なら3.5日）がたつまでは、呼んでも何もせずに終わります。遅れて手動で実行しても、次の定時の実行は飛びません。

### 4. 報告が出たら確認する

自動改善が動くと、次のセッション開始時に報告が出ます。

```text
自動改善（11/16）：試用ルールを2件追加、1件を編集。承認待ちの案が1件。
```

この報告は、`/self-improve:review` を開くか、Claudeに「self-improve の知らせを閉じて」と頼むまで、セッションを始めるたびに出ます（閉じなくても、7日で出なくなります）。人が読んだかどうかを、hookの側からは知れないためです。

閉じたあとも、確認が済むまでは、次の1行が出ます。

```text
未確認の自動変更3件。いちばん古いものは12日前。
```

試用ルールは、誰が入れたものでも、人が `/self-improve:review` で確認するまで、この件数に数えます（`/self-improve:retro` で人が入れたものも含みます。その場で承認していれば、`retro` が確認済みにします）。どのセッションが入れたかという申告には頼りません。

自動改善が追加をやめているときは、その理由も1行で出ます。

```text
自動改善は、いま試用を追加していません：未確認の自動変更が上限（5件）に達している。
```

行数の目安に掛かっていて、試用Skillなら入るときは、「試用ルールを追加していません（試用 Skill は追加できます）」と出ます。

中身を確かめるときは `review` を呼びます。

```text
/self-improve:review
```

未確認の自動変更を1件ずつ見せるので、次のどれかを選びます。

| 選ぶもの | 起きること |
| --- | --- |
| 残す | 試用のまま続ける。下書きから失敗票を起票する（`~/.claude/self-improve/incidents/`） |
| 直す | その場で文言を直す |
| 消す | 試用を消す。その原因は、新しい候補がたまるまで自動改善の対象から外れる |
| 昇格する | **自分専用**か、**チーム**かを選ぶ（下の「昇格」） |

承認待ちの案（ガード、検証コマンド、git管理下のファイルの編集）は、差分を見て承認すると反映されます。自動改善が「環境が原因」「再現しない」と判断して対策を入れなかったものも、記録として残すか捨てるかを選びます。バグの候補は、「Issueにする／今直す／捨てる」を選びます。

未確認が5件たまると、自動改善は新しい追加をやめて、報告だけにします。

## 昇格（自分専用か、チームか）

試用を定着させるときは、行き先を選びます。

| 行き先 | 置き場所 | ほかの人への影響 | コミット |
| --- | --- | --- | --- |
| 自分専用 | ルールは `~/.claude/self-improve/repos/<名前>/rules.md`。Skillは、いまの場所（`~/.claude/skills/<リポジトリ名>-<名前>/`）のまま、試用でなくなる | ない | 要らない |
| チーム | リポジトリの `.claude/rules/`、`.claude/skills/` | チームの全員に効く | する |

- **自分専用のルール**は、そのリポジトリのセッション開始時に、試用ルールと同じように読み込まれます。ほかのリポジトリでは読み込まれません。ファイルは、`- ` で始まる行が1行で1つのルールです。手で直せます（書き込みには確認が出ます）。
- **自分専用に昇格したSkill**は、置き場所も中身も変わりません。試用のあいだは `harness-note` 以外から書けませんが、昇格したあとは、ふつうのファイルとして直せます。
- **チームへ出すものには、失敗票IDを付けません。** 失敗票は、あなたの手元にしかないためです。移した先のファイルにIDが残っていると、昇格のコマンドが断ります。
- チームへの昇格は、移した先のファイルがあること（空でないこと）を確かめてから、試用を消します。移し忘れたまま試用だけが消えることは、ありません。
- 見直しの時期（初期値60日）が来た試用も、確認済みの試用も、同じように昇格できます。

昇格は `/self-improve:review` の中で行います。使われるコマンドは `harness-note promote --key <原因キー> --to personal|team` です。

## 失敗票

失敗票は、全リポジトリの分を `~/.claude/self-improve/incidents/` に置きます（1件1ファイル。`INC-YYYY-NNNN.md`）。リポジトリには置きません。共有リポジトリに、個人の失敗の記録を混ぜないためです。

- 起票は `harness-note incident add` で行います（`/self-improve:retro` と `/self-improve:review` が呼びます）。**人だけの操作**で、自動改善のセッションからは起票できません（自動改善が作るのは、下書きまでです）。
- IDは、全リポジトリで1つの連番です（年ごと）。すでにあるファイルは、上書きしません。
- どのリポジトリで起きたか（`repo`、`repo_id`）と、リモートのURL（`remote`）を記録します。URLからは、認証情報（利用者名、パスワード、トークン、クエリ）を取り除きます。ローカルのパスのリモートは、記録しません。
- 下書きから起票するとき（`--from-draft`）は、下書きに入っている値（`status`、`control`、原因の分類、試用を始めた日）を引き継ぎます。
- 関連する票（`related`）と、整合のチェックは、**今のリポジトリの票だけ**を見ます。一覧も、今のリポジトリの分だけを出します（全部を見るときは、Claudeに「全リポジトリの失敗票を見せて」と頼みます。`harness-note incident list --all`）。

## 自動改善がやること、やらないこと

| 対策 | 自動の扱い |
| --- | --- |
| 文章ルールの追加 | 試用として置く |
| 試用ルールの編集 | 同じ原因がまた出たとき、1回目だけ。2回目からは、ガードなどへ移す案を報告する |
| Skillの追加 | 試用として置く。中身は名前、説明文、本文の文章だけ |
| 昇格済みのルール、CLAUDE.mdの編集 | 差分の案を報告に載せる |
| ガード、検証コマンドの追加 | 案とテストケースを報告に載せる |
| 失敗票の起票、昇格 | しない（人だけの操作）。作るのは下書きまで |
| コミット、プッシュ | しない |

自動改善は、リポジトリの中のファイルも、user 側の設定・ガード・失敗票も書き換えません。書き込むのは次の場所だけです。

| 作るもの | 置き場所 |
| --- | --- |
| 試用ルール | プラグインのデータ領域。セッション開始時に読み込まれる |
| 試用Skill | `~/.claude/skills/<リポジトリ名>-<名前>/` |
| 失敗票の下書き、実行の記録 | プラグインのデータ領域 |

次のときは、追加せず報告だけします。

- 未確認の自動変更が5件に達しているとき
- 試用ルールが10件、試用Skillが5件に達しているとき
- self-improve が読み込ませるルール（試用ルールと自分専用のルールの合計）が、行数の目安（`budget.always_loaded_rule_lines`）を超えるとき
- 事象メモと候補の内容が食い違うとき
- 既存のルールと矛盾しそうなとき
- ルールやSkillの中身が検査を通らないとき（指示の上書き、ガードの回避、外部への送信を促す文、URL、見えない文字、HTMLのコメント、読み込み時に実行される書き方。Skillの本文は、`@` に続く語も。コードの一部なら、バッククォートで囲めば書けます）

**行数の目安で数えるのは、self-improve が足した分だけです。** リポジトリのCLAUDE.mdや `.claude/rules/`（チームのルール）が長くても、自動改善は止まりません。前の実行の下書きが残っている原因でも、その実行で下書きを作り直してからでなければ、試用の追加・編集はできません。

追加できない原因は、自動改善の開始時に「いまは追加できません」と示され、下書きも作りません（候補は残り、次の回にまた対象になります）。

1回の実行で扱うのは、件数の多い順に3件までです。対象はスクリプトが選び、それ以外の原因には書き込めません。前回の実行から間隔（`auto.interval_days`）がたっていないときは、何もせずに終わります。

自動改善のセッションで使えるツールは、Read、Grep、Globと、Bashの `harness-note` だけです。それ以外（Write、Edit、ほかのBash、MCPのツール、サブエージェントの起動、Webの取得、ほかのスキルの呼び出しなど）は、ガードが拒否します。確認は出ません。検証、事象メモ、改善候補の確認も動きません。Skillは、読み直しのための `self-improve:auto-improve` だけ通します。

- `harness-note` は、そのセッションの本物のID（hookに渡る `session_id`）と一致する `--session` が付いた、単純な呼び出しだけを通します。変数の展開、`$(…)`、パイプ、ファイルへのリダイレクト、環境変数の前置き、引用の外の `{ } * ? [ ] ~`（bashが語を作り替える文字）、`command` や `env` や `node …/scripts/note.mjs` で包んだ呼び出しは拒否します。
- ほかのセッションを名乗る書き込みは、3か所で止めています。ガードが `--session` をhookの `session_id` と照らします。`harness-note` が、引き渡された環境変数のIDと食い違う `--session` を断ります。自動改善の実行中は、ロックしたセッション以外からの人だけの操作（失敗票の起票と更新、昇格、試用の追加・編集・削除、候補の採否、下書きの破棄、確認の結果の記録、知らせを閉じる）を、すべて見送ります。どれも、hookが動いていることか、`harness-note` を通ることが前提で、言い切れる保証ではありません。
- 読み取りに自信の持てないコマンド（区切りが単純でないヒアドキュメント、`$'…'` など）は、拒否の側に倒します。
- 自動改善を呼び出したセッションは、終わったあと（ロックが外れたあと、始まらなかったあと）も、書き込みに確認が挟まり、`harness-note` の人だけの操作は見送りになります（2週間）。同じセッションが「人」として試用を足したり、自分の変更を確認済みにしたりできないようにするためです。続きの作業と確認は、新しいセッションで行ってください。
- 自動改善の実行中（数分。途中で落ちたときは、最長2時間）は、人のセッションからの試用の追加や確認も見送りになります。終わってから、やり直してください。

これは、うっかりや近道を防ぐための仕組みで、サンドボックスではありません。hookが動かない環境（プラグインが無効、`HARNESS_DISABLE=1`、除外した場所）では効きません。スケジュール済みタスクの権限は、[SCHEDULING.md](./SCHEDULING.md) のとおりに絞ってください。

## 自分で振り返りたいとき

失敗した直後や、特定の原因を先に片づけたいときは、自分で呼べます。

```text
/self-improve:retro
/self-improve:retro route-placement
```

1. 同じ原因（`cause_key`）が既にないかを尋ねます。
2. 原因を分類して、失敗票を起票します（`~/.claude/self-improve/incidents/`）。事象メモに詳しい経緯が残っていれば、内容がそれと合っているかを確かめてください。
3. 変換を1つ提案します。文章ルールは試用から始まります。ガード、検証コマンド、Skillは、同じ原因が2回出てから提案します（禁止操作と重大なものは1回目から）。ガードとSkillは、自分専用か、チームかを選びます。
4. 差分を見せます。リポジトリのファイルを変えたとき（チームのガード、検証コマンドなど）だけ、1変換につき1コミットで反映します。

失敗を再現するためにエージェントを走らせ直すことはしません。

## ガード

禁止操作の定義は、4か所から読み、**すべて効かせます**（あとのファイルが、前のファイルを上書きすることはありません）。

| 置き場所 | 効く範囲 | 記録に残る名前 |
| --- | --- | --- |
| 共通リスト（プラグインに同梱の `guards.default.json`） | すべてのリポジトリ | `default` |
| `~/.claude/self-improve/guards.json` | すべてのリポジトリ（自分だけ） | `user` |
| `~/.claude/self-improve/repos/<名前>/guards.json` | そのリポジトリ（自分だけ） | `user-repo` |
| リポジトリの `harness/guards.json` | そのリポジトリ（self-improve を入れているチームの全員） | `repo` |

拒否と確認の記録には、どのファイルのルールだったかを残します（プラグインに組み込みの判定は `builtin`）。`<名前>` を含む実際のパスと、いま読まれているファイルは、Claudeに `harness-note status` を実行してもらうと分かります。

**共通リスト**は次のとおりです。`git push --force`（`--force-with-lease` は通します）、フックを飛ばす `git commit --no-verify`（`-n` と、`-nm`・`-nS` のように `n` を含む短いオプションのまとまりも）、ルートやホームを丸ごと消す `rm -r`（引数のどれかがルートかホームなら当たります）は拒否します。`.env` と `.env.<環境名>`（`.env.local`、`.env.production`、`.env.qa` など。環境名は問いません）への書き込みは、拒否ではなく確認を出します（`.env.example`・`.env.sample`・`.env.template`・`.env.md`・`.env.bak` などは、確認なしで通します）。

自分のガードは、`/self-improve:retro` で、失敗票から足します。書き方は3か所とも同じです。

```json
{
  "disable_defaults": [],
  "protect": [],
  "rules": [
    { "id": "no-generated-edit", "path": "^src/generated/", "message": "src/generated/ は手で編集しません。スキーマを直して生成し直してください" }
  ]
}
```

| 項目 | 意味 |
| --- | --- |
| `rules[].path` | 書き込み先のパス（リポジトリの根からの相対パス）に当てる正規表現。`except` で例外を書ける |
| `rules[].pattern` | Bashのコマンドに当てる正規表現 |
| `rules[].decision` | `deny`（拒否。省略時）か `ask`（確認を出す） |
| `rules[].message` | 拒否したときにClaudeへ返す文。**直し方を1行**書く。チームのファイル（`harness/guards.json`）には、失敗票IDを書かない |
| `disable_defaults` | 共通リストのルールを外すときに `id` を書く（`git-force-push`、`git-no-verify`、`env-file-write`、`rm-root-or-home`）。**書けるのは user 側の2つのファイルだけ**。リポジトリの `harness/guards.json` に書いても、外れません（プルした変更で、禁止リストが外れないようにするためです。書いてあれば、セッション開始時に知らせます） |
| `protect` | 書き込みに確認を挟むパスを足す（正規表現） |

ガードを1つ足すときは、同じ場所の `guards.test.json` に「止めるべき入力」と「止めてはいけない入力」を1件ずつ足します。テストは、エージェントも実際のコマンドも動かさずに実行できます（Claudeに「ガードのテストを実行して」と頼みます）。共通リストのテストに加えて、いまのリポジトリで効く3か所のテストケースを、すべて実行します。

```json
[
  { "name": "生成物の手編集を止める", "tool": "Edit", "input": { "file_path": "src/generated/api.ts" }, "expect": "deny" },
  { "name": "生成物以外は通す", "tool": "Edit", "input": { "file_path": "src/api.ts" }, "expect": "allow" }
]
```

**確認が出る書き込み**は、次のとおりです（パスの大文字小文字は区別しません。`~`・`$HOME`・`${HOME}` で書いても、リンクを通しても、同じ判定になります）。

- user 側：`~/.claude/self-improve/` の下のすべて（設定、ガード、失敗票、自分専用のルール）と、`~/.claude/CLAUDE.md`
- リポジトリ側：`harness/config.json`、`harness/guards.json`、`harness/guards.test.json`、`.claude/rules/`、`.claude/skills/`、CLAUDE.md、リンター設定（`eslint.config.*`、`biome.json`、`ruff.toml` など）

書き込み先は、リンクの名前と実体の両方で判定します（`CLAUDE.md` が `AGENTS.md` へのリンクなら、`AGENTS.md` への書き込みにも確認が出ます）。プラグイン自身のファイル、プラグインのデータ領域、試用Skillへの直接の書き込みは、拒否します。

ガードの定義のファイルがJSONとして読めないときは、そのファイルのガードだけが効かなくなります（ほかの3か所は効きます）。セッション開始時と、整合のチェックで、直すまで知らせます。

Bashのコマンドは、粗く読み取って判定します。二重引用の中の `"$(…)"` も読み取るので、Claude Code標準のHEREDOC形式のコミット（`git commit -m "$(cat <<'EOF' … EOF)"`）のあとに別のコマンドが続いても、誤って拒否しません。読み取りに自信の持てない書き方の中に `harness-note` の呼び出しがあるときと、`harness-note` をほかのコマンドで包んだとき（`command harness-note …`、`env … harness-note …`、`node …/scripts/note.mjs …` など）は、通常のセッションでも拒否します（引数の `--session` を確かめられないためです）。この拒否は、失敗の信号には数えません。それ以外のコマンドは、通常のセッションでは止めません（読み取りに自信が持てないときだけ、禁止リストを、コマンドの全文にも当てます）。

## 設定

設定は、次の順に重ねます（あとのものが、前のものを上書きします）。

1. 初期値（プラグインに組み込み）
2. user の設定：`~/.claude/self-improve/config.json`（全リポジトリに効く）
3. リポジトリごとの上書き：`~/.claude/self-improve/repos/<名前>/config.json`（変えたい項目だけを書く）

**リポジトリの `harness/config.json` から読むのは、検証コマンドの `verify` だけです。** ほかの項目を書いても、読みません（セッション開始時に、user 側へ移すよう知らせます）。リポジトリのファイルは、共有されたり、プルで変わったりするので、仕組みの動き方（自動改善の間隔や上限）は決めさせません。

`~/.claude/self-improve/config.json`：

```json
{
  "exclude": [],
  "trial_review_days": 60,
  "episode_retention_days": 90,
  "budget": {
    "always_loaded_rule_lines": 50
  },
  "candidates": {
    "min_sessions": 2,
    "preference_min_sessions": 3,
    "max_per_session": 3,
    "categories": ["dev/bug", "dev/cause", "dev/mistake", "dev/other", "behavior/preference"]
  },
  "auto": {
    "interval_days": 0,
    "max_per_run": 3,
    "max_unreviewed": 5,
    "max_trial_rules": 10,
    "max_trial_skills": 5
  },
  "prune": {
    "interval_days": 30
  }
}
```

| 項目 | 意味 |
| --- | --- |
| `exclude` | self-improve を止める場所（上の「どこで動くか」）。書けるのは user の設定だけ |
| `trial_review_days` | 試用を「見直し」として報告に載せるまでの日数 |
| `episode_retention_days` | 事象メモ、改善候補、生ログを残す日数 |
| `budget.always_loaded_rule_lines` | self-improve がセッション開始時に読み込ませる行数（試用ルール＋自分専用のルール）の目安。超えると警告し、自動改善は試用ルールの追加をやめる |
| `candidates.min_sessions` | 自動改善の対象にするまでの件数（異なるセッションの数） |
| `candidates.preference_min_sessions` | 好みの候補を知らせるまでの件数（全リポジトリの、異なるセッションの数） |
| `candidates.max_per_session` | 1つのセッションが、24時間に記録できる候補の上限 |
| `auto.interval_days` | 自動改善の間隔。0は停止。有効にするときに7にする。前回の実行からこの半分がたつまでは実行せず、この日数を過ぎても実行されていなければ知らせる |
| `auto.max_per_run` | 自動改善が1回の実行で扱う候補の上限 |
| `auto.max_unreviewed` | 未確認の自動変更がこの件数に達したら、追加と編集をやめる |
| `auto.max_trial_rules`、`auto.max_trial_skills` | 試用ルールと試用Skillの上限 |
| `prune.interval_days` | 棚卸しの間隔（未実装。いまは使われません） |

`<名前>` は、リポジトリのディレクトリ名をもとにした名前です。同じ名前のリポジトリが2つあって分けたいときは、`repos/<リポジトリID>/` を作れば、そちらが優先されます（IDは `harness-note status` に出ます）。

実行する日時は、スケジュール済みタスクの側で決めます。設定に書くのは間隔だけです。

### 検証コマンド（リポジトリの `harness/config.json`）

```json
{
  "verify": [
    { "name": "typecheck", "run": "<型チェックのコマンド>" }
  ]
}
```

`verify` は、「壊れたまま完了と報告した」失敗が起きたときに足します。コマンドはリポジトリの根で上から順に実行し、最初の失敗で止めます（1つにつき240秒まで。`timeout_sec` で変えられます）。そのターンでファイルの変更があったときだけ走ります。時間切れのときは、コマンドが起動した子孫のプロセス（テストランナーなど）も、まとめて止めます。ターン終了時のhook全体の制限時間は900秒なので、時間のかかるコマンドを4つ以上並べると、途中で打ち切られることがあります。

### 設定が読めないとき

`~/.claude/self-improve/config.json` がJSONとして読めない、`exclude` が配列でない、`exclude` に解釈できない値がある、のどれかのときは、**ガードは効かせたまま、記録と掃除を止めます**（生ログ、ガードの拒否の記録、事象メモ、改善候補、ターン終了時の確認、検証）。除外したつもりの場所に記録を残さないためです。セッション開始時に、直すまで毎回知らせます。試用ルールと自分専用のルールの読み込みは続けます。

## 掃除

保持期間（`episode_retention_days`）を過ぎた事象メモ、生ログ、状態が `new` のままの改善候補は、セッション開始時に消します。**1日1回**、データ領域にある**全リポジトリの分**をまとめて行います（しばらく開いていないリポジトリの記録も、保持期間で消えます）。保持期間は、リポジトリごとの上書きがあれば、それに従います。

## 棚卸し（任意）

**未実装（ステップ4）です。** `/self-improve:harness-prune` は、まだありません。`prune.interval_days` も、いまは何にも使われません。

入れる予定の中身は次のとおりです。使われていないSkill、発火していないガード、読み込まれていないルール、60日を超えた試用を一覧にし、残すか消すかを1件ずつ人が選びます。自動では消しません。間隔（`prune.interval_days`）を過ぎると、セッション開始時に知らせます。

いまできること：60日を超えた試用は、セッション開始時の通知と `/self-improve:review` に出ます。行数の目安を超えたときは、セッション開始時に警告が出ます。

## データの置き場所

| データ | 場所 | 誰が書くか |
| --- | --- | --- |
| user の設定、リポジトリごとの上書き | `~/.claude/self-improve/config.json`、`~/.claude/self-improve/repos/<名前>/config.json` | `init`（最初の1回）と、人の確認を通したClaude |
| 失敗票（全リポジトリの分） | `~/.claude/self-improve/incidents/` | `harness-note incident add`（人だけの操作） |
| 自分専用のルール | `~/.claude/self-improve/repos/<名前>/rules.md` | `harness-note promote`。手でも直せる |
| 自分のガードとテストケース | `~/.claude/self-improve/guards.json`、`~/.claude/self-improve/repos/<名前>/guards.json`（`guards.test.json` も同じ場所） | 人の確認を通したClaude |
| `harness-note` の許可ルール | `~/.claude/settings.json` | 人の確認を通したClaude（`init`） |
| 検証コマンド、チームのガード | リポジトリの `harness/config.json`、`harness/guards.json` | 人の確認を通したClaude。gitで管理する |
| チームへ昇格したルール、Skill | リポジトリの `.claude/rules/`、`.claude/skills/` | 人の確認を通したClaude。gitで管理する |
| 試用Skill、自分専用に昇格したSkill | `~/.claude/skills/<リポジトリ名>-<名前>/` | `harness-note`（昇格したあとは、手でも直せる） |
| 試用ルール、失敗票の下書き、自動改善の記録、生ログ、事象メモ、改善候補、仕組みの状態（未確認の自動変更、ロックなど） | プラグインのデータ領域（`~/.claude/plugins/data/` の下） | `harness-note` とhook |

`harness-note` が自分で書くのは、プラグインのデータ領域、失敗票、自分専用のルール、試用Skillです。設定とガードの定義は、`harness-note` は書きません（`init` が最初に作る user の設定だけが例外です）。Claudeが、WriteやEditで、人の確認を通して書きます。

## 1.x からの移行

1.x は、リポジトリごとに `/self-improve:init` をして、`harness/` に設定と失敗票を置く作りでした。2.x では、次のように変わります。リポジトリで `/self-improve:init` を呼ぶと、名残を見つけて、移すかどうかを尋ねます。手で行うときは、次のとおりです。

| 1.x のもの | 2.x での扱い | すること |
| --- | --- | --- |
| `harness/incidents/` の失敗票 | 読まれない。失敗票は `~/.claude/self-improve/incidents/` に置く | そのリポジトリで、Claudeに「1.x の失敗票を取り込んで」と頼む（`harness-note incident import`）。内容を確かめてから、`harness/incidents/` をリポジトリから消す |
| `harness/config.json` の `verify` | そのまま読まれる | 何もしない |
| `harness/config.json` の、`verify` 以外の項目 | 読まれない（セッション開始時に知らせる） | 全リポジトリで同じでよい値は `~/.claude/self-improve/config.json` へ、そのリポジトリだけの値は `~/.claude/self-improve/repos/<名前>/config.json` へ移す。`harness/config.json` からは消す（`verify` も空なら、ファイルごと消してよい） |
| `budget.claude_md_lines`、`budget.scoped_rule_file_lines` | なくなった（数えるのは、self-improve が足した分だけ） | 移さずに消す |
| `harness/guards.json`、`harness/guards.test.json` | そのまま効く（チームのガード）。ただし、`disable_defaults` は読まれない | `disable_defaults` を使っていたら、`~/.claude/self-improve/repos/<名前>/guards.json` へ移す。自分だけのガードにしたいルールも、同じファイルへ移せる |
| `.claude/settings.local.json` の許可ルール（`Bash(harness-note *)`） | 害はないが、リポジトリごとに要る | `~/.claude/settings.json` に足せば（`init` が行う）、どのリポジトリでも効く。リポジトリごとのものは消してよい |
| `.gitignore` の `harness/reports/` | 使われていない（棚卸しは未実装） | そのままでよい |
| 試用ルール、試用Skill、改善候補、事象メモ、未確認の自動変更 | そのまま引き継がれる（置き場所は変わらない） | 何もしない |
| すでに記録済みの好みの候補（`behavior/preference`） | user 単位の場所へ移され、全リポジトリで数えられる（2.x での最初の掃除のとき） | 何もしない |
| `harness-note review done --decision promote` | なくなった | `harness-note promote --key <原因キー> --to personal\|team` を使う（`/self-improve:review` が呼ぶ） |
| `init` していないリポジトリ | **動くようになる**（ガードも、記録も） | 止めたい場所は、`exclude` に書く |

失敗票の取り込みについて：

- 番号は、空いていればそのまま使います。ほかのリポジトリの票と重なるときは、その年の次の番号に振り直し、もとのIDを `imported_from` に残します。振り直した票を指していた試用ルールは、新しいIDに付け替えます。
- リポジトリのファイル（`.claude/rules/` のルールや、ガードの `message`）に古いIDを書いていて、番号が振り直されたときは、手で直すか、IDを消してください（チームのファイルには、IDを書かないのが2.xの決まりです）。
- 何度実行しても、同じ票が二重に取り込まれることはありません。もとのファイルは、消しません。

2.x に上げた直後のセッション開始時に、次のような知らせが出ることがあります。どれも、上の表のとおりに移せば消えます。

```text
設定の注意：harness/config.json の auto、trial_review_days は読みません（読むのは verify だけです）。~/.claude/self-improve/repos/<名前>/config.json に移してください。
```

## 困ったとき

| 状況 | 対応 |
| --- | --- |
| ハーネスが作業の邪魔をする | その場だけなら `HARNESS_DISABLE=1 claude` で起動する。プラグインのhookがすべて止まる（ターン終了時の確認も止まる）。そのリポジトリでずっと止めるなら、`exclude` に書く |
| 関係のないリポジトリで動いてほしくない | `~/.claude/self-improve/config.json` の `exclude` に書く（`/self-improve:init` でも足せる） |
| 自動で入った試用が的外れ | `/self-improve:review` で「消す」を選ぶ |
| 消したのに同じ内容が効き続ける | Claude Codeの自動メモリに同じ内容が残っていることがある。`/memory` で確かめる |
| 自動改善をやめたい | `auto.interval_days` を0にし、スケジュール済みタスクを削除する |
| 自動改善が動いていない | セッション開始時に「間隔（7日）を過ぎても実行されていません」と出る。`/self-improve:auto-improve` を手動で呼ぶ |
| 自動改善が試用を追加しない | セッション開始時に「自動改善は、いま試用を追加していません：…」と理由が出る。`/self-improve:review` で確認・昇格するか、ルールを減らす |
| セッション開始時の知らせを消したい | `/self-improve:review` を開くか、Claudeに「self-improve の知らせを閉じて」と頼む（`harness-note report close`）。閉じなくても7日で出なくなる |
| 「…：JSON として読めません…直すまで、記録と掃除を止めています」と出る | `~/.claude/self-improve/config.json` の書き間違いを直す。直すまで、ガードだけが効く |
| 「ルールが長く、N件を読み込みきれませんでした」と出る | セッション開始時に渡せる量には上限がある。`/self-improve:review` で、チームへ昇格するか、減らす |
| 自動改善を呼んだセッションで、書き込みのたびに確認が出る。`harness-note` が「見送り」と返す | 仕様。自動改善を呼び出したセッションは、終わったあとも確認を挟み、試用の追加や確認の記録を受け付けない。続きは新しいセッションで行う |
| 「見送り：自動改善が実行中です」と出る | 自動改善が終わる（ロックが外れる）のを待って、やり直す。途中で落ちた実行のロックは、2時間で失効する |
| `.env` を書くたびに確認が出る | `~/.claude/self-improve/guards.json`（そのリポジトリだけなら `repos/<名前>/guards.json`）の `disable_defaults` に `env-file-write` を書く |
| 試用Skillが別のリポジトリで呼ばれる | `/self-improve:review` で消すか、説明文を直す |
| 検証の失敗が繰り返される | 3回続くと自動で打ち切り、知らせる（コードは検証が通っていない状態のまま）。`verify` のコマンドを見直す |
| チームへ昇格したルールやガードを取り消したい | そのコミットを `git revert` する |
| 自分専用のルールを取り消したい | `~/.claude/self-improve/repos/<名前>/rules.md` から、その行を消す |
| 「記録が止まっている」と出る | hookが7日以上動いていない。`/plugin` でプラグインが有効か確かめる |
| `harness-note` が見つからない、候補が記録されない | Claudeに `harness-note status` を実行してもらう。データの置き場所とセッションID、読まれている設定とガードのファイルが出る。`command not found` なら `/reload-plugins` か起動し直し |
| `harness-note` が「ここでは使えません」と返す | gitリポジトリでない場所か、除外した場所。理由が一緒に出る |
| ガードが必要な操作まで止める | `harness-note status` で、どのファイルのルールかを確かめる。共通リストのルールなら、user 側の `guards.json` の `disable_defaults` に `id` を書く |

## 既知の制約

- **リポジトリ側のファイルへの確認が、すべてのgitリポジトリで出ます。** `.claude/rules/`、`.claude/skills/`、CLAUDE.md、リンター設定、`harness/` の設定を書き換えるときです。1.x では `init` したリポジトリだけでした。邪魔なリポジトリは、`exclude` に書いてください。
- **`verify` は、リポジトリの `harness/config.json` に書かれたコマンドを、確認なしで実行します。** `init` していなくても、そのファイルがあるリポジトリでは実行されます。このファイルの変更は、プルした変更も含めて、中身を見てから取り込んでください（取り込んだコマンドは、次に変更のあったターンの終わりに実行されます）。信用できないリポジトリは、`exclude` に書いてください。Claudeがこのファイルを書き換えるときは確認が出ます。
- **リポジトリごとの置き場所は、ディレクトリ名で決まります**（`~/.claude/self-improve/repos/<名前>/`）。同じ名前のリポジトリが2つあると、設定の上書き・自分のガード・自分専用のルールを共有します。分けたいときは、`repos/<リポジトリID>/` を作ってください（そちらが優先されます）。リポジトリのディレクトリ名を変えたときは、`repos/` の下の名前も変えてください。
- **失敗票は、マシンごとに別です。** `~/.claude/self-improve/` を dotfiles などで同期していれば共有できますが、IDの連番が2台でぶつかることがあります（上書きはせず、次の番号を振ります）。試用、候補、生ログも、マシンごとに別です。当面は1台での利用を前提にしています。
- **好みの候補の記録には、どのリポジトリで出たかが残ります**（リポジトリの名前とID）。
- **ルールやSkillの中身の検査は、言い回しの照合です。** すり抜けも誤検知もあります。禁じる側のルール（「〜しない」「〜するな」）を通すための例外が広く、否定の形で書かれた誘導を通すことがあります。最後の関門は、人の確認（`/self-improve:review`）です。
- **ハーネスのファイルへの確認は、うっかりや近道を防ぐためのものです。** Bash経由の書き換えをすべて見分けることはできません。自動改善のセッションの制限も同じで、hookが動いていることが前提です。
- **検証コマンドのプロセスをまとめて止める処理は、プロセスグループ（macOSとLinux）と `taskkill`（Windows）に頼ります。** Windowsでは確かめていません。自分でセッションを作り直すコマンド（`setsid` など）の子孫は、止められません。
- 棚卸し（`harness-prune`）は未実装です。

## 注意

- 自動改善は、人が証拠を見る前に試用を効かせます。的外れなものが入る可能性があるので、報告が出たら早めに確認してください。
- 試用Skillは個人用の場所に置くので、どのリポジトリでも見えます。
- プラグインのデータ領域は、プラグインをアンインストールすると消えるとされています。試用ルールと改善候補も一緒に消えます。失敗票、設定、自分専用のルール（`~/.claude/self-improve/`）は、残ります。
- 検証には制限時間があります。コマンド1つにつき240秒（`timeout_sec` で変えられます）、ターン終了時のhook全体で900秒です。
- ガードは、すべてのgitリポジトリで、すべてのツール呼び出しのたびに動きます。することがないとき（gitリポジトリでない場所、除外した場所、通常のセッションのReadやGrepなど）は、`node` の起動（計測で約26ミリ秒）に10ミリ秒ほどを足した程度で抜けます。ファイルの書き込みとBashでは、あわせて約60ミリ秒かかります。
- 自動改善のセッションは、Read・Grep・Globで、読めるファイルを何でも読めます。読んだ内容を、`harness-note` で書く記録や下書きに写すこともできます。外へ出す手段（Webの取得、MCPのツール、ほかのコマンド）は拒否されるので、内容が残るのは手元のデータ領域までです。
- 事象メモには、依頼文と応答の全文が入ります。リポジトリの外に置き、信号のあったターンに限り、90日で消しますが、秘密の値を会話に貼らないのがいちばん確実です。記録を残せないリポジトリは、`exclude` に書いてください。
- 失敗票には、リモートのURLが入ります（認証情報は取り除きます）。`~/.claude/self-improve/` を人に見せたり、公開の場所で同期したりするときは、気をつけてください。

## 開発

```bash
cd plugins/self-improve && node --test        # テスト（hookには入力JSONを与えて、終了コードと出力を確かめる）
node scripts/test-guards.mjs                  # 共通の禁止リストと、いまのリポジトリで効くガードのテストケースを実行する
claude plugin validate ./plugins/self-improve # リポジトリの根で
```

テストは、ホーム、`~/.claude`、データ領域を、すべて一時ディレクトリに向けます（`HOME`、`HARNESS_CLAUDE_HOME`、`HARNESS_DATA_DIR`）。実際の `~/.claude` には書きません。現在時刻は、`HARNESS_TEST=1` のときだけ `HARNESS_NOW` で固定できます（テストは、実際の時計に頼りません）。実際のbashを起動するテストは、bash 3.2（macOS）でも通る書き方にし、新しいbashにしかない書き方を確かめる入力は、bashの版を見て飛ばします。
