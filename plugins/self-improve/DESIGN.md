# 自己改善ハーネス 設計書

`self-improve` プラグインの設計。**この文書は 2.x（user 単位で動く版）の設計を書く。** 実装は、11 章のステップ 1（最小構成）とステップ 2（自動改善）まで済んでいる。ステップ 3 のうち `test-guards.mjs` と、自分で足すガードも入っている。ステップ 4（棚卸し）と 13 章の付録は、まだ作っていない。実装で決めたこと・設計から変えたことは本文に反映し、14 章の最後に一覧にしている。1.x（リポジトリごとに `init` して `harness/` に設定と失敗票を置く作り）との違いも、14 章にまとめている。

## 1. 目的とスコープ

Claude Codeが同じ失敗を二度しない状態を、仕組みとして作ります。失敗と作業中の気づきを記録し、改善候補としてためます。件数の重なった候補は、決めた日時に仕組みが自分で検討し、試用のルールやSkillとして追加・編集します。結果は次のセッション開始時に報告します。定着させるか、自分専用にするかチームへ出すかは、人が決めます。このループを、1つのプラグインとして実装します。

| 項目 | 内容 |
| --- | --- |
| 対象レイヤー | 既存ハーネス（Claude Code）の上に載せる現場用ハーネス。エージェントループ本体は作らない |
| 配布形態 | プラグイン用リポジトリ `claude-code` に `self-improve` プラグインとして追加 |
| 適用先 | **その人が開くすべてのgitリポジトリ**（user 単位）。リポジトリごとの初期設定は要らない。止めたい場所は、user の設定の `exclude` に書く。言語やフレームワークは問わない |
| 置き場所の考え方 | 記録（失敗票）、設定、自分だけに効く対策は、user 側（`~/.claude/self-improve/`）とプラグインのデータ領域に置く。リポジトリに置くのは、チームに効かせると人が決めたものだけ |
| 改善の対象 | 自分専用のルール、`.claude/rules/`、禁止操作のガード、検証コマンド、Skills、CLAUDE.md |
| 対象外 | モデルの学習・ファインチューニング、エージェントループの自作 |

進め方の前提は3つです。

- **改善は任意。** 振り返りも棚卸しも、やらなくても何も壊れません。
- **作業を止めるのは2つだけ。** 禁止操作のガードと、検証コマンドの失敗です。それ以外は警告にとどめます。
- **小さく始める。** 最初は記録・ガード・検証・その場の振り返りだけを作り、失敗票がたまってから広げます（11章）。

user 単位にした理由は2つです。1つは、リポジトリごとに `init` して `harness/` をコミットする作りだと、共有リポジトリに個人の失敗の記録と設定が混ざり、チームの合意がないと使い始められないこと。もう1つは、失敗の記録とガードは、入れた時点からどのリポジトリでも効くほうが、取りこぼしが少ないことです。その代わり、関係のないリポジトリでも動くので、止める手段（除外）と、動いていないときの軽さ（9章）を設計に入れます。

仕組みそのものはスタックに依存しません。スタックごとに変わるのは検証コマンドとリンターの設定だけで、どちらも適用先のリポジトリに置きます。本文の例にHonoやExpoが出てきますが、説明用です。プラグインのスクリプト（`.mjs`）はNode.jsで動くため、別スタックのリポジトリでも開発マシンにNode.jsが必要です。

成功の定義は「同じ原因の失敗が再発しないこと」と「指示ファイルが膨らまないこと」の両立です。

## 2. 設計原則

原則は9つです。1〜8は調査した一次情報から、9はこの設計の前提（改善は任意）から置いています。

| # | 原則 | 根拠 | この設計での採用 |
| --- | --- | --- | --- |
| 1 | ルールは実際の失敗からだけ作る | Hashimoto氏は、自身のAGENTS.mdの各行がエージェントの実際の悪い挙動に基づくと述べている（[My AI Adoption Journey](https://mitchellh.com/writing/my-ai-adoption-journey)） | 変換で作るルール行には失敗票IDを付ける。既存の行と、構成を説明する「地図」の行は対象外 |
| 2 | 文章より決定的な制御を優先する | OpenAIのチームは、ドキュメントで足りない規則をリンターや構造テストへ昇格させた（[Harness engineering](https://openai.com/index/harness-engineering/)） | 同じ原因が繰り返すなら、文章ルールからガード・検証コマンド・リンターへ移す |
| 3 | センサーの出力はエージェント向けに書く | Böckeler氏は、直し方を含むリンターメッセージを「良い意味のプロンプトインジェクション」と呼ぶ（[Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html)） | ガードとリンターのエラー文に、直し方を必ず1行書く |
| 4 | 指示ファイルは地図にする | Claude Code公式は1ファイル200行未満を目安とし、長いほど遵守率が下がるとしている（[Memory](https://code.claude.com/docs/en/memory)）。OpenAIは約100行の目次にした | self-improve が毎回読み込ませる行数（試用ルールと自分専用のルール）に目安を置く。チームへ出すルールは `.claude/rules/`（paths付き）とSkillsへ逃がす。リポジトリのCLAUDE.mdの長さは、チームのものなので、この仕組みでは数えない |
| 5 | エージェントを再生して確かめない | Anthropicによると、1回75%で通るタスクが3回とも通る確率は約42%まで落ちる（[Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）。少ない試行での再生は判定が安定しない | 再生による再現確認はしない。ガードは入力を与えるテストで、文章ルールは再発の有無で確かめる（6章） |
| 6 | 足すだけのループにしない | 自己進化型エージェントのサーベイは、無制限の蓄積による劣化を指摘し、寄与の小さいものを退役させることを勧める（[Self-Evolving Coding Agents](https://arxiv.org/pdf/2608.03392)） | 試用を経てから定着させ、棚卸しで減らす（7章、8章） |
| 7 | ハーネス自身を守る | 同サーベイは、評価する側が変質して「常に合格」になる危険を挙げる | ガードの定義、検証コマンド、そのテストへの書き込みには、必ず人の確認を挟む |
| 8 | 人が舵を取る | Böckeler氏は、再発時にguidesやsensorsを改善する作業を人の「steering loop」と位置づける | 効き始めは自動でよいが、定着させる前（自分専用への昇格、チームへのコミット）に、必ず人が中身を確かめる。失敗票の起票と昇格は、人だけの操作にする。反映先はローカル |
| 9 | 作業を止めない | この設計の前提。改善は任意で、本来の開発を妨げない | 止めるのは禁止操作と検証の失敗だけ。整合や行数の問題は警告にする |

原則1と6は緊張関係にあります。失敗のたびに足すと肥大化し、足さなければ再発します。この設計は「試用として軽く足し、定着させるかは後で人が決める」ことで両立させます。

自動改善（4章）もこの考え方の上にあります。自動で書き込むのは、リポジトリの外にある試用の領域だけです。効き始めるのは自動、定着させるのは人、という分担にします。定着の行き先は2つあります。自分専用（user 側に置く。ほかの人には影響しない）と、チーム（リポジトリにコミットする）です。

## 3. 全体アーキテクチャ

ハーネスは6段階のループと、任意の棚卸しでできています。記録から、日時起動の検討、試用としての追加・編集、次のセッションでの報告までは自動で動きます。定着させる経路（自分専用への昇格、チームへのコミット）には、必ず人の承認が入ります。

```text
1 記録（hooks）
  → 2 事象メモと改善候補（Stop の hook と Claude）
  → 3 振り返り（auto-improve が日時起動で。人が retro で始めてもよい）
  → 4 変換（試用のルール・Skill、承認待ちの案）
  → 5 報告と確認（次のセッション開始時、review）
  → 6 承認（人が残す・直す・消す・昇格する（自分専用かチームへ）を選ぶ）
  → 1 に戻る

棚卸し（任意）：使われていないものを一覧にして、人が減らす
```

棚卸しで出た削除や昇格も、新しい変換と同じく人の承認を通ります。

| 段階 | 担い手 | 成果物 | 詳細 |
| --- | --- | --- | --- |
| 1 記録 | hooks（自動） | 生ログ | 4章 |
| 2 事象メモと改善候補 | `Stop` hook（自動）。事象メモはスクリプトが作り、改善候補は、hookに促されたClaudeが書く | 事象メモ、改善候補 | 4章 |
| 3 振り返り | 決めた日時に `/self-improve:auto-improve` が上位の候補を検討する（自動）。人が `/self-improve:retro` を呼んで始めてもよい | 失敗票 | 4章 |
| 4 変換 | 自動の検討は、文章ルールとSkillを試用として追加・編集する。ガードと検証コマンドは案にとどめる | 試用ルール、試用Skill、承認待ちの案 | 4章、5章 |
| 5 報告と確認 | 次のセッション開始時に報告する（自動）。効き目はテスト（ガード）と再発の有無で見る | 報告、テスト結果、再発の一覧 | 4章、6章 |
| 6 承認 | 人。残す・直す・消すを選び、残すものを、自分専用かチームへ昇格する | 自分専用のルール・Skill、またはコミットされた変更 | 7章 |
| 棚卸し（任意。未実装） | `/self-improve:harness-prune` が一覧を出し、人が決める | 削除・昇格の案 | 8章 |

### どこで動くか

self-improve は、プラグインを入れた時点から、すべてのgitリポジトリで動きます。`init` は要りません（`/self-improve:init` は、設定を手元に置くための、user 単位の任意の初期設定です。9章）。

| 場所 | 動き |
| --- | --- |
| gitリポジトリの中（worktreeを含む） | 動く |
| gitリポジトリでない場所 | 何も記録せず、何も止めない |
| user の設定（`~/.claude/self-improve/config.json`）の `exclude` に書いたパスと、その下のリポジトリ | 何も記録せず、何も止めない（ガードも効かせない） |
| ホームディレクトリそのもの（ホームをgitで管理している場合）、`node_modules` の中 | 組み込みで除外する |
| `HARNESS_DISABLE=1` で起動したセッション | 何も記録せず、何も止めない |

判定の決まりは次のとおりです。

- **`exclude` はパスの前方一致。** 書けるのは、絶対パスか `~/` で始まるパスです。そのパスそのものと、その下にあるリポジトリが外れます。パターン（`*` など）は使いません（何が外れるかを、読んで分かるようにするためです）。
- **実体のパスで比べる。** リンク経由で開いても、同じ結果にします。worktreeは、本体のリポジトリ（gitの共通ディレクトリ）が除外されていれば、外します。大文字小文字を区別しないファイルシステム（macOS、Windows）では、小文字にそろえて比べます（`exclude` に `~/Work` と書いて、実体が `~/work` でも外れるように。7章の、書き込みの確認と同じ考え方です）。
- **セッションを始めたリポジトリで決める。** 見る順は、`CLAUDE_PROJECT_DIR`（hookに渡る）、SessionStartが引き渡した `HARNESS_PROJECT_DIR`（Bashから呼ぶ `harness-note` 用）、作業ディレクトリ、の順で、最初に見つかったgitリポジトリです。除外したリポジトリで始めたセッションは、途中で別のリポジトリへ移っても、最後まで止めます。除外していないリポジトリで始めたセッションは、途中で除外した場所へ移っても、もとのリポジトリのセッションとして動かします。セッションの途中で対象が変わると、「どこまで記録されたか」を人が追えなくなるためです。
- **判定は1か所で行う。** ガードの早い判定（何もしないで抜けるかどうか）と、記録する側の判定は、同じモジュール（`scripts/lib/scope.mjs`）の同じ関数を使います。2か所で別々に書くと、「ガードは止めたのに記録は残る」のような食い違いが起きるためです。このモジュールは、すべてのツール呼び出しで読み込まれるので、Node.jsの標準だけで書き、ほかのモジュールを読み込みません。
- **書き間違いは、安全な側に倒す。** user の設定がJSONとして読めない、`exclude` が配列でない、`exclude` に解釈できない値（相対パス、文字列でない値）がある、のどれかのときは、どこを除外したかったのかが（全部は）分かりません。このときは、**ガードは効かせたまま、記録と掃除を止めます**（生ログ、ガードの拒否の記録、セッションの状態、事象メモ、改善候補、ターン終了時の確認、検証）。除外したつもりの場所に記録を残さないためです。セッション開始時に、直すまで毎回知らせます。試用ルールと自分専用のルールの読み込みは続けます。
  - `exclude` の一部の値だけが解釈できないときは、**正しく書けている値の除外は効かせます**（その場所では、ほかの除外と同じく、ガードも記録も止まります）。除外したつもりの場所で、ガードや記録が動き出さないようにするためです。JSONとして読めない、`exclude` が配列でない、のときは、どこも除外しません。
- **リポジトリの場所を決めるファイルが壊れていても、上へ探しに行かない。** `.git` があるのに、gitの共通ディレクトリを解決できないとき（`.git/commondir` の先がない、worktreeの `.git` のファイルが読めない・形が違う、その `gitdir` の先がない）は、上の階層へ探しに行かず、その場所をリポジトリとして扱います（共通ディレクトリは、解決できたところまで。閉じる側に倒します）。2.0.1 までは上の階層へ探しに行ったので、`.git/commondir` を書き換えるだけで、そのリポジトリが「gitリポジトリでない」か「ホーム」と判定され、ガードも記録も止まりました。git自身も、この場合は上へ探しに行きません。これらのファイルへの書き込みには、確認も挟みます（7章）。
- **見つからないパスは、知らせるだけ。** `exclude` に書いたパスが存在しないときは、書き間違いのおそれがあるので、セッション開始時に知らせます（除外そのものは効かせます。あとで作るディレクトリを先に書くこともあるためです）。

## 4. 記録、事象メモ、改善候補、失敗票

記録は4層に分けます。hookが信号を生ログに残し、ターンの終わりに事象メモへまとめます。同じくターンの終わりに、Claudeが気づきを改善候補として1行で残します。人が振り返るときに、これらを材料に失敗票を起票します。生ログ、事象メモ、改善候補はプラグインのデータ領域に、失敗票は user 側（`~/.claude/self-improve/incidents/`）に置きます。どれも、リポジトリには置きません。

事象メモは機械的に作る証拠で、改善候補はLLMが書く未検証の主張です。この2つは混ぜません。判断が入るのは失敗票からです。

### 拾う信号

| 信号 | 拾い方 | 使い道 |
| --- | --- | --- |
| ツールの失敗 | `PostToolUseFailure` hook。`tool_name`、`error` の1行目、`is_interrupt` を残す | 事象メモの材料 |
| 人の訂正 | `UserPromptSubmit` hookで訂正語（「違う」「戻して」など）を検出する | 事象メモの材料。直前のターンに紐づける |
| ガードの拒否 | `guard-harness.mjs` が自分で記録する | 事象メモの材料、棚卸し |
| 検証の失敗 | `verify.mjs` が自分で記録する。出力に含まれる失敗票IDも拾う | 事象メモの材料、棚卸し |
| Skillの呼び出し | `PreToolUse` hook（Skillツール）と、`UserPromptExpansion` hook（人が直接呼んだ分）で記録する | 棚卸し |
| paths付きルールの読み込み | `InstructionsLoaded` hookでファイルパスを記録する | 棚卸し |

下の2つは棚卸しを作る段階（11章のステップ4）で足します（未実装）。生ログは `${CLAUDE_PLUGIN_DATA}/events/<リポジトリID>/` に置き、リポジトリには入れません。リポジトリIDは、gitの共通ディレクトリのパスから作ります。同じ名前のリポジトリやworktreeを取り違えないためです。リポジトリの中のパスは、リポジトリの根からの相対パスで残し、外のパス（リンクの先がリポジトリの外にあるときなど）は、ホームを `~` に置き換えて残します（絶対パスのまま残しません）。

`UserPromptSubmit` は、人が打ったプロンプト以外でも発火します（定期実行のプロンプトなど）。入力からは見分けられないので、自動改善のセッションの分だけを除きます。

訂正語は、直前のターンがあるときだけ調べます（セッションの最初の依頼は、訂正ではありません）。`/` で始まる依頼文（スキルの呼び出し）は調べません。文ごとに見て、質問の文（「？」で終わる文、「何が違う」「違いは」「間違いがないか」など）は訂正に数えません。語の一覧はスクリプトが持ち、user の設定の `correction_words` で足せます。

記録用のhookは `"async": true` で動かし、セッションを遅くしません。`PostToolUseFailure` の `error` は形式がツールごとに違うため、1行目だけをキーにします（[Hooks reference](https://code.claude.com/docs/en/hooks)）。

### 事象メモ

事象メモは、振り返りの材料をターンの終わりにファイルへまとめたものです。あとから振り返るときに「何を頼み、何が起きたか」を思い出せるようにします。

- **作るタイミング**：`Stop` hook。そのターンに上の信号が1つでもあったときだけ作ります。信号のないターンでは何も残しません。
- **作り方**：スクリプトが機械的に組み立てます。LLMは使いません。要約と解釈は、振り返りのときに行います。
- **中身**：そのターンの依頼文、起きたこと（失敗したツールとエラーの1行目、拒否や検証失敗の内容）、Claudeの最後の応答、トランスクリプトのパス、日時。
- **訂正の扱い**：訂正は次のターンの依頼文に現れます。そのため、直前の1ターン分の依頼文と応答を一時的に持っておき、次のターンで訂正語が出たら、その内容とあわせて事象メモにします。
- **保存先**：`${CLAUDE_PLUGIN_DATA}/episodes/<リポジトリID>/`。git管理の外です。90日で消します（初期値）。消すのは、セッション開始時（startup）の掃除です。掃除は**1日1回**、データ領域にある**全リポジトリの分**をまとめて行います（下の「掃除」）。
- **書き直し**：同じターンで `Stop` が何度か起きても（検証の失敗で続行したときなど）、事象メモは1つで、最後の状態に書き直します。

依頼文と応答は `Stop` と `UserPromptSubmit` の入力から取ります。トランスクリプトのファイルは書き込みが遅れることがあり、`Stop` の時点で最後の応答が入っているとは限らないからです（[Hooks reference](https://code.claude.com/docs/en/hooks)）。

事象メモには依頼文と応答の全文が入ります。秘密情報が混ざりうるので、リポジトリの外に置き、信号のあったターンに限り、期限で消す、の3つで範囲を絞ります。

### 改善候補

改善候補は、Claudeが作業中に得た気づきを1行で書き残したものです。hookのスクリプトでは拾えない「気づいたバグ」「よくあるミス」「ユーザーの好み」を対象にします。

- **作るタイミング**：ターンの終わり。**そのターンに信号（失敗、訂正、拒否、検証の失敗）があったときだけ**、`Stop` のhookがClaudeに「書き残す気づきがあれば記録し、なければそのまま終わる」よう頼みます。ファイルの変更があっただけのターンでは、頼みません。すべてのリポジトリで動くので、変更のたびに1往復を足すと、トークンと待ち時間がかさむためです。信号のないターンの気づきは、人が頼めば記録できます。気づきがあれば、Claudeが `harness-note add` で記録してから終わります。頼むのは1ターンに1回だけです（9章）。
- **中身**：カテゴリ、`cause_key`、1行の内容、日時、セッションID。同じターンに事象メモがあれば、その参照も入れます。
- **キーの付け方**：記録の前に `harness-note keys` で既存のキーを確かめ、同じ原因なら同じキーを使います。キーは英小文字・数字をハイフンでつないだ3〜50文字です。似たキー（語の並び替え、複数形、前方一致、1〜2文字の違い）が既にあるときは、`harness-note add` が記録したうえで警告し、まとめ直すコマンド（`harness-note rekey`）を示します。
- **上限**：1つのセッションが記録できるのは、直近24時間に3件までです。超えた分は記録せず、「そのまま終了してよい」と返します（エラーにはしません）。数えてから書くまでを排他にするので、同時に呼ばれても超えません。
- **短時間の重複**：同じセッションが同じキーを10分以内にもう一度書いたとき、または同じキー・同じ文面が10分以内に来たとき（やり直しなど）は、記録せず、上限にも数えません。
- **セッションID**：`Stop` のhookが、記録のコマンドにセッションIDを添えて頼みます（`--session`）。渡らなかったときは、環境変数、直近に動いていたセッションの順に推定します。件数は「異なるセッションの数」で数えるので、**hookが記録しているセッションのIDだけ**を受け付けます（`lock` と同じ前提）。実在しないIDを名乗っても、件数は増えません。`--session` と環境変数のIDが食い違う呼び出しは、エラーにします。さらにガードが、`harness-note` の呼び出しに付いた `--session` を、hookに渡る本物の `session_id` と照らし、合わないものを拒否します（下の「自動改善のセッションの隔離」）。
- **保存先**：プラグインのデータ領域の `candidates/<リポジトリID>/`。git管理の外です。好みの候補（`behavior/preference`）だけは、user 単位の `candidates/_user/` に置きます（下の「好みの候補」）。どの候補にも、どのリポジトリで出たか（名前とID）を残します。

改善候補には状態があります。

| 状態 | 意味 | 件数に数えるか |
| --- | --- | --- |
| `new` | 記録されたまま | 数える |
| `consumed` | 失敗票（下書きを含む）の材料になった | 数えない |
| `rejected` | 人が「消す」「対応しない」を選んだ | 数えない |

90日を過ぎた `new` は消します（`consumed` と `rejected` は、採否の記録として残します）。

件数は、同じ `cause_key` の `new` の候補を記録した**異なるセッションの数**で数えます。1つのセッションで同じキーを何度書いても1件です。荒れた1回の作業だけでルールが入るのを防ぎます。改善候補は1件では何もしません。件数が重なったときに、はじめて自動改善の対象にします。

カテゴリは次の5つから始め、user の設定で変えられるようにします。実際の候補に合わせて見直す前提の仮置きです。

| カテゴリ | 中身 | 扱い |
| --- | --- | --- |
| `dev/bug` | 作業中に気づいた実装のバグ | 自動改善の対象外。報告に一覧を載せ、確認のときに「Issueにする／今直す／捨てる」を選ぶ |
| `dev/cause` | バグが起きた原因 | 自動改善の対象 |
| `dev/mistake` | よくある開発時のミス | 自動改善の対象 |
| `dev/other` | 上に当たらない開発上の気づき | 自動改善の対象外。報告に件数を載せ、人が振り返るときに判断する |
| `behavior/preference` | ユーザーの好み、選びがちな選択肢 | 自動改善の対象外。**user 単位で、全リポジトリの分を数える。** 3件以上重なったら、セッション開始時に1行で知らせ、本人に確認のうえ `~/.claude/CLAUDE.md` へ |

#### 好みの候補

好みは、リポジトリではなく、人に付きます。そのため、ほかの候補と扱いを分けます。

- **保存**：user 単位の1か所（`candidates/_user/`）に置きます。どのリポジトリのセッションからも、同じ候補が見えます。
- **数え方**：全リポジトリの分を、異なるセッションの数で数えます（リポジトリAで1回、リポジトリBで2回なら、3件）。
- **知らせ**：リポジトリごとではなく、user 単位で1つにまとめます。知らせを閉じた記録も user 単位（`state/_user/state.json`）に持つので、どこかのリポジトリで1回閉じれば、ほかのリポジトリでも出ません。重なった好みの顔ぶれが変わったら、もう一度知らせます。
- **自動改善の報告には載せない**：自動改善はリポジトリごとに動くので、user 単位のものを載せると、リポジトリの数だけ同じ知らせが出るためです。
- **採否**：どのリポジトリで決めても、全リポジトリの分にまとめて付きます。合っていれば、人が `~/.claude/CLAUDE.md`（全リポジトリに効く）に1行で足します。

好みの候補も `harness-note` で記録して数えます。Claude Codeの自動メモリが同じ内容を別に保存することがありますが、そちらは止めません（[Memory](https://code.claude.com/docs/en/memory)）。そのため、試用ルールを消しても、同じ内容が自動メモリに残って効き続けることがあります。消すときは `/memory` もあわせて確かめます。

### 日時起動の自動改善

決めた日時に、仕組みが自分で候補を検討し、対策を追加・編集します。人が毎回指示する必要はありません。結果は、次のセッション開始時に報告します。

**自動改善はリポジトリごとに動き、既定では止めてあります。** 記録とガードはすべてのgitリポジトリで動きますが、自動改善は、間隔を設定したリポジトリでだけ動きます。候補も、試用も、未確認の件数も、ロックも、リポジトリごとです（好みの候補だけが user 単位です）。

**起動**：Claudeデスクトップアプリのスケジュール済みタスクが、決めた日時に `/self-improve:auto-improve` を呼びます（手順はプラグインの `SCHEDULING.md`）。プラグインは自分では起動できないためです。日時はタスクの側で決め、設定には間隔（`auto.interval_days`。有効にするときは7日）だけを持ちます。日時を2か所に書くと、ずれるためです。間隔は、user の設定（全リポジトリ）か、リポジトリごとの上書き（そのリポジトリだけ）に書きます（9章）。リポジトリの `harness/config.json` に書いても、読みません。

- 前回の実行から、間隔の半分がたっていないときは、何もせずに終わります。追いかけの実行と手動の実行が重なっても、二重には動きません。判定は `harness-note lock` が行い、実行した時刻は、ロックを取った時点で記録します（途中で落ちても、二重に動かないようにするため）。最小の間隔を「間隔の半分」にするのは、追いかけの実行（月曜9時の分が火曜の夜に動く、など）や手動の実行のあとでも、次の定時の実行を飛ばさないためです。
- 間隔（`auto.interval_days`）を過ぎても実行されていないときは、セッション開始時に知らせます。その場で `/self-improve:auto-improve` を呼べます。対象になる原因キーがないあいだは、知らせません（実行しても何も起きないため）。
- 初期値では止めてあります（`auto.interval_days` が0）。対象になる原因キーができると、セッション開始時に「自動改善を有効にしますか」と知らせます（閉じるまで。下の「次のセッションでの報告」と同じ扱い）。

**書き込みの原則**：自動改善は、`harness-note` コマンドを通してしか書き込みません。ファイルを直接編集することはありません。理由は2つあります。

- `.claude` 配下への書き込みには、編集を自動で許可するモードでも確認が出ます。そしてスケジュール済みタスクは、確認が出るとそこで止まって待ちます（[Permission modes](https://code.claude.com/docs/en/permission-modes)、[Desktop scheduled tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks)）。
- 書き込める場所と中身を、コマンドの側で決められます。プロンプトで頼むだけでは、範囲を守らせる保証になりません。

**置き場所**

| 作るもの | 置き場所 | 効かせ方 |
| --- | --- | --- |
| 試用ルール | プラグインのデータ領域の `trial/<リポジトリID>/rules/<原因キー>.json`（1つの原因につき1つ） | セッション開始時のhookが、Claudeのコンテキストに読み込ませる |
| 試用Skill | `~/.claude/skills/<リポジトリ名>-<名前>/` | Claude Codeが個人用のSkillとして読み込む |
| 失敗票の下書き | データ領域の `pending/<リポジトリID>/` | 効かせるものではない。人が残すと決めたときに、`harness-note incident add --from-draft` で失敗票として起票する（user 側に置く） |
| 実行の記録 | データ領域の `reports/<リポジトリID>/auto-YYYY-MM-DD.md` | 次のセッションの報告のもとになる |

どれもリポジトリの外にあり、gitには入りません。作業中の変更と混ざらず、worktreeで作業していても同じものが効きます。

試用ルールをデータ領域に置くと、ファイルの種類で絞ること（paths）はできず、常時ロードと同じ重さになります。そのため件数と行数に上限を置きます。自分専用へ昇格したルールも、同じようにセッション開始時に読み込むので、同じ行数の目安で数えます。チームへ昇格するときは、paths付きのルールとして `.claude/rules/` へ移せます。

試用Skillは個人用の場所に置くので、どのリポジトリでも見えます。名前にリポジトリ名を付け、説明文に「どのリポジトリの、どんな作業のときに使うか」を書かせます（説明文にリポジトリ名が入っていなければ、`harness-note` が拒否します）。

**対象の選び方**

- 同じ `cause_key` の候補が、異なるセッションで2件以上あるものを対象にします。件数の多い順、同数なら新しい順に並べ、1回の実行で上から3件まで扱います（初期値）。対象は `harness-note lock` がその場で決めてロックに書き込み、それ以外の原因キーへの書き込みは `harness-note` が受け付けません。
- 並べ替えはスクリプトが機械的に行い、LLMには選ばせません。LLMに選ばせると、ルールを足す方向に寄るためです。
- 対象にするカテゴリは `dev/cause` と `dev/mistake` だけです。ほかのカテゴリは報告に載せます。

**自動でやること**

1. 候補と事象メモを材料に、失敗票の下書きを作ります。事象メモがあれば内容を照らし、食い違うものは進めずに報告だけします。材料にした候補は `consumed` にします。
2. 対策を1つ選び、試用として追加します。
3. 実行の記録を書きます。1件ごとに、根拠にした候補と事象メモ、照らし合わせた既存のルールを残します。件数の集計と、報告に載せるだけのもの（バグ・その他の候補、見直しの時期が来た試用、再発した原因）は、`harness-note` が機械的に足します。好みの候補は、user 単位の知らせに回すので、載せません。

順番は `harness-note` が守らせます。**その実行で**下書き（`pending add`）を作った原因にしか、試用を追加・編集できません。前の実行の下書きがファイルとして残っていても、それでは通しません（ロックに、その実行で下書きを作った原因を記録して確かめます）。下書きを作ると、材料の候補が `consumed` になり、再発として数えられ、未確認の変更として登録されます。古い下書きで通すと、これらを飛ばして試用を編集できてしまうためです。1回の実行で、1つの原因に入れられる対策は1つです。環境が原因・再現しないと判断したものは、下書きだけを作ります（「対策を入れなかった記録」として、人の確認に回ります）。

歯止め（下）に掛かっていて試用を追加できない原因は、`lock` の時点で「いまは追加できません」と理由つきで示します。その原因には、下書きも作らせません（候補を `consumed` にしてしまうと、歯止めが外れたあとに対象に戻らないため）。ガード・検証コマンド・差分の案を出すときと、対策を入れないと判断したときだけは、下書きを作れます。

**試用中の原因がまた出たとき**

| 再発の回数 | 自動の扱い |
| --- | --- |
| 1回目 | 試用ルールを編集してよい。文言が悪かった可能性があるため。報告に「再発・編集」と書く |
| 2回目以降 | 編集しない。文章では効かないと見なし、ガードや検証コマンドへ移す案を報告に載せる |

再発は、編集したかどうかにかかわらず「再発した原因」（10章）に数えます。編集で再発が見えなくなるのを防ぐためです。数えるのは、試用中（または昇格済み）の原因について、自動改善が新しい下書きを作ったときです。同じ実行のなかで入れた試用は、その実行でもう一度 `pending add` を呼んでも、再発には数えません（下書きへの追記として扱います）。

再発として扱うのにも、新しい候補が2件（異なるセッション）必要です。1件では何もしない、という決まりをここでも変えません。試用Skillの再発と、昇格済みのルールの再発は、回数にかかわらず編集せず、案だけを報告に載せます。

**自動でやる範囲と、やらない範囲**

| 対策 | 自動の扱い | 理由 |
| --- | --- | --- |
| 文章ルールの追加 | 試用として置く | リポジトリの外にあり、消せば元に戻る |
| 試用ルールの編集 | 再発の1回目だけ | 上の表のとおり |
| Skillの追加 | 試用として置く。中身は名前、説明文、本文の文章だけ | リポジトリの外にあり、消せば元に戻る |
| 昇格済みのルール（自分専用のルール、`.claude/rules/`）、CLAUDE.mdの編集 | 差分の案を報告に載せる | git管理下のファイルと、user 側のファイルは、無人で書き換えない |
| ガード、検証コマンドの追加 | 案とテストケースを報告に載せる | 誤検知すると作業を止める。止める制御は、人が見てから入れる |
| 失敗票の起票、昇格 | しない（`harness-note` が見送る） | 記録として残すか、定着させるかは、人が決める。自動改善が作るのは下書きまで |
| コミット、プッシュ | しない | 定着は人が決める |

試用Skillには、スクリプト、hook、ツールの許可（`allowed-tools`）を入れさせません。Skillの設定欄を使うと、確認なしの実行やhookを持ち込めるためです。`harness-note` が書き込むときに検査し、当てはまるものは拒否します。

- 設定欄（frontmatter）は `harness-note` が自分で書きます。入るのは `name` と `description` だけです。SKILL.md の全文を受け取ったときも、ほかの設定欄（`hooks`、`allowed-tools`、`model`、`context`、`shell` など）があれば拒否します。
- 本文は文章だけです。読み込み時にシェルを実行する書き方（`` !`コマンド` `` と、` ```! ` のブロック）、シバン行、`<script>` を拒否します。公式ドキュメントによると、この書き方のコマンドは、Skillの内容がClaudeに渡る前に実行されるためです（[Skills](https://code.claude.com/docs/en/skills)）。`~~~!` のブロック、HTMLのコメント（読む人に見えない指示を置けるため）、`@` に続く語（ファイルの取り込みとして扱われうるため）も拒否します。この3つがSkillの本文でどう処理されるかは、公式ドキュメントに明記がないので、拒否の側に倒しています。`@` は、前の文字を問わず拒否します（`"@.env"`、`[@.env]`、`参照:@.env` も）。通すのは、メールアドレス（英数字の直後の `@`）と、コードの中（バッククォートで囲んだ部分と、コードブロック）だけです。デコレータ（`@Injectable()` など）を書けるようにするためで、エラー文に「コードはバッククォートで囲む」と書きます。
- 置くファイルは `SKILL.md` と、このプラグインが置いたことを示す印のファイルだけです。スクリプトなどの添付は置けません。
- 書き込み先は、名前から作ったパスを正規化して確かめます。`..` や区切り文字を含む名前、シンボリックリンクになっている書き込み先、すでにあるディレクトリには書きません。消せるのも、印のファイルがあるものだけです。
- 試用Skillを置けるのは、自動改善のセッションだけです。人が始める振り返り（`retro`）では、Skillは、自分専用なら `~/.claude/skills/` に、チームで使うならリポジトリの `.claude/skills/` に、承認を通して置きます（7章）。
- 自分専用へ昇格した試用Skillは、置き場所を変えず、印のファイルに昇格した日時を書きます。それ以降は試用として扱わず、`harness-note` も消しません（7章）。

**歯止め**

- **未確認の上限**：人がまだ確認していない自動変更が5件（初期値）に達したら、追加も編集もやめて、報告だけにします。報告を読まないまま試用がたまり続けるのを防ぐ、いちばん大事な歯止めです。
- **試用ルールは、誰が入れたものでも未確認に数える**：ロックしたセッション以外から入った試用ルール（人が `retro` で入れたものを含む）も、人が `review` で確認するまで、未確認として数えます（セッション開始時の1行にも、上限にも）。`harness-note` からは、どのセッションが入れたかを確かめきれない（`--session` は自己申告）ので、名乗りの判定に頼らない形にします。`retro` は、その場で人の承認を得ていれば、続けて確認済みにします。同じ原因に未確認の変更が既にあるときは、二重には数えません。
- **試用の上限**：試用ルールは10件、試用Skillは5件までです（初期値）。超えるときは追加しません。人が `retro` で入れる試用ルールにも、件数の上限は同じく効きます。
- **行数**：self-improve がセッション開始時に読み込ませる行数（**試用ルールと、自分専用のルールの合計**）が、目安（8章の `always_loaded_rule_lines`。初期値50行）を超えるときは、試用ルールを追加しません。人が入れるときは、止めずに警告します。**数えるのは、self-improve が足した分だけです。** リポジトリのCLAUDE.mdや `.claude/rules/`（チームのルール）の行数は数えません。チームのルールが長い共有リポジトリで、自分の試用ルールが1件も入らなくなるのを避けるためです（チームのルールの長さは、その人には変えられません）。試用ルールには、別に件数の上限があります。
- **止まっていることの知らせ**：未確認の上限や行数の目安で追加をやめているあいだは、セッション開始時に、その理由を1行で知らせます（自動改善を有効にしているときだけ）。行数の目安に掛かっていても試用Skillは入るときは、「試用ルールを追加していません（試用 Skill は追加できます）」と書きます。
- **矛盾**：既存のルールと矛盾しそうなときは、追加しません。
- **断られた原因**：人が「消す」を選んだ原因は、その後の候補が新たに2件たまるまで対象にしません。
- **中身**：ルールとSkillの本文に、指示の上書き、ガードの回避、外部への送信を促す文を入れさせません。候補は会話の内容からLLMが書いたもので、外から来た文章が混ざりうるためです。検査は言い回しの照合で、URLも拒否します。すり抜けも誤検知もあるので、人の確認が最後の関門です。試用ルールは1行・200文字までで、読み込むときにも同じ検査をします。
  - 照合の前に、文字をNFKCで正規化します（全角の英字などで照合を外せないように）。書式用の文字（ゼロ幅の文字、ソフトハイフン、双方向の制御など）、行・段落の区切りの文字（U+2028、U+2029、U+0085）、タブと改行以外の制御文字は、入っているだけで拒否します。
  - 各パターンは、すべての一致を調べます。1つ目が例外に当たっても、2つ目以降を見ます。
  - 禁じる側のルール（「〜しない」「〜するな」「Never …」）は通します。例外にするのは、その文が否定で終わるとき（日本語）か、同じ文の前に否定があるとき（英語）だけです。
  - HTMLのコメントは拒否します。
  - セッション開始時に読み込むときは、本文に加えて、原因キーと失敗票IDの形も確かめ、件数は `max_trial_rules` で切ります（新しいものを優先）。データ領域を直接書き換えられた場合の備えです。自分専用のルールの行にも、同じ検査をします（人が手で直せるファイルなので）。読み込まなかったものがあれば、知らせます。
  - **読み込みきれなかったルールは、黙って切らずに知らせます。** hookがコンテキストに渡せる量には上限があるので、ルールは合わせて6,000文字までを、行の途中で切らずに入れます（自分専用のルールを先に、試用ルールは新しいものから）。入らなかった分は、件数をセッション開始時に知らせます。

**自動改善のセッションの隔離**：`auto-improve` は最初に `harness-note lock` で自分のセッションIDを登録し、最後に `unlock` します。登録されたセッションでは、次のようにします。

- `guard-harness.mjs` は、**通すツールの一覧**で判定します。通すのは、Read、Grep、Globと、Bashの `harness-note` の単純な呼び出しだけです。それ以外のツール（Write、Edit、ほかのBash、MCPのツール、サブエージェントの起動、Webの取得など。あとから増えるツールも）は、すべて拒否します。確認は出しません。そのため、PreToolUse のhookは matcher を付けず、すべてのツールを見ます。
- Skill ツールは、読み直しのための `self-improve:auto-improve` だけを通します。自動改善のスキルは `lock` の前に読み込まれるので、ほかのスキルは要りません。スキルには、PreToolUse の外で動くものがあります（本文の `` !`コマンド` `` は、内容がClaudeに渡る前に実行され、`context: fork` のスキルはサブエージェントで動きます）。利用者がほかに入れているスキルの中身は分からないので、通しません。
- 「読むだけのBash」（`cat`、`git log` など）は通しません。読むのは Read・Grep・Glob です。読むだけのつもりのコマンドにも、書き込みや実行の抜け道（`sed` の `w`、`sort -o`、`find -exec`、`git -c core.pager=…` など）があり、見分けきれないためです。
- 通す `harness-note` は、次をすべて満たすものだけです。コマンド全体が `harness-note` の呼び出しだけでできている。環境変数の前置き、ファイルへのリダイレクト、コマンド置換、変数の展開がない（リダイレクト先やヒアストリングの語も見ます）。引用の外に、bashが語を作り替える文字（`{ } * ? [ ] ~`）がない。**hookに渡る本物の `session_id` と一致する `--session` が、ちょうど1つ付いている**（`--session=…` の形も、複数の指定も見ます）。データの置き場所を差し替えたり、ほかのセッションを名乗ったりできないようにするためです。
  - 引用の外の `{ }` を拒否するのは、ブレース展開で、ガードの読む語と、bashが実際に渡す語が食い違うためです。`{--session=zz,--key}` は、ガードには1語に見えますが、bashは `--session=zz --key` の2語に展開し、後ろの `--key` が本物の `--session` を値として飲み込みます。`*`・`?`・`[ ]`（パス名展開）と `~`（チルダ展開）も、同じ理由で拒否します。
- Bashのコマンドは粗く読み取ります。読み取りに自信の持てないもの（区切りが単純でないヒアドキュメント、終わりの見つからないヒアドキュメント、区切りを引用していない本文の展開、`$'…'`、`${…@…}`、閉じていない引用）は、拒否の側に倒します。
- 検証、事象メモ、改善候補の確認、セッション開始時の報告は動かしません。検証が失敗して、Claudeが作業途中のコードを無人で直すのを防ぐためです。
- `harness-note add`（改善候補の記録）は受け付けず、「何もせず終了してよい」と返します。ハーネス自身の作業が候補になるのを防ぐためです。

ロックはセッション単位です。同じ時間に人が別のセッションで作業していても、そちらの記録は止まりません。2時間たったロックは無効と見なします。セッションIDは、スキルの本文に埋め込まれる値（`${CLAUDE_SESSION_ID}`）を `--session` で渡します。IDが分からないまま `lock` はしません（人のセッションを巻き込まないため）。また、そのセッションをhookが記録していないとき（hookが動いていない、またはIDがhookの見ているものと違う）も、`lock` は始めません。書き込みの拒否が効かないまま、無人の実行が進むのを防ぐためです。

**セッションの名乗りを信じない**：`harness-note` に渡る `--session` は、呼ぶ側の自己申告です。そのままでは、自動改善のセッションが別のIDを名乗って、人の書き込みとして歯止めをすり抜けられます。次の3つで塞ぎます。

- ガード（PreToolUse）は、どのセッションでも、`harness-note` の呼び出しに付いた `--session` を、hookに渡る本物の `session_id` と照らし、合わないものを拒否します。`harness-note` の呼び出しを含むコマンドに、環境変数の前置き、変数の展開、コマンド置換、引用の外の `{ } * ? [ ] ~`、読み取りに自信の持てない書き方があるときも拒否します。ほかのコマンドで包んだ呼び出し（`command harness-note …`、`env … harness-note …`、`node <プラグイン>/scripts/note.mjs …`、`bash <プラグイン>/bin/harness-note …` など）も、引数を確かめられないので拒否します。このガード自身の書式の検査による拒否は、失敗の信号（`guard_denied`）には数えません。
- `harness-note` は、環境変数のIDと `--session` が食い違う呼び出しを受け付けません。`--session` を複数付けて違うIDを書いたものも同じです。
- 自動改善の実行中は、ロックしたセッション以外からの「人だけの操作」を、名乗りにかかわらず、すべて見送ります（失敗票の起票・更新・取り込み（`incident add` / `set` / `import`）、昇格（`promote`）、試用の追加・編集・削除、試用Skillの削除、候補の採否（`mark`）、キーのまとめ直し（`rekey`）、下書きの破棄、確認の結果の記録（`review done`）、知らせを閉じる（`report close`））。hookが動かない環境や、引き渡しの環境変数が届かない環境で、ロック中のセッションが別のIDを名乗っても、歯止めの外では何も書けないようにするためです。人は、実行が終わってからやり直します。

どのセッションが呼んだかを `harness-note` が確かめる手段は、引き渡しの環境変数しかなく、それが届くかどうかは実機の確認待ちです（14章）。そのため、判定を名乗りに頼る箇所を減らしています（上の3つ目と、4章の「試用ルールは、誰が入れたものでも未確認に数える」）。スキルに `--session` を書かせず、ガードが PreToolUse の `updatedInput` でhookの `session_id` を付ける方式にすれば、自己申告そのものをなくせます。これは、実機で3つのID（hookの `session_id`、スキルに埋め込まれるID、引き渡しの環境変数）の一致を確かめてから判断します（未対応）。

**ロックを試みたセッションは、あとも確認を挟む**：`lock` を呼んだセッション（始まらなかった場合を含む）は、ロックが外れたあとも、書き込みと、外へ働きかけるツール（MCPのツール、サブエージェントの起動、Webの取得、予定の登録）に確認を挟みます（2週間）。ロックが外れた直後に、同じセッションが続けてファイルを書き換えるのを防ぐためです。`harness-note` の側も、このセッションを自動改善のセッションと同じに扱い、上の「人だけの操作」をすべて見送ります。ガードは `harness-note` の呼び出しを「変更なし」として通すので、ここで止めないと、ロックを外した同じセッションが「人」として、対象外の試用ルールを足し、自分の変更を確認済みにし、報告を閉じられるためです。記録の期限（2週間）は、読み出すときにも確かめ、状態を書き換えるたびに期限切れを消します（次の `lock` を待ちません）。続きの作業と確認は、新しいセッションで行います。`unlock` は、実行の記録（`report write`）を書いたあとでなければ受け付けません。推定のIDでも受け付けません（別のセッションがロックを外せないように）。`harness-note status` は、ロックのIDを先頭の8文字しか出しません。 このセッションからの `harness-note` には、ロックが外れたあとも、一致する `--session` がちょうど1つ付いていることをガードが求めます。`--session` を省くと、引き渡しの環境変数が届かない環境では、直近の別のセッションと推定されて、人だけの操作が通ってしまうためです。

**リポジトリとロックの特定**：ガードは、リポジトリを `CLAUDE_PROJECT_DIR`、`HARNESS_PROJECT_DIR`、hookの `cwd` の順に見ます（入れ子のリポジトリへ `cd` しても、もとのリポジトリのガードが外れないように。3章の「どこで動くか」と同じ判定です）。ロックは、セッションIDで、データ領域の全リポジトリの分を調べます。読めないロックのファイルは、「ロックなし」ではなく、更新から2時間のあいだ、どのセッションに対しても拒否の側に倒します。

**次のセッションでの報告**：セッション開始時に、何をしたかを知らせます（例：「自動改善（11/16）：試用ルールを2件追加、1件を編集。承認待ちの案が1件」）。同じ内容をClaudeのコンテキストにも渡すので、その場で中身を尋ねられます。

人が読んだかどうかを、hookの側からは知れません（プロンプトの送信もターンの終了も、無人のセッションで起きます）。そのため「見た」を推定せず、報告の1行は、**人が `/self-improve:review` を開くか、明示的に閉じる（`harness-note report close`）まで、または7日たつまで**、セッションを始めるたびに出します。1回きりの知らせ（「有効にしますか」「間隔を過ぎても実行されていません」など）も同じ扱いです。自動改善のセッション（ロック中、または自動改善を呼び出したセッション）が `review` を読んでも、閉じません。自動改善の実行中と、セッションを確かめられないとき（`--session` も引き渡しの環境変数もなく、IDが直近のセッションからの推定のとき）も、`review` と `report close` は知らせを閉じません。

閉じたあとも、未確認のものが残っているあいだは、1行だけ出します（例：「未確認の自動変更3件。いちばん古いものは12日前」）。これは、確認が済むまで消えません。

**確認のしかた**：`/self-improve:review` を呼ぶと、未確認の自動変更を1件ずつ見せます。

| 選ぶもの | 起きること |
| --- | --- |
| 残す | 試用のまま続ける。下書きから失敗票を起票する（`harness-note incident add --from-draft`。user 側に置く。コミットするものはない） |
| 直す | その場で文言を直す。あとは「残す」と同じ |
| 消す | 試用を消し、下書きを捨てる。その原因を「断られた」と記録する |
| 昇格する | 自分専用か、チームかを選ぶ。自分専用は `harness-note promote --to personal`（user 側に置く）。チームは、`.claude/rules/`（Skillは `.claude/skills/`）へ移してから `harness-note promote --to team`。7章の承認を通す |

承認待ちの案（ガード、検証コマンド、git管理下のファイルの編集）は、差分を見て承認すると反映します。何もしなければ、試用のまま効き続けます。ただし未確認が上限に達すると、自動改善は新しい追加をやめます。

未確認の自動変更は、1回の実行で、1つの原因につき1件と数えます（試用ルールの追加、再発による編集、試用Skillの追加、承認待ちの案、対策を入れなかった記録のどれか）。確認の結果は `harness-note review done`（残す・直す・消す・承認・却下）と `harness-note promote`（昇格）で記録します。同じ確認で、見直しの時期が来た試用、バグの候補、重なった好みの候補も扱います。

### 振り返り（`/self-improve:retro`）

人が自分で始める振り返りです。自動改善を待たずに対策を入れたいときに使います。

- **その場で振り返る**：失敗した直後に、同じセッションで呼びます。会話の文脈がそのまま材料になります。
- **原因を指定する**：`/self-improve:retro <原因キー>` で呼ぶと、その原因の改善候補と事象メモを材料にします。

自動変更の確認は、別のスキル（`/self-improve:review`）に分けています。失敗した直後に `retro` を呼んだのに、先週の自動変更の確認が始まる、という取り違えを防ぐためです。

どちらの場合も、エージェントを再生して失敗を再現する確認はしません。代わりに、失敗票を起票するときに証拠を確認します。事象メモやトランスクリプトに詳しい経緯が残っていれば、失敗票の「実際の結果」がそれと合っているかを人が確かめます。証拠が薄いものは、変換せず記録だけ残します。

`retro` は、失敗票を `harness-note incident add` で起票し、対策を1つ入れます。記録と、自分だけに効く対策（試用ルール、自分のガード、自分専用のSkill）は、リポジトリの外に置くので、コミットするものはありません。チームに効かせる対策（リポジトリのガード、検証コマンド、`.claude/skills/`）を足したときだけ、1変換1コミットで反映します。

### 失敗票

失敗票は、**全リポジトリの分を、user 側の `~/.claude/self-improve/incidents/INC-YYYY-NNNN.md` に置きます**（1件1ファイル）。リポジトリには置きません。失敗票は「その人が、そのリポジトリで、何を間違えさせたか」の記録で、共有リポジトリに混ぜるものではないためです。gitで管理するかどうかは、その人が決めます（dotfilesなど）。

**起票は `harness-note incident add` だけが行います。** ClaudeがWriteで直接ファイルを書くことはしません。理由は3つです。IDの連番を、数えてから書くまで排他にして振れること。どのリポジトリの票かを、機械的に記録できること。`~/.claude` の下への書き込みには確認が出るので、失敗のたびに確認を出さないことです。

- **人だけの操作。** 自動改善のセッションと、その実行中のほかのセッションからは、起票も更新もできません（「見送り」を返します）。自動改善が作るのは、データ領域の下書きまでです。人が確認で「残す」か「昇格する」を選んだときに、下書きから起票します。
- **IDは、全リポジトリで1つの連番**（年ごと）。置き場所が1つなので、リポジトリごとに番号を振ると、ファイル名がぶつかるためです。
- **上書きしない。** 番号は、すでにあるファイルを数えて次を振り、同じ名前のファイルがあれば失敗する方法で書きます（あれば、その次の番号を試します）。手で置いたファイルや、形の崩れたファイルがあっても、上書きしません。
- **どのリポジトリで起きたかを記録する。** リポジトリの名前（`repo`）、ID（`repo_id`）、リモートのURL（`remote`）です。リポジトリのIDはマシンの中のパスから作るので、別のマシンや、置き場所を変えたあとでも分かるよう、リモートのURLも残します。
- **リモートのURLからは、認証情報を取り除く。** `scheme://` の形は、利用者名とパスワード（`@` を含むパスワードでも、最後の `@` まで）、`;` のパラメーター、クエリ、フラグメントを落とします。`://` のない形（`git@host:org/repo.git` などのscpの形）は、`@` を含めば最後の `@` までを落とし（`user:token@host:…` の `token` も残さない）、利用者名が `git` だけのときは `git@` を残します。`;` のパラメーター、クエリ、フラグメントも落とします。ローカルのパス（`/path/to/repo`、`file://…`）は記録しません（マシンの中のパスを残さないため）。URLは、gitの設定ファイルから `origin` を読みます（gitコマンドは呼びません）。
- **下書きから起票するときは、下書きの値を引き継ぐ**（`--from-draft`）。自動改善が試用を入れたとき、下書きには `status: trial`、`control`、原因の分類、試用を始めた日が入っています。これを捨てて `open` に戻すと、試用が入っているのに票は未対応、という食い違いが残るためです。起票したら、下書きは捨てます。
- **関連する票と整合のチェックは、今のリポジトリの票だけを見る。** 同じ `cause_key` でも、別のリポジトリの票は関連に入れません（原因キーは、リポジトリごとに付けるものです）。一覧（`incident list`）も、今のリポジトリの分だけを出します（`--all` で全部）。別のリポジトリの票は、書き換えません。
- **更新は `harness-note incident set`**（`status` と `control`）。昇格のときは、`harness-note promote` が票を `converted` にします。

```yaml
# 失敗票の先頭（frontmatter）
id: INC-2026-0007          # harness-note が振る（全リポジトリで 1 つの連番）
date: 2026-11-15
repo: example-app          # どのリポジトリで起きたか（名前）
repo_id: example-app-0123456789ab
remote: https://example.com/acme/example-app.git   # 認証情報は取り除いてある。なければ null
area: backend              # 値はリポジトリごとに決める
category: dev/mistake      # 改善候補のカテゴリ
signal: human_correction   # tool_failure / human_correction / guard_denied / verify_failed / noticed
root_cause: knowledge      # 5章の分類から1つ
cause_key: route-placement # 「同じ原因」を表す短いキー。自由に付ける
related: []                # 同じ cause_key の過去の失敗票（今のリポジトリの分）
severity: normal           # normal / high
status: open               # open / trial / converted / wontfix / retired
control: null              # 足した制御の場所（下の表）
applied_by: null           # auto（自動改善）/ human
trial_started_at: null
promoted_at: null
```

本文は「何を頼んだか」「期待した結果」「実際の結果」「根拠（セッションID、事象メモ、コミット）」の4見出しです。

`control` の書き方は、置き場所で決まります。

| 足した制御 | `control` |
| --- | --- |
| 試用ルール | `trial:rules/<原因キー>` |
| 試用Skill | `skill:<リポジトリ名>-<名前>` |
| 自分専用のルール、自分専用に昇格したSkill、自分のガード（user 側のファイル） | `personal:<~ で始まるパス>` |
| チームのルール、Skill、ガード、検証コマンド（リポジトリのファイル） | リポジトリの根からのパス |

「同じ原因」は `cause_key` が同じことで判定します。同じ原因の失敗がまた起きたら、新しい失敗票を起票し、`related` で最初の票につなぎます（起票のときに、自動で入ります）。制御は最初の票に付けます。`retro` は起票の前に、既存の `cause_key` の一覧を見せて、同じものがないかを尋ねます。

`status` は次のように変わります。

| から | へ | 条件 |
| --- | --- | --- |
| `open` | `trial` | 試用ルールまたは試用Skillを置いた |
| `open` | `converted` | ガード、検証コマンド、Skillを承認して足した（試用を経ない） |
| `trial` | `converted` | 人が昇格を承認した（自分専用でも、チームでも） |
| `trial` | `open` | 試用を外し、別の対策（ガードへ移す案など）を検討している |
| `trial` | `wontfix` | 人が「消す」を選んだ |
| `open` | `wontfix` | 環境が原因、再現しない、または対応しないと決めた |
| `converted` | `retired` | 棚卸しで制御を外した |

1.x の失敗票（リポジトリの `harness/incidents/`）は、`harness-note incident import` で取り込めます。IDは、空いていればそのまま使い、ほかのリポジトリの票と重なるときは、その年の次の番号に振り直して、もとのIDを `imported_from` に残します。何度実行しても、同じ票を二重には取り込みません。もとのファイルは消しません。

## 5. 分類と変換

失敗票は原因で8種類に分け、原因ごとに変換先と置き場所を決めておきます。毎回「とりあえずCLAUDE.mdに追記」となるのを防ぐためです。

カテゴリ（4章）は気づきの種類を表し、原因（この章）は変換先を決めます。この章の変換に進むのは、`dev/cause` と `dev/mistake` の候補から作った失敗票です。

| 原因 | 例 | 変換先 | 置き場所 |
| --- | --- | --- | --- |
| `knowledge` 規約や構成を知らない | Honoのルートを違うディレクトリに作る | 文章ルール1行 | 試用の領域（4章）。昇格後は、自分専用のルールか、`.claude/rules/`（paths付き） |
| `procedure` 手順を飛ばす | マイグレーション生成を忘れる | 手順をSkillにする。スクリプト化は人が承認してから | 試用の領域。昇格後は、自分専用のSkill（`~/.claude/skills/`）か、`.claude/skills/<名前>/` |
| `forbidden` やってはいけない操作 | 特定ディレクトリの手編集、本番DBへの書き込み | ガードの拒否パターン | 自分のガード（user 側）か、チームのガード（`harness/guards.json`） |
| `verification` 壊れたまま完了と報告 | 型エラーを残して終了 | 検証コマンド | リポジトリの `harness/config.json` の `verify` |
| `structure` 構造違反 | 層をまたぐimport、命名 | カスタムlint。検証コマンドから実行する | リポジトリのリンター設定 |
| `judgment` 判断の質 | 過剰設計、要件の取り違え | 仕様書への参照を促す文章ルール。人のレビュー | 試用の領域 |
| `environment` 環境やツールが原因 | 不安定なテスト、遅いコマンド | 環境を直す。ルールにしない | 対象外（`wontfix`） |
| `one_off` 再現しない | たまたまの誤り | 記録だけ残す | 対象外（`wontfix`） |

### 変換のルール

1. **文章ルールは1回目から試用にしてよい。** 試用ルールは軽く、定着させるかは後で決められます。
2. **ガード・検証コマンド・Skillは、同じ `cause_key` が2回起きてから。** 作業を止めたり手順を変えたりするので、慎重に足します。`forbidden` と `severity: high` だけは1回で足します。
3. **1つの失敗票につき、変換は1つ。** 複数を同時に足すと、どれが効いたか分からなくなります。
4. **追記より置き換え。** 既存のルールを書き換えて済むなら、そうします。
5. **文章ルールは「命令形1行＋失敗票ID」。** 例：`- ルート定義は src/routes/ に置く（INC-2026-0007）`。試用ルールと、自分専用のルールが、この形です。
6. **エラー文には直し方を書く。** 例：`routes から db を直接importしています。services/ 経由にしてください`
7. **チームへ出すものには、失敗票IDを付けない。** リポジトリのファイル（`.claude/rules/`、`harness/guards.json` の `message`、コミットメッセージ）にIDを書いても、失敗票はその人の手元にしかなく、チームのほかの人はたどれません。別の人のIDと番号がぶつかることもあります。チームへ昇格するとき、移した先のファイルにIDが残っていれば、`harness-note promote` が断ります。
8. **足す前に矛盾を確かめる。** 矛盾する2つのルールがあると、Claudeはどちらかを任意に選ぶことがあります（[Memory](https://code.claude.com/docs/en/memory)）。

ルール2には例外が1つあります。自動改善が置く試用Skillは、候補が2件重なった時点で置けます。中身が文章だけで、人が確認して消せるためです（4章）。

### 禁止操作の定義（4か所）

禁止操作の定義は、4か所から読み、**すべて効かせます**。あとのファイルが、前のファイルのルールを上書きすることはありません（足し算だけです）。Bashのパターンのルールも、書き込み先のパスのルールも、当たったものをすべて判定に通し、**拒否が1つでもあれば拒否**にします（確認より拒否が勝ちます）。2.0.1 までは、パスのルールは最初に当たった1件しか見ていなかったので、共通リストの `.env` の確認が先に当たり、user 側やリポジトリの `.env` の拒否が効きませんでした。

| 置き場所 | 効く範囲 | 誰が決めるか | 拒否の記録に残る名前 |
| --- | --- | --- | --- |
| 共通リスト（プラグインに同梱の `guards.default.json`） | すべてのリポジトリ | プラグイン | `default` |
| `~/.claude/self-improve/guards.json` | すべてのリポジトリ（その人だけ） | その人 | `user` |
| `~/.claude/self-improve/repos/<名前>/guards.json` | そのリポジトリ（その人だけ） | その人 | `user-repo` |
| リポジトリの `harness/guards.json` | そのリポジトリ（self-improve を入れているチームの全員） | チーム | `repo` |

- **共通リスト**：どのリポジトリでも止めたい操作です（`git push --force`、フックを飛ばすコミットなど）。失敗票からの変換先にはしません。
- **user 側の2つ**：その人だけの禁止操作です。失敗票からの変換は、まずここに書きます（ほかの人に影響せず、チームの合意も要りません）。
- **リポジトリの `harness/guards.json`**：チームで合意した禁止操作です。コミットして共有します。失敗票IDは書きません。

拒否と確認の記録（生ログ）には、どのファイルのルールだったか（上の名前。プラグインに組み込みの判定は `builtin`）を残します。「なぜ止まったのか」を、あとから4か所のどれかまでたどれるようにするためです。いま読まれているファイルは、`harness-note status` に出ます。

共通リストに入れているのは4つです。誤検知すると作業を止めるので、数を絞っています。**共通リストの中身は、1.x から変えていません。**

| ルール | 扱い | 当てる範囲 |
| --- | --- | --- |
| force push | 拒否 | `--force`、`-f`、`+refspec`。`--force-with-lease` は通す |
| フックを飛ばすコミット | 拒否 | `git commit` の `--no-verify` と `-n`。`n` を含む短いオプションのまとまり（`-nm`、`-anm`、`-nS`、`-vn`）も当てる。`-m "-n"` のように、メッセージの値が `-n` のものと、値をとるオプションのあとの `n`（`-uno`）は当てない |
| `.env` への書き込み | **確認**（`ask`） | `.env` と `.env.<環境名>`（`.env.local`、`.env.production`、`.env.qa` など。環境名は問わない）。`.env.example`・`.env.sample`・`.env.template`・`.env.md`・`.env.bak` などと、`chmod` は対象にしない。読むだけ・読み込んで起動するだけなら通す |
| ルートやホームを丸ごと消す `rm -r` | 拒否 | 引数のどれかがルートかホームなら当てる（`rm -rf build ~` も） |

`.env` を拒否ではなく確認にするのは、`cp .env.example .env` のような初期設定を、ルールごと外さずに通せるようにするためです。無人のセッションでは、確認が出ると止まるので、安全側に倒れます。

**Bashのコマンドの読み取り**：コマンドを区切り（`;`、`&&`、`|` など）ごとに分け、引用とヒアドキュメントを意識して読みます。読み取りがずれると、禁止リストが隠れます（引用の中の `<<EOF` をヒアドキュメントの始まりと読むと、次の行のコマンドを本文として読み飛ばす、など）。逆に、読み取れない部分を大づかみに扱うと、誤って止めます。

- **コマンド置換（`$(…)`）は、二重引用の中のものも、中身を読む。** `$(` の閉じを、引用・入れ子・バッククォート・ヒアドキュメント・コメントを読み飛ばして探し、中身を別のコマンドとして同じように読みます（入れ子は4段まで）。置換を含む語は、1語のまま扱います。Claude Code標準のHEREDOC形式のコミット（`git commit -m "$(cat <<'EOF' … EOF)"`）が、これに当たります。
- **コマンドの全文に禁止リストを当てるのは、読み取りに自信がないときだけ。** 読み取れなかった書き方（`case` を含む置換、深すぎる入れ子、閉じていない引用、区切りが単純でないヒアドキュメントなど）があるときは、区切ったあとの形に加えて、全文にも当てます。読み取れているときは、当てません。1.0.0 では、コマンド置換があるだけで全文に当てていたので、HEREDOC形式のコミットのあとに `git log -n 3` が続くと、`commit` と `-n` が全文の中で並んで、`--no-verify` として誤って拒否していました。
- **置換を含む語があるセグメントは、置換を中身の文字列に戻した形にも当てる。** 置換を含む語は `$(…)` という置き場所の文字になり、中身は別のコマンドとして読むので、外側のコマンドの引数を置換で作ると（`git push $(echo --force) origin main`、バッククォート、二重引用の `"$(…)"`）、どの形にも `git push … --force` が現れません。2.0.0〜2.0.1 では、これで共通リストをすり抜けられました（1.x の全文照合では止まっていたので、後退でした）。そこで、置換を中身に戻した形（`git push echo --force origin main`）も照合の対象に足します。ただし、コミットメッセージの値（`-m`・`--message`・`-F`・`--file` と、`-am` のようなまとまりの値）に当たる語は戻しません。HEREDOC形式のコミットの本文（`--no-verify` や `-n` と書いてあってもよい）で、誤って止めないためです。

ガードの定義のファイルが読めないとき（JSONの書き間違いなど）は、**そのファイルのガードだけ**が効かなくなります（ほかの3か所は効きます）。黙って外れないよう、整合チェック（`check.mjs`）とセッション開始時に、直すまで知らせます。

ルールは2種類で、どちらも `id` と `message`（直し方を1行）が要ります。`decision` に `ask` を書くと、拒否ではなく確認にできます（省略時は拒否）。書き方は、user 側の2つとリポジトリのファイルで同じです。

```json
{
  "disable_defaults": [],
  "protect": [],
  "rules": [
    { "id": "no-generated-edit", "path": "^src/generated/", "message": "src/generated/ は手で編集しません。スキーマを直して生成し直してください" },
    { "id": "no-prod-db", "pattern": "\\bpsql\\b.*prod", "message": "本番DBには書き込みません。検証環境で確かめてください" }
  ]
}
```

- `path`：書き込み先のパス（リポジトリの根からの相対パス）に当てる正規表現です。Write・Edit のほか、Bashで書き換えると分かるコマンドにも効きます。`except` で例外を書けます。
- `pattern`：Bashのコマンドに当てる正規表現です（配列で複数書けます）。区切りごとに分けたコマンドに、空白を含む引用（コミットメッセージなど）を伏せてから当てます。`bash -c` や `eval` の中身も調べます。
- `disable_defaults`：共通リストのルールを外すときに `id` を書きます。**書けるのは、user 側の2つのファイルだけです。** リポジトリの `harness/guards.json` に書いても、外しません（書いてあれば、知らせます）。リポジトリのファイルは、プルした変更で変わります。他人の変更で、その人の禁止リストが外れないようにするためです。
- `protect`：書き込みに確認を挟むパスを足します（7章）。user 側の2つと、リポジトリのファイルのどれにも書けます。

変換先を共通リストにすると、別のリポジトリ（`claude-code`）を変更することになります。複数のリポジトリで同じパターンが出たときは、まず user 全体のファイル（`~/.claude/self-improve/guards.json`）に置きます。誰にとっても止めるべきものだと分かったら、人がプラグインの共通リストへ手で移します。

## 6. 効果の確かめ方

エージェントを再生して失敗を再現する確認は行いません。制御の種類ごとに、安く確実な方法で確かめます。

再生をやめた理由は3つです。

- **再現しにくい。** 発生率30%の失敗は、3回再生しても2回以上失敗する確率が約22%しかありません。人の訂正は会話の途中で起きるので、最初の依頼文だけでは同じ状況になりません。
- **危険。** 禁止操作の失敗を、ガードを外して再生すると、`git push --force` のような操作が本当に実行されます。
- **重い。** 1回の確認に何回もエージェントを走らせる時間と費用は、個人の開発には見合いません。

| 制御の種類 | 確かめ方 | いつ |
| --- | --- | --- |
| ガード | hookの入力JSONを `guard-harness.mjs` に直接渡すテスト。エージェントも実際のコマンドも動かさない | 足すときと、プラグインを更新したとき |
| 検証コマンド、lint | 問題のある状態で1回実行し、実際に失敗することを見る | 足すとき |
| 文章ルール、Skill | 確かめる手段は持たない。同じ `cause_key` の失敗票がまた出たかどうかで見る | 昇格と棚卸しのとき |

### ガードのテスト

テストケースは、ガードの定義と同じ場所の `guards.test.json` に置き（user 全体、user のリポジトリごと、リポジトリの `harness/` の3か所）、`test-guards.mjs` で実行します。共通リストのテストケースはプラグインの `guards.default.test.json` にあり、同じコマンドで一緒に実行されます。

- 共通リストのテストは、空のリポジトリと、空の user 側の設定で実行します。利用者のガードや除外（`disable_defaults`、`exclude`）に、結果が左右されないようにするためです。
- 自分で足したテストケースは、実際の設定のまま、引数で渡したリポジトリ（省略時は、いまの場所）で実行します。そのリポジトリで効く3か所のテストケースを、すべて実行します。ほかのリポジトリ用のテストケースは実行しません。
- テストの実行は、何も記録しません（拒否の記録も残しません）。

`expect` は `deny`（拒否）、`ask`（確認）、`allow`（通す）のどれかです。

```json
[
  { "name": "force push を止める", "tool": "Bash", "input": { "command": "git push --force origin main" }, "expect": "deny" },
  { "name": "通常の push は通す", "tool": "Bash", "input": { "command": "git push origin feature/x" }, "expect": "allow" }
]
```

ガードを1つ足すときは、「止めるべき入力」と「止めてはいけない入力」を1件ずつ足します。止める側だけを確かめると、止めすぎるガードに気づけません。

### 文章ルールの見方

文章ルールには「効いた」を直接示す信号がありません。さらに、失敗が月に1回程度なら、ルールがなくても数週間は再発しないのが普通です。そのため「しばらく再発しなかった」は効果の証拠になりません。

見られるのは逆向きの事実だけです。ルールを置いたあとに同じ `cause_key` の失敗票が出たら、そのルールは効いていません。1回目の再発では文言を直してもかまいません。2回目からは文章を直すのではなく、ガードや検証コマンドへ移します（原則2、4章）。

## 7. 承認とガバナンス

ハーネスの変更はローカルに直接反映し、定着させる前に人が中身を確かめます。定着の行き先は、自分専用（user 側）とチーム（リポジトリ）の2つです。PRを使うモードは、複数人で共有するリポジトリ向けの拡張として付録に回します（13章）。

### 誰が書くか

書き込みは、「`harness-note` が自分で書くもの」と「Claudeが、人の確認を通して書くもの」に分けます。前者は、置き場所と中身をコマンドの側で決めて検査できるもの。後者は、人が差分を見て決めるべきものです。

| 変更の種類 | 置き場所 | 扱い |
| --- | --- | --- |
| 改善候補、試用ルール、試用Skill、失敗票の下書き、自動改善の記録 | プラグインのデータ領域、`~/.claude/skills/` | `harness-note` コマンドだけが書き込む。書き込むときに、置き場所と中身を検査する。ほかの手段での書き込みは、ガードが拒否する |
| 失敗票の起票・更新 | `~/.claude/self-improve/incidents/` | `harness-note incident add` / `set` が書き込む（人だけの操作）。Write・Editでの書き込みには、確認を挟む |
| 自分専用のルール（昇格） | `~/.claude/self-improve/repos/<名前>/rules.md` | `harness-note promote` が1行足す（人だけの操作）。手で直すときは、確認を挟む |
| user の設定、リポジトリごとの上書き、自分のガードとテストケース | `~/.claude/self-improve/` の下 | `harness-note` は書かない（`init` が最初に作る user の設定だけが例外）。Claudeが書くときは、差分を見せ、承認を得る |
| user のCLAUDE.md（好みを足すとき） | `~/.claude/CLAUDE.md` | 差分を見せ、承認を得る |
| `harness-note` の許可ルール | `~/.claude/settings.json` | 差分を見せ、承認を得る（`init`） |
| `.claude/rules/` への書き込みと削除（チームへの昇格を含む） | リポジトリ | 差分を見せ、承認を得る |
| CLAUDE.md、`.claude/skills/`、リンター設定 | リポジトリ | 差分を見せ、承認を得る |
| `harness/config.json`（検証コマンド）、`harness/guards.json`、`harness/guards.test.json` | リポジトリ | 差分を見せ、承認を得る |
| 検証コマンドの実行の許可 | `~/.claude/self-improve/repos/<名前>/verify-trust.json` | `harness-note verify trust` が、実行するコマンドの一覧を出してから記録する（人だけの操作）。呼び出しには、ガードが確認を挟み、一覧を見せる（9章） |
| `.git/commondir`、worktreeの `.git` のファイル、`.git/config` | リポジトリ（`.git` の中） | 確認を挟む（gitコマンド自身の書き込みは対象外） |
| プラグイン自身のファイル | プラグイン | 拒否する |

「承認を得る」は、Skillの指示だけに任せません。`guard-harness.mjs` が `PreToolUse` で `permissionDecision: "ask"` を返し、対象パスへの書き込みには必ず確認が出るようにします（[Hooks reference](https://code.claude.com/docs/en/hooks)）。Bashで対象パスに触れるコマンド（`sed -i`、リダイレクト、`mv`、`rm` など）も同じ扱いにします。

**user 側**で確認を挟むのは、`~/.claude/self-improve/` の下のすべてと、`~/.claude/CLAUDE.md` です。

- `~/.claude` の下への書き込みには、Claude Code自身も確認を出すとされています（[Permission modes](https://code.claude.com/docs/en/permission-modes)）。それでも、このプラグインの側でも確認を返します。Claude Codeの確認が、モードや設定で出ない場合の備えです（実機の確認待ち。14章）。
- **書き方の違いで、すり抜けさせない。** `~`、`$HOME`、`${HOME}` を展開してから比べます。パスの比較は、大文字小文字を区別しません（区別しないファイルシステムで、`.CLAUDE/Self-Improve/` が同じ場所を指すため）。
- `~/.claude/settings.json` は、このプラグインの確認の対象にしていません（Claude Code自身の確認に任せます。ほかの用途の書き込みが多いためです）。

**リポジトリ側**で確認を挟むのは、次のものです。1.x と同じですが、`init` したリポジトリだけでなく、すべてのgitリポジトリで効きます。

- CLAUDE.md は、リポジトリのどの階層のものも対象にします（`CLAUDE.local.md` を含む）。パスの比較は、大文字小文字を区別しません（区別しないファイルシステムで、`CLAUDE.MD` が同じファイルを指すため）。
- リンター設定は、名前で分かる専用のファイル（`eslint.config.*`、`.eslintrc*`、`biome.json`、`ruff.toml`、`.rubocop.yml`、`.golangci.yml` など）を対象にします。`package.json` や `pyproject.toml` のように、ほかの用途と兼ねるファイルは対象にしません。足りない分は、ガードの定義の `protect` にパスの正規表現を書いて足します。
- Bashで見るのは、リダイレクト先と、書き換えると分かっているコマンド（`sed -i`、`perl -i`、`tee`、`cp`、`mv`、`rm`、`touch`、`git checkout`・`restore`・`rm`・`mv` など）の引数です。`git add` と `git commit` は対象にしません（承認したあとのコミットを止めないため）。
- プラグインのデータ領域と試用Skillへの直接の書き込み（`harness-note` を通さないもの）は、プラグイン自身のファイルと同じく拒否します。自分専用へ昇格したSkillは、試用ではないので、拒否しません（ふつうのファイルとして直せます）。
- **gitの、リポジトリの場所を決めるファイル**（`.git/commondir`、`.git/worktrees/<名前>/commondir`、worktreeの `.git` のファイル）と `.git/config` への、Write・Editと、Bashで書き換えると分かっているコマンドの書き込みには、確認を挟みます（`.git` そのものの `rm`・`mv` も）。共通ディレクトリの場所は、リポジトリIDと `exclude` の判定に使うためです（3章）。worktreeでは、`gitdir` がリポジトリの外（本体の `.git/worktrees/` の下）にあるので、共通ディレクトリからの相対パスでも見ます。ほかの `.git/` の下と、`git config` のようにgit自身が書くものは、対象にしません（gitが日常的に書くため）。

**書き込み先は、リンクの名前と実体の両方で判定します。** どちらかが保護の対象なら、確認（または拒否）にします。

- `CLAUDE.md` が `AGENTS.md` へのシンボリックリンクなら、`AGENTS.md` への書き込みは、CLAUDE.md を書き換えます。実体（`AGENTS.md`）を指す書き込みにも、確認を挟みます（リポジトリの根と、書き込み先の親ディレクトリにあるリンクを調べます）。
- リンクを通した名前（`~/skills-link/…` が `~/.claude/skills/…` を指す、など）で、試用Skillやデータ領域に書こうとしても、実体のパスで拒否します。
- user 側の置き場所がリンクのとき（dotfilesで管理している、など）は、リンクの名前でも、実体のパスでも、確認を挟みます。
- 生ログには、リポジトリの中のパスは相対パスで、外のパスはホームを `~` に置き換えて残します。

この守りには限界があります。Bash経由の書き込みをすべて見分けることはできません（スクリプトの中からの書き込み、ワイルドカードで指した書き込みなど）。防げるのはうっかりや近道であって、意図的な回避ではありません。

自動改善のセッションでは、確認ではなく拒否にします（4章）。スケジュール済みタスクは確認が出ると止まって待つので、確認そのものを出さないようにするためです。自動改善を呼び出したセッションは、ロックが外れたあとも、書き込みに確認を挟みます（4章）。

### 試用から昇格まで

1. 新しい文章ルールは、試用として置きます。置き場所はプラグインのデータ領域で、セッション開始時のhookがClaudeのコンテキストに読み込ませます（4章）。人が `retro` で入れるときも、自動改善が入れるときも同じです。
2. 昇格は日数で自動判定しません。人が好きなときに行います。判断の材料は、置いてからの日数と、同じ `cause_key` がまた出たかどうかです。
3. 昇格するとき、人が**行き先**を選びます。

| 行き先 | 置き場所 | 効かせ方 | ほかの人への影響 |
| --- | --- | --- | --- |
| 自分専用（`--to personal`） | ルールは `~/.claude/self-improve/repos/<名前>/rules.md`。Skillは、いまの場所（`~/.claude/skills/<リポジトリ名>-<名前>/`）のまま | ルールは、**そのリポジトリのセッション開始時に**、試用ルールと同じ経路で読み込ませる。Skillは、Claude Codeが個人用のSkillとして読み込む | ない |
| チーム（`--to team`） | リポジトリの `.claude/rules/`、`.claude/skills/` | Claude Codeが読み込む | チームの全員に効く。コミットする |

4. 試用は期限で自動削除しません。60日（初期値）を超えたものは、自動改善の報告と棚卸しの両方に載せ、「昇格する（自分専用かチームへ）／残す／消す」を尋ねます。

**昇格は `harness-note promote --key <原因キー> --to personal|team` で行います**（人だけの操作）。未確認の試用も、確認済みの試用も、見直しの時期が来た試用も、同じコマンドで昇格できます。昇格すると、その原因の未確認の変更は確認済みになります。

- **自分専用（ルール）**：自分専用のルールのファイルに、試用ルールと同じ形の1行（`- <命令形1行>（失敗票ID）`）を足し、試用ルールを消します。ファイルは、`- ` で始まる行が1行で1つのルールです。人が手で直せます。読み込むときに、試用ルールと同じ中身の検査をし、通らない行は読み込まずに知らせます。
- **自分専用（Skill）**：置き場所も中身も変えません。印のファイルに、昇格した日時（`promoted_at`）を書くだけです。それ以降は、試用として扱いません（件数の上限にも、見直しにも数えません。`harness-note skill remove` でも消しません）。**ガードも、編集を止めません。** 試用のあいだは `harness-note` 以外から書けませんが、昇格したものは、その人のふつうのSkillです。
- **チーム**：人が先に、リポジトリのファイルへルールやSkillを書きます（確認が出ます）。そのあと `--path <移した先>` を付けて呼びます。`harness-note` は、**試用を消す前に、移した先を確かめます**。リポジトリの中にあること、ファイルがあること、空でないこと、失敗票ID（`INC-…`）が書かれていないこと、の4つです。確かめられなければ、試用は消しません。移し忘れたまま試用だけが消えると、決まりそのものがなくなるためです。
- **失敗票**：その原因の失敗票があれば、`converted` にして、`control` に行き先を、`promoted_at` に日付を入れます。失敗票は、`--incident` で指定するか、試用ルールに付いている失敗票IDから決めます。別のリポジトリの票は、書き換えません。

自分専用を用意した理由は、共有リポジトリで使うためです。行き先がチームしかないと、見直しの時期が来た試用は「チームのリポジトリにコミットする」か「消す」しか選べません。自分にだけ効かせたい決まりは、消すことになります。

試用ルールを `.claude/rules/` の下に置かない理由は2つあります。`.claude` 配下への書き込みには確認が出るので、無人では書けません。また、git管理外のファイルはworktreeに届きません。自分専用のルールを、リポジトリの `CLAUDE.local.md` ではなく user 側に置くのも、同じ理由です（worktreeに届かず、リポジトリの中にファイルが増えます）。

そのかわり、セッション開始時に読み込ませた内容が、会話の圧縮のあとも残るかを確かめる必要があります。圧縮や再開のときにも読み込み直すようにします（9章）。

ガードと検証コマンドに試用はありません。作業を止める制御なので、最初から承認を通します。Skillは、自動改善が作るものに限り試用として置き、人が作るものは承認を通します。

### 守ること

- **チームへ出す変更は、1変換に1コミット。** 問題が出たら、そのコミットだけをrevertします。コミットメッセージには、何を足したかを書きます（例：`harness: ルートの置き場所のルールを追加`）。失敗票IDは書きません（5章のルール7）。自分専用の変更は、リポジトリの外にあるので、コミットはありません（取り消すときは、その行やファイルを消します）。
- **整合チェックは警告だけ。** `check.mjs` はコミットを止めません（終了コードはいつも0）。調べるのは、今のリポジトリの分だけです。試用ルールと自分専用のルールが指す失敗票が実在するか、失敗票の `status` と `control` が食い違っていないか（`control` の指す先があるか）、self-improve が読み込ませる行数が目安を超えていないか、の3つです。あわせて、設定とガードの定義（4か所）が読めるかも見ます。リポジトリのCLAUDE.mdや `.claude/rules/` は調べません（チームのもので、self-improve が足したものではないためです）。結果はセッション開始時の通知（同じ内容は、閉じるか7日たつまで。読めないガードの定義と設定は、直すまで毎回）と、`retro`・`review`・`harness-prune` の実行時に出します。
- **全体を止めるスイッチ。** 環境変数 `HARNESS_DISABLE=1` を付けて起動すると、プラグインのhookはすべて何もしません。ハーネス自身が作業を妨げたときの逃げ道です。そのリポジトリでずっと止めるなら、`exclude` に書きます（3章）。

ローカルでの承認の弱点は、作業中のセッションの中で行われることです。差分を流し読みで通すと、承認が形だけになります。棚卸し（8章）を、承認済みのルールを見直す2つ目の関門として扱います。

## 8. 棚卸し（任意）

この章は未実装です（11章のステップ4）。`harness-prune` スキルも、Skillの呼び出しとルールの読み込みの記録も、まだありません。行数の目安だけは `check.mjs` と自動改善の歯止めで使っています。

棚卸しは、使われていないものを一覧にして、残すかどうかを人が決める作業です。自動では消しません。やらなくてもハーネスは動き続けます。

### 何を見て判断するか

制御の種類によって、読める信号が違います。

| 対象 | 読める信号 | 一覧に出す条件 |
| --- | --- | --- |
| Skill | 呼び出し回数 | 90日間、一度も呼ばれていない |
| ガード、検証コマンド | 発火回数 | 90日間、一度も発火していない |
| paths付きのルール | 読み込み回数（ファイル単位） | 90日間、一度も読み込まれていない |
| 常時ロードの文章ルール（自分専用のルール、CLAUDE.md、pathsなしのルール） | なし | 置いてからの日数と、同じ `cause_key` の再発の有無を並べて出す |
| 試用ルール | 置いてからの日数 | 60日を超えた |

常時ロードの文章ルールは毎回読み込まれるので、「使われていない」を示す信号がありません。ここだけは材料を並べて、人が判断します。

発火していないガードは「問題が起きていない」のか「検出できていない」のか、記録だけでは区別できません。Böckeler氏も未解決の問いとして挙げています。禁止操作のガードは、発火がなくても残すのを基本にします。

### 手順（`/self-improve:harness-prune`）

1. 上の表の条件に当たるものを一覧にします。
2. 重複しているルール、矛盾しているルール、リンターが既に見ている規約を書いたルールを挙げます。
3. 同じ `cause_key` の失敗票が増え続けている文章ルールを、ガードや検証コマンドへ移す候補として挙げます。
4. それぞれについて、人が「残す／消す／移す」を選びます。
5. 選んだ内容を、1件ずつ差分を承認して反映します。消した制御の失敗票は `status: retired` にします。
6. 一覧と結果をレポートに書き出します。置き場所は、棚卸しを作るときに決めます（1.x の設計ではリポジトリの `harness/reports/` でしたが、個人の記録をリポジトリに置かない2.x の考え方に合わせて、user 側かデータ領域にする見込みです）。

生ログはマシンごとのプラグインのデータ領域にあり、プラグインをアンインストールすると消えるとされています。集計をレポートに書き出すのは、その備えです。

### 行数の目安

数えるのは、**self-improve が足して、毎回読み込ませている分だけ**です。

| 対象 | 目安 | 補足 |
| --- | --- | --- |
| 試用ルール＋自分専用のルール（そのリポジトリの分） | 50行（`budget.always_loaded_rule_lines`） | セッション開始時に必ず読み込ませるので、CLAUDE.mdと同じ重さ |

目安を超えても作業は止めません。`check.mjs` が警告を出し、昇格（チームへ）か削減を勧めるだけです。自動改善は、この目安を超えるとき、試用ルールの追加を見送ります（4章の「歯止め」）。

1.x では、リポジトリのCLAUDE.md（100行）、pathsなしのルールの合計（50行）、paths付きルール1ファイル（50行）も数えていました。2.x では数えません。チームのルールは、その人が減らせるものではなく、チームのルールが長い共有リポジトリで、警告が出続け、自動改善が止まったままになるためです。チームのルールを減らす手段（paths付きルールとSkillsへ逃がす。`@import` で分割しても、起動時に読まれるのでコンテキストは減らない（[Memory](https://code.claude.com/docs/en/memory)））は、チームで決めます。

読み込ませる量には、もう1つ上限があります。hookがコンテキストに渡せる量の都合で、ルールは合わせて6,000文字までしか読み込ませません。入らなかった分は、黙って切らずに、件数を知らせます（4章）。

### 通知

棚卸しの間隔は、設定の `prune.interval_days` に日数で書きます（初期値30日。いまは使われません）。前回のレポートから間隔を過ぎると、セッション開始時に知らせます。0にすると通知も出ません。

実行済みとして数えるのは、人が選んだ結果を書いたレポートだけです。候補の一覧だけを書き出したレポート（13章）は数えません。

## 9. 実装構成

仕組みはプラグイン側に置きます。データは4か所に分かれます。その人の設定・失敗票・自分専用のルール・自分のガードは user 側（`~/.claude/self-improve/`）、試用と記録はプラグインのデータ領域、Skill（試用と自分専用）は個人用のSkillの置き場所、チームに効かせるものだけが適用先のリポジトリです。

### プラグイン（`claude-code` リポジトリ）

```text
plugins/self-improve/

├── SCHEDULING.md           # 自動改善と棚卸しを日時で動かす手順（未検証）
├── DESIGN.md               # この設計書
├── .claude-plugin/plugin.json   # 名前、説明、版（version）
├── package.json            # テスト用（node --test）。外部の依存パッケージはない
├── hooks/hooks.json
├── guards.default.json     # 共通の禁止リスト（初期値）
├── guards.default.test.json # 共通の禁止リストのテストケース
├── bin/

├── scripts/
│   ├── note.mjs            # harness-note の中身
│   ├── log-event.mjs       # 信号を生ログに1行追記する

│   ├── verify.mjs          # リポジトリの harness/config.json の verify を実行する（時間切れのときは、子孫のプロセスごと止める）

│   ├── guard-harness.mjs   # 禁止操作を拒否し、ハーネスのファイルへの書き込みには確認を挟む。自動改善のセッションでは、通すツールを一覧で絞る。することがなければ、すぐ抜ける
│   ├── session-start.mjs   # 試用ルールと自分専用のルールを読み込ませ、自動改善の結果などを報告する。1日1回、掃除する

│       ├── bash.mjs        # Bash のコマンドの読み取り
│       ├── trial.mjs       # 試用ルール、試用 Skill、自分専用のルール、行数
│       ├── content.mjs     # ルールと Skill の中身の検査
│       ├── candidates.mjs  # 改善候補（好みの候補は user 単位）
│       ├── auto.mjs        # 自動改善の状態、未確認の変更、確認、昇格

│   ├── auto-improve/SKILL.md   # 日時起動で候補を検討し、試用として追加・編集する
│   ├── review/SKILL.md         # 自動変更を1件ずつ確認し、昇格（自分専用かチームへ）する
│   └── retro/SKILL.md          # 人が始める振り返り
├── templates/              # user の設定（config.json）、リポジトリの設定（repo-config.json。verify だけ）、ガード、失敗票のひな形
└── tests/                  # node --test のテスト
```

`harness-prune` スキル（棚卸しの一覧を出し、選んだ内容を反映する）は、ステップ4で足します。まだありません。

スクリプトはNode.jsの標準機能だけで動きます（Node.js 22で確認）。外部の依存パッケージは使わず、ネットワークにも出ません。

スキルはプラグイン名を付けて呼びます（例：`/self-improve:retro`）。

### `harness-note` コマンド

リポジトリの外にあるデータ（プラグインのデータ領域、試用Skill、失敗票、自分専用のルール）は、このコマンドが読み書きします。置き場所と中身の検査を、1か所に集めるためです。**設定とガードの定義は、このコマンドでは書きません**（人が差分を見て決めるものなので、Claudeが確認を通して書きます。7章）。

self-improve が動かない場所（gitリポジトリでない、除外してある、`HARNESS_DISABLE=1`）では、どのサブコマンドも「ここでは使えません」と理由を返し、何も書きません。user の設定が読めないあいだは、候補の記録（`add`）を「記録しません」と返します。

| サブコマンド | すること | 使う場面 |
| --- | --- | --- |
| `add`、`keys`、`list` | 改善候補の記録、原因キーの一覧、候補の一覧 | ターン終了時、確認のとき |
| `mark`、`rekey` | 候補を `consumed`・`rejected` にする。似た原因キーをまとめ直す | `retro`、`review` |
| `episodes <原因キー>` | その原因の事象メモを出力する（`--id`、`--recent` でも引ける） | 自動改善、振り返り |
| `trial add`、`trial edit`、`trial remove`、`trial list` | 試用ルールを書く。置き場所は固定で、行数と中身を検査する | 自動改善、`retro`、`review` |
| `skill add`、`skill remove`、`skill list` | 試用Skillを `~/.claude/skills/` に書く。設定欄と中身を検査する | 自動改善、`review` |
| `pending add`、`pending list`、`pending show`、`pending remove` | 失敗票の下書きを書く・読む・捨てる。`add` は材料にした候補を `consumed` にする | 自動改善、`review` |
| `report write`、`report list`、`report show` | 実行の記録を書く・読む | 自動改善、`review` |
| `report close` | セッション開始時の知らせ（報告の1行、1回きりの知らせ、user 単位の知らせ）を閉じる。自動改善のセッションからは閉じられない | 人に頼まれたとき |
| `incident add`、`incident set` | 失敗票を起票する・更新する（user 側に置く。人だけの操作）。`add --from-draft` は、下書きの値を引き継いで起票し、下書きを捨てる | `retro`、`review` |
| `incident list`、`incident show` | 失敗票の一覧（今のリポジトリの分。`--all` で全リポジトリ）と中身 | `retro`、`review` |
| `incident import` | 1.x の失敗票（リポジトリの `harness/incidents/`）を user 側へ取り込む（人だけの操作）。出力に、取り込み元のリポジトリの名前を出す | 1.x からの移行 |
| `verify`、`verify trust` | リポジトリの検証コマンド（`harness/config.json` の `verify`）の一覧と、実行を許可しているか。`trust` は、一覧を出してから、いまの中身を許可したと記録する（人だけの操作。セッションが推定のときも見送る） | `init`、`retro`、`review`、セッション開始時の知らせのあと |
| `promote` | 試用を、自分専用（`--to personal`）かチーム（`--to team --path <移した先>`）へ昇格する（人だけの操作）。チームのときは、移した先を確かめてから試用を消す | `review` |
| `lock`、`unlock` | 自動改善のセッションを登録・解除する。`lock` は間隔を確かめ、対象を決める。`unlock` は、`report write` のあとだけ受け付ける | 自動改善 |
| `targets`、`status` | 自動改善の対象になる原因キーと、歯止めの状況を出す。データの置き場所とセッションの解決結果、読まれている設定とガードの定義のファイル、設定の誤りと注意を出す | 確認、動作の確かめ |
| `review`、`review done` | 未確認の自動変更を中身つきで並べる。確認の結果（keep / edit / remove / apply / dismiss）を記録する。昇格は `promote` で行う | `review` |

`mark`・`rekey`・`review done`・`report close` と、読み出し系（`list` の類、`targets`、`status`、`review`）は、1.x の実装で足したものです。`incident` と `promote` は、2.x で足しました（失敗票を user 側に一本化したことと、昇格の行き先が2つになったことによります）。1.x の `review done --decision promote` はなくし、`promote` に一本化しました（呼ぶと、`promote` を案内するエラーになります）。

セッションIDは `--session`、環境変数、直近に動いていたセッションの順に解決します。`--session` と環境変数が食い違うとき、`--session` を複数付けて違うIDを書いたときは、エラーにします。`lock`・`unlock` は、推定のIDでは受け付けません。`add` と `lock` は、hookが記録しているセッションのIDだけを受け付けます（4章）。テスト用の環境変数（現在時刻を固定する `HARNESS_NOW`、`~/.claude` の場所を差し替える `HARNESS_CLAUDE_HOME`、ガードの拒否を記録しない `HARNESS_GUARD_DRYRUN`）は、テスト用の印（`HARNESS_TEST=1`）があるときだけ読みます。ふだんも読むと、環境変数1つで、間隔やロックの失効を動かしたり、user 側の置き場所（`exclude`、`disable_defaults`、失敗票）をリポジトリの中へ向けたりできるためです。

- **書き込み先のパスは受け取らない**：どのサブコマンドも、置き場所を決める引数を持ちません。知らないオプション（`--allowed-tools` など）はエラーにします。`promote --to team` の `--path` は、書き込み先ではなく、人が書いたファイルを確かめるための引数です（リポジトリの中のファイルだけを受け付け、読むだけです）。
- **方針で書かなかったときはエラーにしない**：上限、重複、歯止め、自動改善のセッションでの `add` などで記録・追加しなかったときは、終了コード0で理由を返します（「記録しません」「見送り」）。中身の検査で断ったときと、使い方の誤りは、終了コード1です。`harness-note` の失敗は、ツールの失敗の信号には数えません。
- **長い文の渡し方**：下書きの各欄、Skillの本文、実行の記録は、値に `-` を指定すると標準入力（ヒアドキュメント）から読みます。
- **データの置き場所の渡し方**：ClaudeがBashから実行するコマンドには、`${CLAUDE_PLUGIN_DATA}` が渡らないとされています。そのため、次の順に解決します。前の手段が外れても、後ろの手段で動くようにするためです。
  1. 環境変数 `HARNESS_DATA_DIR`（セッション開始時のhookが `CLAUDE_ENV_FILE` に `export` を書いて引き渡す。テストでもこれで上書きする）。なければ `CLAUDE_PLUGIN_DATA`
  2. セッション開始時のhookがデータ領域に残す、引き渡しのファイル（`handoff.json`）。`~/.claude/plugins/data/` の下から探す
  3. 既定のパスの計算（`~/.claude/plugins/data/<プラグイン名>-<マーケットプレイス名>`。`--plugin-dir` で読み込んだときは `self-improve-inline`）
- **セッションを始めたリポジトリの渡し方**：ClaudeがBashから実行するコマンドには、`CLAUDE_PROJECT_DIR` も渡らないとされています。そのため、セッション開始時のhookが、セッションを始めたリポジトリの場所を `HARNESS_PROJECT_DIR` として、同じ手段（`CLAUDE_ENV_FILE`）で引き渡します。`harness-note` は、これを先に見てリポジトリを決めます（入れ子のリポジトリへ `cd` したあとに呼ばれても、もとのリポジトリのデータを読み書きするように。届かないときは、作業ディレクトリのリポジトリで決めます）。
- **セッションIDの渡し方**：`--session` で渡します。`Stop` のhookは記録のコマンドにIDを添えて頼み、スキルは本文に埋め込まれる `${CLAUDE_SESSION_ID}` を使います。渡らなかったときは、環境変数（`HARNESS_SESSION_ID`、`CLAUDE_CODE_SESSION_ID`）、直近に動いていたセッションの順に推定します。`harness-note status` で、どの手段で解決したかを確かめられます。
- **許可ルール**：`init` が、ユーザー設定（`~/.claude/settings.json`）に `Bash(harness-note *)` の許可ルールを足します（スクリプトは書かず、Claudeが確認を通して足します）。これがないと、候補を記録するたびに確認が出ます。user 単位の設定なので、どのリポジトリでも、スケジュール済みタスクのセッションでも効きます。各スキルの `allowed-tools` にも `Bash(harness-note *)` を書いてあります。
- **端末からは呼べない**：プラグインの `bin/` が通るのは、ClaudeのBashツールの中だけです。候補を見たいときは、Claudeに頼むか `/self-improve:review` を使います。

### user 側（`~/.claude/self-improve/`）

```text
~/.claude/
├── settings.json                  # harness-note の許可ルール（init が、確認を通して足す）
├── CLAUDE.md                      # 重なった好みを、人が確認して足す先
└── self-improve/
    ├── config.json                # user の設定（全リポジトリに効く。exclude もここ）
    ├── guards.json                # 自分のガード（全リポジトリ）
    ├── guards.test.json           # そのテストケース
    ├── incidents/INC-*.md         # 失敗票（全リポジトリの分。harness-note が書く）
    └── repos/<名前>/              # リポジトリごとの置き場所
        ├── config.json            # 設定の上書き（変えたい項目だけ）
        ├── guards.json            # 自分のガード（そのリポジトリだけ）
        ├── guards.test.json       # そのテストケース
        ├── rules.md               # 自分専用のルール（昇格先。harness-note promote が足す）
        └── verify-trust.json      # 検証コマンドの実行の許可（リポジトリIDごとに、許可した中身のハッシュ。harness-note verify trust が書く）
```

どのファイルも、なくても動きます（設定は初期値、ガードは共通リストだけ）。`init` スキルが作るのは、`config.json` と `incidents/` だけです。ほかは、要るときに作ります。

`<名前>` は、リポジトリのディレクトリ名をもとにした名前です（人が見て分かり、手で作れるように）。同じ名前のリポジトリが2つあると、置き場所を共有します。分けたいときは、`repos/<リポジトリID>/` を作れば、そちらを優先します。実際のパスは `harness-note status` に出ます。

`~/.claude` の下なので、ここへのWrite・Editには、Claude Codeの確認が出る前提で設計します（7章）。そのため、頻繁に書くもの（失敗票、自分専用のルールへの追記）は `harness-note` が書き、たまにしか書かないもの（設定、ガード）は、人の確認を通してClaudeが書きます。

### 適用先のリポジトリ

```text
<repo>/
├── CLAUDE.md                      # チームのもの。self-improve は行数を数えない
├── .claude/
│   ├── rules/*.md                 # チームへ昇格したルール
│   └── skills/<名前>/SKILL.md     # チームへ昇格したSkill
└── harness/                       # 要るときだけ。なくても動く
    ├── config.json                # 検証コマンド（verify）だけ
    ├── guards.json                # チームの禁止操作
    └── guards.test.json           # そのテストケース
```

**リポジトリには、チームに効かせると人が決めたものだけを置きます。** self-improve が動くために、リポジトリに要るファイルはありません。`init` スキルも、検証コマンドを使うと答えたときの `harness/config.json` のほかは、何も作りません。

### リポジトリの外

```text
~/.claude/
├── skills/<リポジトリ名>-<名前>/SKILL.md   # 試用Skill。自分専用へ昇格したSkillも、同じ場所のまま
└── plugins/data/<プラグインID>/            # プラグインのデータ領域
    ├── events/<リポジトリID>/              # 生ログ
    ├── episodes/<リポジトリID>/            # 事象メモ
    ├── candidates/<リポジトリID>/          # 改善候補
    ├── candidates/_user/                   # 好みの候補（user 単位）
    ├── trial/<リポジトリID>/rules/         # 試用ルール
    ├── pending/<リポジトリID>/             # 失敗票の下書き
    ├── reports/<リポジトリID>/             # 自動改善の記録
    ├── state/<リポジトリID>/               # 仕組みの状態（下記）
    ├── state/_user/state.json              # user 単位の状態（知らせを閉じたか、最後に掃除した日）
    └── handoff.json                        # harness-note への引き渡し
```

`state/<リポジトリID>/` には、仕組みが動くための状態を置きます。自動改善の状態（前回の実行、未確認の自動変更、断られた原因、再発の回数、昇格済みの原因、報告と知らせを閉じたかどうか、自動改善を呼び出したセッション）、ロック、hookが最後に動いた時刻、リポジトリの控え（`repo.json`。名前と場所。掃除のときに、開いていないリポジトリの保持期間を調べるのに使います）、セッションごとの一時的な状態（依頼文と応答を1ターン分、頼んだかどうかの印、検証の連続失敗回数）です。セッションごとの状態は、2週間で消します。

リポジトリIDは、gitの共通ディレクトリのパスから作ります（`<リポジトリ名>-<パスのハッシュ>`。`.git` を自分で読み、gitコマンドは呼びません）。worktreeでも同じIDになるので、試用と候補は共有されます。リポジトリを移動したり名前を変えたりすると、IDが変わって過去のデータから切り離されます（失敗票には、リモートのURLが残ります）。データ領域は、プラグインをアンインストールすると消えるとされています。user 側（`~/.claude/self-improve/`）は、残ります。

**掃除**：保持期間（`episode_retention_days`）を過ぎた事象メモ、生ログ、`new` のままの改善候補と、2週間を過ぎたセッションごとの状態は、セッション開始時（startup）に消します。**1日1回**だけ行い、**データ領域にある全リポジトリの分**をまとめて掃除します。

- すべてのリポジトリで動くので、セッションを始めるたびに掃除すると無駄が多いためです。最後に掃除した日を user 単位の状態に持ち、同じ日のうちは、どのリポジトリのセッションでも掃除しません（日付を先に書くので、同時に始まったセッションが二重に掃除することも避けられます）。
- しばらく開いていないリポジトリの記録も、保持期間で消えるようにするためです（リポジトリごとの掃除だと、開かないかぎり残り続けます）。
- 保持期間は、リポジトリごとの上書きがあれば、それに従います（リポジトリの控えから、そのリポジトリの設定を読みます）。
- user の設定が読めないあいだは、掃除もしません（保持期間が分からないためです）。

### 設定

設定は、次の順に重ねます（あとのものが、前のものを上書きします。`budget` や `auto` のような入れ子は、項目ごとに重ねます）。

| 順 | 層 | 置き場所 | 何を書くか |
| --- | --- | --- | --- |
| 1 | 初期値 | プラグインに組み込み | — |
| 2 | user の設定 | `~/.claude/self-improve/config.json` | 全リポジトリに効かせる値。`exclude` はここだけ |
| 3 | リポジトリごとの上書き | `~/.claude/self-improve/repos/<名前>/config.json` | そのリポジトリだけ変えたい項目 |

**リポジトリの `harness/config.json` から読むのは、検証コマンドの `verify` だけです。** ほかの項目が書いてあっても、読みません（セッション開始時に、「読みません。user 側へ移してください」と知らせます）。リポジトリのファイルは、共有されたり、プルで変わったりします。他人の変更で、その人の仕組みの動き方（自動改善の間隔や上限、保持期間）が変わらないようにするためです。`verify` だけは、「このリポジトリでは、何が通れば完了か」というリポジトリの性質なので、リポジトリに置きます。

user の設定（`~/.claude/self-improve/config.json`）：

```json
{
  "exclude": [],
  "trial_review_days": 60,
  "episode_retention_days": 90,
  "budget": {
    "always_loaded_rule_lines": 50
  },
  "candidates": {
    "min_sessions": 2,
    "preference_min_sessions": 3,
    "max_per_session": 3,
    "categories": ["dev/bug", "dev/cause", "dev/mistake", "dev/other", "behavior/preference"]
  },
  "auto": {
    "interval_days": 0,
    "max_per_run": 3,
    "max_unreviewed": 5,
    "max_trial_rules": 10,
    "max_trial_skills": 5
  },
  "prune": {
    "interval_days": 30
  }
}
```

| 項目 | 意味 |
| --- | --- |
| `exclude` | self-improve を止める場所（3章の「どこで動くか」）。絶対パスか `~/` で始まるパスの配列。user の設定にだけ書ける |
| `trial_review_days` | 試用を「見直し」として報告と棚卸しに載せるまでの日数 |
| `episode_retention_days` | 事象メモ、改善候補、生ログを残す日数 |
| `budget.always_loaded_rule_lines` | self-improve がセッション開始時に読み込ませる行数（試用ルール＋自分専用のルール）の目安。超えると警告する。自動改善は、超えるときは試用ルールを追加しない |
| `candidates.min_sessions` | 自動改善の対象にするまでの件数（異なるセッションの数）。好みの候補は `preference_min_sessions`（全リポジトリで数える） |
| `candidates.max_per_session` | 1つのセッションが、直近24時間に記録できる候補の上限 |
| `auto.interval_days` | 自動改善の間隔。0は停止（初期値）。有効にするときに7にする。前回の実行からこの半分がたつまでは実行せず、この日数を過ぎても実行されていなければ知らせる |
| `auto.max_per_run` | 自動改善が1回の実行で扱う候補の上限 |
| `auto.max_unreviewed` | 未確認の自動変更がこの件数に達したら、追加と編集をやめる |
| `auto.max_trial_rules`、`auto.max_trial_skills` | 試用ルールと試用Skillの上限 |
| `prune.interval_days` | 棚卸しの間隔（未実装。いまは使われない） |
| `correction_words`（任意） | 訂正語として足す言い回しの一覧 |

読めない層があるときの扱いは、層ごとに違います。

| 読めないもの | 扱い |
| --- | --- |
| user の設定（JSONでない、`exclude` が配列でない、`exclude` に解釈できない値がある） | **ガードは効かせたまま、記録と掃除を止める**（3章）。直すまで、セッション開始時に毎回知らせる。`exclude` の一部の値だけが解釈できないときは、正しく書けている値の除外は効かせる |
| リポジトリごとの上書き | その層を飛ばして動かす。セッション開始時に毎回知らせる |
| リポジトリの `harness/config.json` | 検証コマンドを動かさない。セッション開始時に毎回知らせる |

検証コマンド（リポジトリの `harness/config.json`）：

```json
{
  "verify": [
    { "name": "typecheck", "run": "pnpm tsc --noEmit" }
  ]
}
```

`verify` は、「壊れたまま完了と報告した」失敗が起きたときに1行ずつ足します。ファイルがなければ、検証は動きません。

コマンドはリポジトリの根で、上から順に実行し、最初の失敗で止めます。1つにつき240秒で打ち切ります（`timeout_sec` で変えられます）。`Stop` のhook全体の制限時間は900秒なので、時間のかかるコマンドを4つ以上並べると、途中で打ち切られることがあります。出力に失敗票ID（`INC-…`）があれば拾います。`node scripts/verify.mjs <リポジトリ>` で、ターンの外からも1回走らせられます。

**時間切れのときは、子孫のプロセスごと止めます。** コマンドは、新しいプロセスグループで起動し、時間切れになったら、グループ全体に終了のシグナルを送ります（Windowsでは `taskkill` でプロセスツリーを止めます）。シェルだけを止めると、シェルが起動したテストランナーやウォッチャーが残り、ポートやCPUを握ったままになるためです。hook自身が止められたとき（`Stop` のhook全体の時間切れ、Ctrl+C）も、実行中のコマンドのグループを止めてから終わります。

**検証コマンドは、人が許可した中身と一致するときだけ実行します**（2.0.2）。`verify` は、リポジトリのファイル（`harness/config.json`）に書かれたコマンドです。2.x では `init` が要らないので、クローンしただけのリポジトリにこのファイルがあれば、同意なしに、変更のあったターンの終わりに実行されてしまいます（2.0.1 まで）。Claude Code のフォルダーの信頼の確認も、このファイルを対象にしていません。そこで、初回だけ確認する方式にします。

- `verify` の内容を、実行する形（`name`・`run`・`timeout_sec`）にそろえたJSONのハッシュ（SHA-256）にし、`~/.claude/self-improve/repos/<名前>/verify-trust.json` に、リポジトリIDごとに記録します。記録と一致するときだけ実行します。同じ名前の別のリポジトリ（IDが違う）とは、許可を共有しません。
- 一致しないとき（初めて見る中身、プルなどで変わった中身）は、実行せず、セッション開始時に知らせます（中身ごとに1回きりの知らせ。閉じるか7日で消え、中身が変われば、また出ます）。知らせには、検証コマンドの名前と、許可のしかた（Claudeに「検証コマンドを許可して」と頼む。`harness-note verify trust`）を書きます。`node scripts/verify.mjs` で直接実行しても、許可がなければ実行しません。
- **許可は人だけの操作です。** 自動改善のセッション、ロックを試みたセッション、自動改善の実行中、セッションが推定のときは、「見送り」にします。許可のコマンドは、実行するコマンドの一覧を出してから記録します。さらに、ガードが、この呼び出しに確認を挟み、確認の文に実行するコマンドの一覧を載せます（許可ルール `Bash(harness-note *)` があっても、人が一覧を見てから決めるように。リポジトリの CLAUDE.md などに「`harness-note verify trust` を実行して」と書かれていても、黙って許可されないためです）。
- `init` で検証コマンドを使うと答えたときは、中身を見せたうえで、その場で許可を記録します。`retro`・`review` で検証コマンドを足したときも同じです。
- 1.x から上げた利用者のリポジトリでは、上げた直後に一度だけ許可を求めることになります（READMEの移行の手順に書きます）。
- 許可したあとも、コマンドが呼ぶ先（`npm test` が読む `package.json` の `scripts`、リポジトリの中のスクリプトなど）が変わることは、見ていません。ハッシュで見るのは `verify` に書かれた文字だけです（12章）。

### hooksの割り当て

| イベント | スクリプト | 動作 | 作業を止めるか |
| --- | --- | --- | --- |
| `SessionStart`（すべての種類。matcher は付けない） | `session-start.mjs` | 試用ルールと、そのリポジトリの自分専用のルールを、Claudeのコンテキストに読み込ませる。データの置き場所、セッションID、セッションを始めたリポジトリの場所を `harness-note` に引き渡す | 止めない |
| `SessionStart`（startupのみ） | `session-start.mjs` | 自動改善の結果を報告する。あわせて、未確認の件数、実行されていない予定、記録が止まっていないか、重なった好みの候補、許可されていない検証コマンド、設定の誤りと注意を知らせる。1日1回、全リポジトリ分を掃除する | 止めない |
| `UserPromptSubmit` | `log-event.mjs` | 訂正語を検出する。依頼文を1ターン分だけ一時保持する | 止めない |
| `PostToolUseFailure` | `log-event.mjs` | ツールの失敗を記録する | 止めない |
| `PostToolUse`（Write・Edit・NotebookEdit・Bash） | `log-event.mjs` | 「このターンで変更あり」の印を付ける。`harness-note` の実行と、読むだけと分かっているコマンド（`ls`、`cat`、`git status` など）は数えない | 止めない |
| `PreToolUse`（すべてのツール。matcher は付けない） | `guard-harness.mjs` | 禁止操作を拒否する。ハーネスのファイルと `.env` への書き込みには確認を挟む。自動改善のセッションでは、通すツールの一覧（Read・Grep・Glob・`harness-note` のBash）にないものを、すべて拒否する。通常のセッションでは、ファイルの書き込みとBash以外のツールは、すぐに通す | 止める |
| `Stop` | `on-stop.mjs` | 検証コマンドを実行する（変更があったターン。人が許可した中身と一致するときだけ）。続けて、信号があれば事象メモを作り、改善候補の確認をClaudeに頼む | 検証が失敗したときと、候補の確認を頼むときだけ続けさせる |
| `PreToolUse`（Skill）、`UserPromptExpansion`、`InstructionsLoaded` | `log-event.mjs` | 棚卸し用の記録。ステップ4で足す（未実装） | 止めない |

どのhookも、最初に「ここで動くか」を確かめ（3章）、動かない場所では、何も出さず、何も書かずに終わります。

プラグインのhookは `hooks/hooks.json` に定義し、スクリプトは `${CLAUDE_PLUGIN_ROOT}` で参照します（`node "${CLAUDE_PLUGIN_ROOT}/scripts/….mjs"`。パスは二重引用符で囲みます）。拒否するときは終了コード2を返します。終了コード1はブロックになりません（[Hooks reference](https://code.claude.com/docs/en/hooks)）。スクリプトの中で例外が起きたときは、作業を止めない側に倒します（終了コード1か0）。

`SessionStart` の種類には、公式ドキュメントに `fork`（セッションの分岐）もあります。matcher を付けていないので、分岐したセッションでも試用ルールを読み込みます。

### hookの設計上の注意

- **ガードは軽く抜ける**：`PreToolUse` のガードは、**その人が開くすべての場所で、すべてのツール呼び出しのたびに**動きます。関係のない場所での重さが、そのまま全体の重さになります。`guard-harness.mjs` の先頭では、Node.js の標準のモジュールと `lib/scope.mjs`（これも標準だけで書いてあります）だけを読み込み、することがないと言い切れるときは、ほかの `lib/` を読み込まずに抜けます。抜けるのは、次の2つです。
  - self-improve が動かない場所（gitリポジトリでない、除外してある、`HARNESS_DISABLE=1`）。判定は、記録する側と同じ関数です（3章）。
  - 動く場所でも、「ファイルの書き込みでも Bash でもなく、ロックがどこにもなく、このセッションが lock を試みた記録もない」とき（通常のセッションの Read や Grep など）。

  データ領域の場所が環境変数から分からないとき、ロックのファイルがあるとき（読めないものを含む）は、言い切らずに先へ進みます。計測では、`node` の起動だけで約26ミリ秒、抜ける場合は約37〜39ミリ秒（起動に10ミリ秒ほどを足した程度）、先へ進む場合（ファイルの書き込みと Bash）は約57〜59ミリ秒でした（Linux、Node.js 22、20回の平均）。
- **同じイベントのhookは並列に走る**：`Stop` に検証と事象メモを別々のhookとして置くと、事象メモが検証の結果より先に動くことがあります。そのため1つのスクリプト（`on-stop.mjs`）から順に呼びます。
- **セッション開始時の報告**：`SessionStart` の素の出力はClaudeのコンテキストに入るだけで、ユーザーには表示されません。ユーザーに見せる報告には、出力JSONの `systemMessage` を使います。報告は `startup` のときだけ出します。再開や圧縮のたびに出るのを防ぐためです。
- **ルールの読み込み**：試用ルールと自分専用のルールは、再開、クリア、圧縮のあとにも読み込み直します。圧縮で内容が要約され、ルールが落ちるのを防ぐためです。hookが渡せる量は、1つの欄につき10,000文字までです。超えた分はファイルに逃がされ、Claudeはそれを読みに行きません（[Hooks reference](https://code.claude.com/docs/en/hooks)）。試用ルールは10件・1件200文字までですが、自分専用のルールには件数の上限がないので、ルールは合わせて6,000文字までを、行の途中で切らずに入れます（自分専用のルールを先に、試用ルールは新しいものから。残りは知らせの分）。入らなかった分は、黙って切らずに、件数を知らせます。
- **無人のセッションでの報告**：`startup` は、スケジュール済みタスクや `claude -p` のセッションでも発火します。プロンプトの送信（`UserPromptSubmit`）もターンの終了（`Stop`）も、無人のセッションで起きます。hookの側からは、人が報告を読んだかどうかを知れません。そのため「報告済み」を推定しません。
  - 報告の1行は、人が `/self-improve:review` を開くか、`harness-note report close` で閉じるまで、または7日たつまで、`startup` のたびに出します。
  - 1回きりの知らせ（有効にするかの問い合わせ、実行されていない予定、見直しの時期が来た試用、記録が止まっている、整合の警告、重なった好みの候補、許可されていない検証コマンド、設定の注意）も同じ扱いです。重なった好みの候補と設定の注意は、user 単位の知らせです（どのリポジトリで閉じても、全リポジトリで閉じます）。初めて出した時刻を記録し、閉じるか、7日たつまで出します。中身が変われば（別の試用が見直しの時期に来た、など）、新しい知らせとして出します。
  - 閉じられる知らせを出したときは、閉じ方を1行で添えます。
  - `harness-note lock` を試みたセッションは、実行できたかどうかにかかわらず「自動改善のセッション」として覚えておきます（2週間）。そのセッションが `review` を読んでも、知らせは閉じません。すでにロック中のセッションには、報告を出しません。
  - 自動改善が追加をやめている理由（歯止め）と、読めないガードの定義・読めない設定の知らせは、閉じても消えません。理由が続くかぎり出します。
- **検証の繰り返し**：`Stop` で終了コード2を返すと、Claudeは作業を続けます。公式の連続8回の上限は、Claudeがツールを呼ぶたびにリセットされるので、止め役になりません。そこで `verify.mjs` がセッションごとの連続失敗回数をデータ領域に記録し、3回続いたら打ち切って人に知らせます（`systemMessage`）。打ち切ったら数え直し、次に変更があったターンでは、また検証します。これとは別に、1ターンのあいだに `on-stop.mjs` がClaudeを続けさせる回数にも上限（6回）を置きます。失敗と成功が交互に続いても、止まるようにするためです。この上限で打ち切ったときに、検証が失敗したままなら、「コードは検証が通っていない状態です」と、どの検証が失敗しているかを添えて知らせます。
- **検証を走らせる条件**：そのターンでファイルの変更があったときだけ走らせます。判定には `PostToolUse` で付けた印を使います。`Stop` の入力には変更ファイルの一覧がないからです。検証が通ったあとに変更がなければ、同じターンの次の `Stop`（候補を記録したあとなど）では、検証を繰り返しません。
- **ターンの区切り**：生ログの各行にセッションIDとプロンプトID（`prompt_id`）を付け、同じIDのものを1ターンとして集めます。`prompt_id` が渡らない版では、依頼文を受け取った時刻で区切ります。記録用のhookは非同期で動くので、状態は追記だけの生ログに書き、同じファイルを読んで書き戻すことは避けています。
- **確認が出たときの挙動は、実行のしかたで違う**：`claude -p` では、確認は拒否として扱われるとされています。デスクトップのスケジュール済みタスクでは拒否にならず、答えるまで止まって待ちます（[Desktop scheduled tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks)）。自動改善のセッションで、確認ではなく拒否を返すのはこのためです。
- **記録が止まっていないかの判定**：生ログの行数では判定しません。失敗のない週に誤って警告が出るためです。記録用のhook（`UserPromptSubmit`、`Stop`）が最後に動いた時刻を記録し、それが7日以上前なら警告します。ただし、しばらく使っていなかっただけのときに警告しないよう、「最後の記録より後にセッションが始まっていて、それから1日以上、何も記録されていない」ことも条件にします。

### 改善候補の確認（ターン終了時）

改善候補の確認は、スクリプト型のhookで行います。`on-stop.mjs` が条件を見て、満たすときだけ本体のClaudeに頼みます。

頼むのは、次のすべてを満たすときです。

- そのターンに、信号（ツールの失敗、訂正、ガードの拒否、検証の失敗）があった（**ファイルの変更だけでは、頼みません**）
- user の設定が読めている（読めないあいだは、記録を止めています）
- このターンでは、まだ頼んでいない
- そのセッションが直近24時間に記録した候補が、上限（3件）に達していない
- 自動改善のセッションではない

頼み方は、`Stop` の出力JSONの `hookSpecificOutput.additionalContext` で、「書き残す気づきがあれば `harness-note add` で1行ずつ記録し、なければ何もせずに終わる」と伝える形です。Claudeは1回だけ続行します。伝える文には、セッションIDを添えた記録のコマンド、カテゴリの一覧、あと何件記録できるか、そのターンの事象メモの参照（あれば）を入れます。手順の最後（手順4）に、「記録したら、ユーザーへの報告は、この会話でユーザーが使っている言語で1行だけ書く」と、例（「改善候補を 1 件記録しました：<原因キー>」）を添えます。依頼文そのものは日本語なので、これがないと、日本語でない会話に日本語の報告が混ざるためです。記録のコマンドのひな形は、`--text '<1行>'` のように単一引用符で書きます。二重引用符だと、文の中の `$` やバッククォートをbashが展開するので、ガードが断るためです（断られたときも、この拒否は失敗の信号には数えません）。

終了コード2ではなく `additionalContext` を使うのは、これが失敗ではないためです。公式ドキュメントによると、`Stop` の `additionalContext` は「エラーではないフィードバック」で、会話は続き、画面にはhookのエラーではなく「Stop hook feedback」として出ます（[Hooks reference](https://code.claude.com/docs/en/hooks)）。信号のあるターンのたびに「hookのエラー」と表示されると、利用者が誤解します。検証の失敗は実際の失敗なので、終了コード2のままにします。この欄を知らない古い版では、確認が出ないだけで、作業は止まりません。

- **ループしない**：頼んだことを、セッションIDとプロンプトID（`prompt_id`）の組で記録します。同じターンの2回目の `Stop` では頼みません。LLMの判断に頼らず、スクリプトで止めます（入力の `stop_hook_active` にも頼りません）。
- **検証との順番**：検証が失敗したときは、検証の結果だけを返します。Claudeが直して検証が通ったあとの `Stop` で、候補の確認を頼みます。失敗の原因が分かった直後なので、いちばん価値のある気づきを拾えます。検証を打ち切ったターンでは、候補の確認も頼みません。
- **待ち時間**：条件を満たさないターン（質問に答えただけ、変更しただけ、など）では何も起きません。満たすターンでは、本体のClaudeが1回続行する分だけ延びます。1.x では、ファイルの変更があったターンでも頼んでいました。2.x ではすべてのリポジトリで動くので、変更のたびに1往復が足されると、トークンと待ち時間がかさみます。失敗の信号があったターンに絞りました（信号のないターンの気づきは、人が頼めば記録できます）。
- **判定するのは本体のClaude**：会話の全体を知っているので、最後の応答で触れなかった気づきも書けます。
- **止め方**：プラグインのhookなので、`HARNESS_DISABLE=1` で止まります。

LLMが判定する型（`prompt` 型）のhookは使いません。すべてのターンで動いて絞れないこと、ループの停止がプロンプト頼みになること、検証が失敗したターンの気づきを落とすことが理由です。

### プラグインの外に置くもの

| 賄えないもの | 理由 | 対応 |
| --- | --- | --- |
| その人のデータ（設定、失敗票、自分専用のルール、自分のガード） | プラグインの更新やアンインストールで消えてはいけない。全リポジトリで共有する | user 側（`~/.claude/self-improve/`）に置く。`init` スキルが、user の設定と失敗票の置き場所を作る |
| チームに効かせるもの（チームへ昇格したルール、検証コマンド、チームのガード） | リポジトリごとにgitで管理するもの | 人が、確認を通して、リポジトリに置く |
| 権限ルール、CLAUDE.md | プラグイン同梱の `settings.json` で効くのは `agent` と `subagentStatusLine` だけ。プラグイン直下のCLAUDE.mdも読み込まれない（[Add components to a plugin](https://code.claude.com/docs/en/plugins/components)） | `PreToolUse` hookの拒否と確認で代替する。`harness-note` の許可ルールは、`init` がユーザー設定に、確認を通して足す |
| 時刻どおりの定期実行 | プラグインは自分では起動できない | Claudeデスクトップアプリのスケジュール済みタスクで起動する。実行されていなければ、セッション開始時に知らせる |

## 10. 見るもの

見るのは4つだけで、目標値は置きません。失敗票が月に数件の規模では、率の指標は1件で大きく動き、判断の材料にならないからです。

| 見るもの | 中身 | 出どころ |
| --- | --- | --- |
| 再発した原因 | 制御を置いたあとに、同じ `cause_key` がまた出たものの一覧と件数。試用ルールを編集した分も含める | 失敗票、改善候補 |
| self-improve が読み込ませる行数 | 試用ルールと自分専用のルールの合計（そのリポジトリの分） | `check.mjs` |
| 未確認の自動変更 | 件数と、いちばん古いものの経過日数。増え続けるなら、確認が追いついていない | 自動改善の記録 |
| 自動改善の採否 | 自動で入れた試用のうち、残した件数と消した件数。消すほうが多いなら、対象にする件数を上げるか、自動改善を止める | 自動改善の記録 |

再発を率にしないのは、振り返りをさぼるほど数値が良く見えるからです。一覧なら、どのルールが効いていないかがそのまま分かります。3つ目と4つ目は、自動改善が負担や雑音になっていないかを見るためのものです。

## 11. 導入ステップ

最初に作るのは、初日から効果が出る部分だけです。次の段階に進む条件は、期間ではなく失敗票の件数で決めます。

実装の状況：ステップ1と2は実装済みです。ステップ3の項目（`test-guards.mjs`、自分で足すガード、案を報告に載せること、昇格）も、`review` と一緒に入れてあります。2.x で、ステップ1の `init` が要らなくなりました（プラグインを入れた時点で、記録とガードが動きます）。ステップ0の実験は、まだ実機で行えていません（14章）。各ステップの完了条件（実際に動かして確かめること）は、これからです。ステップ4は未実装です。

0. **実験（着手前）**
   - 最小構成の前に確かめるもの
     - セッション開始時のhookの出力がClaudeのコンテキストに入り、ルールとして効くか。一度に渡せる量の上限。圧縮のあとの読み込み直し
     - `SessionStart` の `systemMessage` がユーザーに見えるか
     - プラグインの `bin/` のコマンドを、ClaudeがBashから呼べるか。許可ルールで確認が出なくなるか
     - `harness-note` に、データの置き場所、セッションID、セッションを始めたリポジトリの場所を渡せるか
     - `~/.claude/self-improve/` の下への書き込み（`harness-note` が書くもの、Claudeが書くもの）に、確認がどう出るか
     - ターン終了時の改善候補の確認が、1ターンに1回で止まるか。続行にかかる時間
   - 自動改善の前に確かめるもの
     - スケジュール済みタスクのセッションで、プラグインのスキルとhookが動くか
     - `harness-note` が、`~/.claude/skills/` とデータ領域に確認なしで書けるか
     - 個人用の場所に置いた試用Skillが、次のセッションで読み込まれるか
     - 自動改善のセッションで、書き込みの拒否が効くか
1. **最小構成（最初の2週間）**
   - プラグインを入れる（すべてのgitリポジトリで動き始める）。`init`（任意）：user の設定を作り、`harness-note` の許可ルールを足し、止めたい場所を除外する
   - `guard-harness.mjs`：共通の禁止リストを拒否し、ハーネスのファイルには確認を挟む。動かない場所では、すぐ抜ける
   - `on-stop.mjs`、`verify.mjs`、`episode.mjs`：検証コマンドは、なしで始める。信号があれば事象メモを作る
   - `log-event.mjs`：ツールの失敗と訂正語を拾う
   - `harness-note`（`add`、`keys`、`list`、`trial`、`incident`）と、ターン終了時の確認：改善候補を記録する
   - `session-start.mjs`：試用ルールを読み込ませる
   - `retro`：人が始める振り返り。失敗票を起票し、試用ルールを1つ入れる
   - `check.mjs`：整合と行数の警告
   - README：インストール、どこで動くか、日常の使い方
   - 完了条件：改善候補が記録され、`retro` で失敗票が1件起票され、試用ルールが次のセッションで効いたことを確かめた。関係のないリポジトリを除外でき、そこでは何も記録されないことを確かめた
2. **自動改善（対象になる原因キーが1つできたら）**
   - `harness-note` の残り（`skill`、`pending`、`report`、`lock`）と、セッションの隔離
   - `auto-improve`：まず手動で呼んで中身を確かめる
   - `review`：自動変更の確認
   - `session-start.mjs`：報告、未確認の件数、60日を超えた試用の一覧、実行されていない予定の通知
   - `SCHEDULING.md` の手順で、スケジュール済みタスクを設定する
   - 完了条件：日時どおりに1回動き、次のセッションで報告が出て、`review` で1件ずつ確認できた
3. **変換先を広げる（失敗票が5件ほどたまったら）**
   - `test-guards.mjs` と、自分で足すガード（user 側とリポジトリの3か所）
   - ガードと検証コマンドの案を、自動改善の報告に載せる
   - 試用ルールと試用Skillの昇格（自分専用かチームへ）
   - 完了条件：ガードを1つ足してテストが通り、昇格を1回行った
4. **棚卸し（失敗票が10件ほどたまったら）**
   - Skillの呼び出しとルールの読み込みの記録
   - `harness-prune` とレポート、間隔を過ぎたときの通知
   - カテゴリ、8分類、`cause_key` の付け方を、実際の候補と失敗票に合わせて見直す
   - 完了条件：棚卸しを1回実行し、レポートが残った

完了条件は「仕組みが動いたこと」にしています。ルールの件数を条件にすると、数を満たすためにルールを足す動機が生まれるからです。

## 12. リスクと未決事項

個人で使う道具として一番大きなリスクは、負担になって使われなくなることです。次に大きいのは、仕組みが「ルールを足す機械」になることです。

| リスク | 起きること | 対策 |
| --- | --- | --- |
| 使われなくなる | 振り返りが手間になり、ループが止まる | 記録、検討、試用までを自動にする。人がやるのは報告の確認だけ（4章） |
| ハーネスが作業を壊す | ガードの誤検知や検証の繰り返しで進めなくなる | `HARNESS_DISABLE=1` で全体を止める。そのリポジトリを `exclude` に書く。検証は3回で打ち切る。作業を止める制御は自動では入れない（3章、4章、7章、9章） |
| 関係のないリポジトリで動く | すべてのgitリポジトリで動くので、顧客のリポジトリや、記録を残せない場所でも、記録とガードが動く。リポジトリ側のファイル（CLAUDE.md、`.claude/rules/` など）への確認も、すべてのリポジトリで出る | `exclude` で止める。除外した場所では、何も記録せず、何も止めない。セッションを始めたリポジトリで決め、途中で変えない。書き間違えたときは、記録を止める側に倒す（3章） |
| 全リポジトリで重くなる | ガードがすべてのツール呼び出しで動く。ターン終了時の確認が、すべてのリポジトリで1往復を足す | 動かない場所と、することがないツールでは、`lib/` を読み込まずに抜ける。ターン終了時の確認は、失敗の信号があったターンだけ。掃除は1日1回（9章） |
| プルした変更で、仕組みの動きが変わる | リポジトリのファイルに設定やガードの解除を書かれ、その人の環境で効く | リポジトリのファイルから読むのは、`verify` と、足し算のガード（`rules`、`protect`）だけ。設定のほかの項目と `disable_defaults` は読まない（5章、9章） |
| 確認なしでコマンドが実行される | リポジトリの `harness/config.json` の `verify` が、初期設定なしでも、変更のあったターンの終わりに実行される（クローンしただけのリポジトリでも） | 人が `harness-note verify trust` で許可した中身（ハッシュ）と一致するときだけ実行する。中身が変われば、もう一度許可を求める。許可は人だけの操作で、呼び出しには確認を挟む。Claudeが書き換えるときも確認を挟む。コマンドが呼ぶ先（`package.json` の `scripts` など）の変化は見ていないので、READMEの「既知の制約」に書く（9章） |
| 個人の記録がチームへ漏れる | 失敗票や失敗票IDが、共有リポジトリに入る。リモートのURLに付けた認証情報が、失敗票に残る | 失敗票は user 側に置く。チームへ出すものには、失敗票IDを付けない（昇格のコマンドが確かめる）。リモートのURLから、認証情報を取り除く（4章、5章、7章） |
| 記録が止まっても気づかない | hookが動かなくなり、事象メモが残らない | hookが最後に動いた時刻を記録し、7日以上前なら警告する（9章） |
| 無人で的外れなルールが効き始める | 人が証拠を見ないまま試用ルールが入り、次の作業に影響する | 1回3件まで。異なるセッションで重なった原因だけを対象にする。次のセッションで報告し、1件ずつ消せる（4章） |
| 報告が読まれない | 未確認の試用がたまり、確認が形だけになる | 未確認が5件に達したら追加をやめ、やめていることを知らせる。報告は、確認を開くか閉じるまで出す。未確認があるあいだは毎回1行出す。件数と経過日数を見る（4章、10章） |
| 同じ対策が繰り返し入る | 消したルールが翌週また入る。同じルールが毎週書き換わる | 材料にした候補は数え直さない。断られた原因は、新しい候補がたまるまで対象にしない。編集は再発の1回目だけ（4章） |
| 無人の実行が作業中のコードを触る | 検証の失敗を直そうとして、書きかけのコードを編集する | 自動改善のセッションでは、通すツールを一覧で絞り（Read・Grep・Glob・`harness-note`）、検証を動かさない（4章）。hookが動いていることが前提で、サンドボックスではない |
| 外から来た文章がルールになる | 会話に混ざった指示が、試用ルールやSkillとして残る | 書き込みは `harness-note` に限り、中身を検査する。試用Skillにはスクリプト、hook、ツールの許可を入れさせない（4章） |
| 実在しない失敗への対策 | たまたまの誤りにルールが付き、残り続ける | 事象メモがあれば照らす。試用から始め、60日で見直す（4章、7章） |
| 指示の肥大化 | 常時ロードが増え、遵守率が下がる | 試用の上限、行数の目安（試用ルール＋自分専用のルール）、棚卸し。チームへ昇格するときにpaths付きにする。読み込みきれない分は、黙って切らずに知らせる（4章、8章） |
| 候補がノイズになる | 些細な気づきが大量にたまる | 1セッション3件まで（24時間）。1件では対象にしない。90日で消す（4章） |
| セッションを名乗って件数や歯止めをごまかす | 1つのセッションが別のIDを名乗り、対象を作ったり、人の書き込みとして試用を入れたりする | ガードが `--session` をhookの `session_id` と照らす。候補は、hookが記録したセッションの分だけ数える。実行中にほかのセッションから入った試用は、未確認の自動変更にする（4章） |
| 原因キーがぶれる | 同じ原因に別のキーが付き、件数が重ならない | 記録の前に既存のキーを確かめさせる。似たキーには警告する。確認のときにまとめ直す（4章） |
| ターン終了が遅くなる | 改善候補の確認で、本体のClaudeが1回続行する | 失敗の信号があったターンに限り、1ターンに1回だけ頼む（9章） |
| 日時どおりに動かない | アプリが閉じている、マシンが眠っている、確認が出て止まる | 間隔を過ぎたらセッション開始時に知らせる。確認が出ないよう、書き込みはコマンドに限る（4章） |
| 試用Skillがほかのリポジトリでも見える | 個人用の場所に置くため、関係のない作業で呼ばれる | 名前にリポジトリ名を付け、説明文に使う場面を書かせる。上限は5件（4章） |
| claude.ai・Coworkでは入らない | 公式ドキュメントによると、直下に `bin/` を持つプラグインは、claude.aiとCoworkではインストールされない（[Add components to a plugin](https://code.claude.com/docs/en/plugins/components)） | Claude Code（端末、デスクトップアプリのローカルのセッション）で使う前提にする。まとめてインストール用の bundle（`japan-da-man-mods`）の依存には入れず、個別に入れる（満たせない依存があると、bundle ごと読み込めなくなるおそれがあるため） |
| 承認の抜け道 | Bash経由でハーネスのファイルが書き換わる。リンクを通した名前や、`$HOME`・大文字小文字の違いで、確認をすり抜ける。`.git/commondir` などを書き換えて、リポジトリの判定そのものを外す。プロジェクトの設定（`.claude/settings.json`）の `env` で、hookを止める | 対象パスに触れるコマンドに確認を挟む。書き込み先は、リンクの名前と実体の両方で判定し、`~`・`$HOME` を展開して、大文字小文字を区別せずに比べる。リポジトリの場所を決めるファイルが壊れていても、上へ探しに行かず、書き込みには確認を挟む（3章、7章）。テスト用の環境変数は `HARNESS_TEST=1` のときだけ読む。`HARNESS_DISABLE` は、プロジェクトの設定の `env` でも止められるが、プロジェクトの設定はhookそのものも止められるので、新しい穴ではない（READMEの「既知の制約」）。完全には防げないと割り切る（7章） |
| 検証のプロセスが残る | 時間切れで検証コマンドを止めても、テストランナーなどの子孫のプロセスが残り、ポートやCPUを握る | プロセスグループごと止める。hook自身が止められたときも同じ（9章） |
| ルールの中身の検査をすり抜ける | 禁じる側のルール（「〜しない」）を通すための例外が広く、否定の形で書かれた誘導を通すことがある | 直さないと決めた既知の制約。最後の関門は、人の確認（`review`）。試用ルールは1行・200文字までで、URLは拒否する（4章） |
| 事象メモへの秘密情報の混入 | 依頼文や応答に含まれたトークンがファイルに残る | リポジトリの外に置く。信号のあったターンに限る。90日で消す（4章） |
| 複数のマシンでの作業 | 試用、候補、生ログ、失敗票、設定がマシンごとに別になる | 当面は1台での利用を前提にする。チームへ昇格したルールはgitで共有される。user 側（`~/.claude/self-improve/`）を同期するかどうかは、その人が決める（失敗票の番号がぶつかっても、上書きはしない） |
| 同じ名前のリポジトリ | リポジトリごとの置き場所（`repos/<名前>/`）を、同じディレクトリ名の別のリポジトリと共有する | `repos/<リポジトリID>/` を作れば、そちらを優先する。READMEの「既知の制約」に書く（9章） |

この仕組みが苦手なのは `judgment`（要件の取り違えや過剰設計）です。コードで判定しにくく、Böckeler氏も挙動面のハーネスはまだ解かれていないとしています。ここは仕様の精度と人のレビューで補う前提にします。

### 着手前に決めること

- [ ] 最初に除外する場所（顧客のリポジトリ、記録を残せない場所）をどこにするか。プラグインを入れる前に、`exclude` を書いておくのが安全（入れた時点から、すべてのgitリポジトリで動くため）
- [ ] ステップ0の実験の結果。特に、セッション開始時に読み込ませた試用ルールが効くかと、`harness-note` が `~/.claude` の下に確認なしで書けるか。実装は済んでいるが、実験はまだ（14章の「実機で確かめること」）

決まったこと：事象メモには、依頼文と応答の全文を残します。

次の3つは仮置きです。運用してから見直します。

- [ ] 自動改善の値：間隔7日、1回3件、未確認の上限5件、試用ルール10件、試用Skill5件
- [ ] 好みの候補：全リポジトリで3件以上重なったら知らせ、本人に確認のうえ `~/.claude/CLAUDE.md` へ。自動メモリとの重複は許容する
- [ ] バグの候補：報告に載せ、確認のときに「Issueにする／今直す／捨てる」を選ぶ

### 後で決めること

- [ ] 複数のリポジトリで同じガードが出たとき、user 全体のガードから、プラグインの共通リストへ移す基準
- [ ] 棚卸しのレポートの置き場所（user 側か、データ領域か）
- [ ] リポジトリごとの置き場所を、名前（`repos/<名前>/`）で決めるままでよいか（同じ名前のリポジトリを多く持つ人が出てきたら、見直す）
- [ ] 試用の見直し（60日）と保持期間（90日）の値

## 13. 付録：後で足すもの

最小構成が回り始めてから検討するものです。どれも今は作りません。

| 拡張 | 内容 | 先送りにする理由 |
| --- | --- | --- |
| 棚卸しの候補出しの定期実行 | スケジュール済みタスクから、棚卸しの候補の一覧だけを書き出す。手順はプラグインの `SCHEDULING.md` | 棚卸しはステップ4。それまでは、セッション開始時の通知で足りる |
| PRモード | 複数人で共有するリポジトリで、チームへ出すハーネスの変更をPRで承認する。プラグインの指定はリポジトリの `.claude/settings.json` で行う（[Manage Claude Code plugins for your organization](https://code.claude.com/docs/en/plugins/org.md)） | 2.x で、共有リポジトリでも、自分専用の範囲なら使えるようになった。チームへ出す分は、いまは人が手でコミットする |
| 失敗票の同期 | 複数のマシンで、失敗票と自分専用のルールを共有する | 当面は1台での利用を前提にする。置き場所が `~/.claude/self-improve/` の1か所なので、dotfilesなどで同期はできる |
| セッション外の失敗の取り込み | `gh` からCI失敗、レビュー指摘、revertを拾い、失敗票の下書きにする | 個人でPRを使わない運用では、拾うものがほぼない |
| ガードの試用 | 自動改善が、拒否ではなく確認を出すだけのガードを試用として置く | まず文章ルールとSkillで回す。作業を止める制御を無人で入れる判断は、採否の実績を見てからにする |
| レビュー用サブエージェント | ハーネスの変更を別のエージェントにレビューさせる | 変更の件数が少ないうちは、人の承認で足りる |

### 実装で決めたこと・変えたこと

設計の時点で決まっていなかった点と、公式ドキュメントを読んで変えた点です。どれも本文に反映してあります。

| 項目 | 実装 | 理由 |
| --- | --- | --- |
| 報告と知らせを出す期間（4章、9章） | 「人が見た」を推定しない。`review` を開くか、`report close` で閉じるか、7日たつまで、`startup` のたびに出す。1回きりの知らせも同じ | プロンプトの送信もターンの終了も、無人のセッションで起きる。hookからは、人が読んだかを知れない |
| 実行した時刻の記録（4章） | `unlock` ではなく `lock` の時点 | 途中で落ちた実行が、間隔の判定をすり抜けて二重に動くのを防ぐ |
| 二重実行を防ぐ間隔（4章） | 最小の間隔は `interval_days` の半分。「実行されていません」と知らせるのは `interval_days` を過ぎたとき | 追いかけの実行や手動の実行のあとに、次の定時の実行が飛ばないようにする |
| 未確認の自動変更の数え方（4章） | 1回の実行で、1つの原因につき1件。「対策を入れなかった記録」も数える | 下書きだけが残って、人の目に触れないまま候補が消費されるのを防ぐ |
| 再発の扱い（4章） | 再発として扱うのにも、新しい候補が2件必要。試用Skillと昇格済みのルールの再発は、案だけ | 「1件では何もしない」をここでも変えない。Skillには編集のコマンドがない |
| `lock` の前提（4章） | hookが記録しているセッションでだけ始める。実行中は、セッションを確かめられない書き込みを受け付けない | 隔離はhookとセッションIDの一致に頼っている。前提が外れたときに、無人の実行を進めないため |
| セッションの名乗り（4章） | ガードが、`harness-note` の `--session` をhookの `session_id` と照らす。`harness-note` は、環境変数と食い違う `--session` を拒否する。`add` は、hookが記録したセッションだけ。実行中にほかのセッションから入った試用は、未確認の自動変更にする | `--session` は自己申告で、そのままでは、別のIDを名乗って歯止めと人の確認をすり抜けられる |
| ロックを試みたセッションのその後（4章） | ロックが外れたあと・始まらなかったあとも、書き込みと、外へ働きかけるツールに確認を挟む。`unlock` は `report write` のあとだけ。推定のIDでは外せない | ロックが外れた直後に、同じセッションがファイルを書き換えるのを防ぐ |

| `exclude` に解釈できない値があるとき、ほかの正しい値の除外が効くのに、文書は「読めない設定と同じ」と読めた | 動き（正しく書けている値の除外は効かせる）は変えず、文書とコメントを合わせた | 3章 |
| 大文字小文字を区別しないファイルシステムで、`exclude` の綴りが実体と違うと、除外が効かない | macOS・Windows では、小文字にそろえて比べる | 3章 |
| `guards.default.json` の説明が、1.x の置き場所（`harness/guards.json` の `disable_defaults`）のままだった | 2.x の置き場所に直した | 5章 |
| `user:token@host:org/repo` の形のURL、`;` のパラメーターに、認証情報が残った | `://` のない形でも、`@` を含めば最後の `@` までを落とす。`;` のパラメーター、クエリ、フラグメントを落とす | 4章 |
| プロジェクトの設定の `env` で、テスト用の `HARNESS_CLAUDE_HOME` を設定されると、user 側の置き場所をリポジトリの中へ向けられた | テスト用の環境変数は、`HARNESS_TEST=1` のときだけ読む。`HARNESS_DISABLE` は残し、READMEの「既知の制約」に書く | 9章、12章 |
| （意見）`harness-note incident import` で、他人のリポジトリの票が混ざっても気づきにくい | 出力に、取り込み元のリポジトリの名前を出す | 9章 |

**変えていないこと**

- 自動改善はリポジトリごとに動き、既定では止めてあります。
- 試用ルールの置き場所（プラグインのデータ領域）と、試用Skillの置き場所（`~/.claude/skills/<リポジトリ名>-<名前>/`）は、そのままです。
- 共通の禁止リストの中身（4つのルール）は、そのままです。
- ルールの中身の検査で、否定の言い回しの例外が広い件は、最初のレビューで直さないと決めたもので、そのままです（12章）。

### 設計から変えた点（user 単位化の指示に書かれていなくて、実装で決めたこと）

user 単位化は、変更の一覧（どこで動くか、設定、`init`、失敗票、ガード、昇格、行数の目安、ターン終了時の確認、好み、掃除）をもとに作り直しました。一覧に書かれていなかった細部は、次のように決めました。

| 項目 | 決めたこと | 理由 |
| --- | --- | --- |
| `exclude` の書き方（3章） | 絶対パスか `~/` で始まるパスの前方一致。パターン（glob）は使わない。実体のパスで比べ、worktreeは本体の場所でも判定する | 何が外れるかを、読んで分かるようにする。リンクやworktreeで、除外をすり抜けないように |
| `exclude` の誤り（3章） | 解釈できない値（配列でない、相対パス、文字列でない）があれば、「設定が読めない」と同じく記録を止める。ただし、配列の中の正しく書けている値の除外は効かせる（配列でないときは、どこも除外しない）。見つからないパスは、知らせるだけで、除外は効かせる | 除外したつもりの場所に、記録を残さない側に倒す。除外したつもりの場所で、ガードや記録が動き出さないように。あとで作るディレクトリを先に書けるように |
| セッションのリポジトリの決め方（3章） | `CLAUDE_PROJECT_DIR` → `HARNESS_PROJECT_DIR`（SessionStartが引き渡す。新設）→ 作業ディレクトリ、の順で、最初のgitリポジトリ | hookには `CLAUDE_PROJECT_DIR` が渡るが、Bashから呼ぶ `harness-note` には渡らないとされているため |
| 記録を止めているあいだに動くもの（3章） | ガードと、ルールの読み込みと、知らせは動かす。検証コマンドは動かさない | 検証は、記録（変更の印）に頼って「変更があったターン」を見分けるため |
| リポジトリごとの置き場所（9章） | `~/.claude/self-improve/repos/<名前>/`（ディレクトリ名から作る）。`repos/<リポジトリID>/` があれば、そちらを優先する | 一覧のとおり `<名前>` にした。人が手で作れる。同じ名前のリポジトリを分ける手段も残す |
| 自分専用のルールの置き場所と形（7章） | `repos/<名前>/rules.md`。`- ` で始まる行が1行1ルール。読み込むときに、試用ルールと同じ検査をする | 人が手で直せる形にする。手で直せるので、読み込むときに確かめる |
| Skillの自分専用への昇格（7章） | 置き場所を変えず、印のファイルに昇格した日時を書く | 試用Skillは、もともと個人用の場所にある。動かすと、名前や参照が変わる |
| チームへの昇格の確かめ（7章） | 移した先に失敗票ID（`INC-…`）があれば断る。`control` には、リポジトリの根からの相対パスを残す | 「チームへ出すものには、失敗票IDを付けない」を、人の注意ではなく、コマンドで守らせる |
| 昇格のコマンド（9章） | `review done --decision promote` をなくし、`harness-note promote` に一本化 | 未確認でない試用（確認済み、見直しの時期）も昇格できるようにするため |
| 失敗票のコマンド（9章） | `incident add` のほかに、`list`（今のリポジトリ。`--all` で全部）、`show`、`set`（`status` と `control`）を足した。`add --from-draft` は、起票後に下書きを捨てる | ファイルを直接書かせないので、読む口と、更新する口が要る |
| `disable_defaults` を書ける場所（5章） | user 側の2つのファイルだけ。リポジトリの `harness/guards.json` に書いても外さず、知らせる | プルした変更で、禁止リストが外れないように。1.x から移る人には、移し方を案内する |
| `protect` を書ける場所（5章） | user 側の2つと、リポジトリのファイルのどれでも | 確認を足す方向の設定で、害がない |
| ガードのテストの範囲（6章） | user 側の2か所の `guards.test.json` も実行する。共通リストのテストは、空の設定で実行する。引数で渡したリポジトリで判定する | 自分のガードにもテストを置けるように。利用者の設定で、共通リストのテストが落ちないように |
| 行数の目安の設定（8章） | `budget` は `always_loaded_rule_lines` だけ（`claude_md_lines`、`scoped_rule_file_lines` はなくした）。`check.mjs` は、リポジトリのCLAUDE.mdと `.claude/rules/` を調べない | 数えるのは、self-improve が足した分だけ、という決まりに合わせる |
| 読み込む量の上限（4章、9章） | ルールは合わせて6,000文字まで（自分専用を先、試用は新しいものから）。入らない分は、件数を知らせる | 自分専用のルールには件数の上限がない。黙って切らない |
| 好みの候補の知らせ（4章） | 自動改善の報告には載せず、user 単位の知らせ1つにまとめる。設定の注意（読まれない項目、見つからない除外のパス）も、user 単位の知らせ | リポジトリの数だけ、同じ知らせが出ないように |
| リモートのURLの読み方（4章） | gitの設定ファイルから `origin` を読む（gitコマンドは呼ばない）。ローカルのパスのリモートは、記録しない | hookとコマンドを軽く保つ。マシンの中のパスを残さない |
| リポジトリ側のファイルへの確認（7章） | 1.x のまま、すべてのgitリポジトリで効かせる | ハーネス自身を守る原則（2章の7）は、`init` の有無で変えない。邪魔な場所は `exclude` で止められる |
| 1.x からの移行（4章、9章） | 失敗票は `harness-note incident import` で取り込む（番号が重なれば振り直す。もとのファイルは消さない）。リポジトリごとに記録済みの好みの候補は、掃除のときに user 単位の場所へ移す。`init` が名残を見つけて案内する | 手で移すと、番号の重なりや、リポジトリの情報の付け忘れが起きる |
| `control` の書き方（4章） | user 側のファイルは `personal:<~ で始まるパス>`。`check.mjs` は、その先があるかを確かめる | リポジトリのパスと、user 側のパスを、見分けられるように |
| 版（9章） | `plugin.json` に `version` を持つ | 作り変えた版を、見分けられるように |

2.0.2（2.0.1 のレビューの修正）で決めたことです。

| 項目 | 決めたこと | 理由 |
| --- | --- | --- |
| 検証コマンドの許可の置き場所（9章） | `~/.claude/self-improve/repos/<名前>/verify-trust.json`。中はリポジトリIDごと | 人の決めたことなので、データ領域（アンインストールで消える）ではなく user 側に置く。同じ名前の別のリポジトリと、許可を共有しないように |
| 何をハッシュにするか（9章） | 実行する形にそろえた `verify`（`name`・`run`・`timeout_sec`）のJSON | 書式や、`verify` 以外の項目の違いで、許可をやり直させない。実行されるものが変われば、必ず変わる |
| 許可の知らせ（9章） | 中身ごとの1回きりの知らせ（閉じるか7日で消える） | 使わないリポジトリで、毎回出続けないように。中身が変われば、また出る |
| 許可の呼び出しへの確認（9章） | ガードが `harness-note verify trust` に確認を挟み、実行するコマンドの一覧を見せる。一覧を見るだけ（`harness-note verify`）は通す | `Bash(harness-note *)` の許可ルールがあると、Claudeが自分で許可できてしまう。リポジトリの文章から誘導されても、人の確認を通るように |
| 直接実行（9章） | `node scripts/verify.mjs` も、許可がなければ実行しない | スキルの `allowed-tools` に入っていて、確認なしで呼べるため |
| 置換を中身に戻さない値（5章） | `-m`・`--message`・`-F`・`--file` の値（`-am` のようなまとまり、`--message=…`、`-m…` を含む）。コマンドを問わない | HEREDOC形式のコミットの本文で誤って止めない。`git push` などには、これらのオプションがないので、すり抜けには使えない |
| 確認を挟む `.git` の中のファイル（7章） | `.git` そのもの、`.git/commondir`、`.git/worktrees/<名前>/commondir`、`.git/config`。Bashは、書き換えると分かっているコマンドとリダイレクトだけ | 共通ディレクトリの場所を変えられるファイルに絞る。`git config` などgit自身の書き込みは日常的なので、止めない |
| `exclude` の大文字小文字（3章） | `process.platform` が `darwin` か `win32` のときだけ、小文字にそろえて比べる | Linux では、綴りの違うパスは別の場所 |
