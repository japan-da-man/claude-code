# spec-flow: 要望から仕様へ

ユーザーの要望を 4 段階で仕様にする。**各段階の終わりで必ず止まって承認をもらい**、承認されるまで次の段階に進まない。このスキルではコードを変更しない（書くのは `docs/specs/` の下だけ）。

| # | id | 段階 | 担当 | 成果物 |
| - | - | - | - | - |
| 1 | `request` | 要求整理 | メイン（あなた） | `01-request.md` |
| 2 | `impact` | 影響画面確認 | サブエージェント `spec-flow:impact-scout`（並列） | `02-impact.md` |
| 3 | `requirements` | 要件定義 | メイン | `03-requirements.md` |
| 4 | `options` | 機能案・UI案 | サブエージェント `spec-flow:option-designer` | `04-options.md`、`mock/index.html` |

ヒアリングはメインで行う（サブエージェントはユーザーに質問できない）。成果物はユーザーの言葉（ふつうは日本語）で書く。

## 0. 始め方

引数を見て決める。

- `--local` があれば外し、その spec では Artifact を使わない（`progress.json` の `local: true`）。
- **引数が `docs/specs/` にある id**：その spec を再開する。
- **引数がない**：`docs/specs/*/progress.json` のうち終わっていないもの（承認されていない段階があるもの）を探す。1 つならそれを再開、複数なら AskUserQuestion で選んでもらう。1 つもなければ、どんな機能が欲しいか尋ねる。
- **それ以外**：新しい要望として始める。

**新しく始めるとき**は、id を `YYYYMMDD-<英語 2〜4 語の kebab-case>`（例 `20261002-csv-export`）にして `docs/specs/<id>/progress.json` を作る。

```json
{
  "version": 1,
  "id": "20261002-csv-export",
  "title": "一覧を CSV で書き出す",
  "request": "（ユーザーの要望の原文をそのまま）",
  "local": false,
  "createdAt": "2026-10-02T09:00:00.000Z",
  "updatedAt": "2026-10-02T09:00:00.000Z",
  "chosen": null,
  "mock": { "file": "mock/index.html", "url": null },
  "steps": [
    { "id": "request", "label": "要求整理", "status": "pending", "file": "01-request.md" },
    { "id": "impact", "label": "影響画面確認", "status": "pending", "file": "02-impact.md" },
    { "id": "requirements", "label": "要件定義", "status": "pending", "file": "03-requirements.md" },
    { "id": "options", "label": "機能案・UI案", "status": "pending", "file": "04-options.md" }
  ]
}
```

**再開するとき**は、`progress.json` を読み直し（spec-flow の mod がチェックで承認を書き込んでいることがある）、承認済みでない最初の段階から続ける。

- その段階が `review`：成果物はできていて承認待ち。下の「承認をもらう」から始める。
- `pending` か `in_progress`：その段階の作業から始める（`in_progress` は前回の中断。成果物ファイルがあれば読んで続きから）。
- 頼まれた文に修正の内容があれば（spec-flow のチェックリストから送られた修正依頼など）、その段階の成果物を直してから「承認をもらう」に進む。

### progress.json の扱い

- `status` は `pending` → `in_progress` → `review` → `approved` と進む。
- 段階を始めるときに `in_progress`、成果物を書き終えたら `review`、承認されたら `approved` と `approvedAt` を書く。書くたびに `updatedAt` も更新する。
- いつも読み直してから書き換える（mod が同じファイルを書くことがある）。

### プロジェクトの前提をつかむ

始めに一度だけ、このリポジトリの前提を短いメモ（10 行程度）にまとめる。サブエージェントにも渡す。

- **CLAUDE.md**（ルートと、関係しそうなサブディレクトリのもの）に構成・画面の場所・用語・規約が書いてあれば、それに従う。
- **書いていなければ**、`package.json` / `Gemfile` / `pyproject.toml` / `go.mod` などとディレクトリ構成から推測する。推測したことは推測と明記する。

## 段階の終わりに: 承認をもらう

各段階の成果物を書いて `review` にしたら、次の形で見せる。

```
spec-flow: <title>（docs/specs/<id>）
- [x] 要求整理
- [?] 影響画面確認  ← 確認待ち
- [ ] 要件定義
- [ ] 機能案・UI案
```

そのあと、成果物の要点を 5〜10 行で伝え、AskUserQuestion で聞く。

- 「承認して次へ」（Recommended）
- 「直してほしい」（どこをどう直すかは Other で書いてもらう）
- 「ここで止める」

それぞれのあとの動き：

- **承認**：`approved` にして、同じターンのまま次の段階に進む。
- **修正**：成果物を直して、もう一度この確認を出す。
- **止める**：`review` のまま終える。再開の方法を伝える：「`/spec-flow:spec <id>` で再開できます。`/specs` のチェックリストからも承認できます」。

AskUserQuestion が使えないとき（`claude -p` など）は、チェックリストと要点を出して、上の再開の方法を伝えてターンを終える。勝手に次へ進まない。

## 1. 要求整理（メイン）

目的は「何を、誰のために、なぜ」をはっきりさせ、影響調査の観点を決めること。

1. 要望を言い換えて、目的・使う人・使う場面・できるようになること・うまくいったと判断する基準に分ける。
2. 質問の前に、関係しそうな語でリポジトリを軽く検索する（5 分程度）。コードを見ればわかることは聞かない。
3. 曖昧な点のうち、**答えによって仕様が変わるもの**だけを AskUserQuestion で聞く。
   - 1 回に 4 問まで。各問におすすめの選択肢を先頭に置き、「(Recommended)」を付ける。
   - 2 往復までにする。残りは「仮定」として書き、要件定義で確かめる。
4. `01-request.md` を書く。

```markdown
# 要求整理: <title>

## 要望（原文）
## 目的・背景
## 使う人と使う場面
## やりたいこと
- <使う人> として、<したいこと>。なぜなら <理由>。
## ヒアリング結果
| 質問 | 回答 |
## 仮定（確認していないこと）
## 対象外
## 未決事項
## 影響調査の観点
- 調べるキーワード・同義語・関係しそうな画面や機能
```

## 2. 影響画面確認（サブエージェント）

目的は、既存の画面・機能・データ・テストへの影響を**漏れなく**洗い出すこと。

1. `01-request.md` の「影響調査の観点」から、調査を観点ごとに分ける。リポジトリの大きさで 1〜4 つ。例：
   - 画面・ルーティング・UI コンポーネント
   - API・ドメインロジック・データモデル・マイグレーション
   - 共通処理・権限・設定・通知・バッチ・外部連携
   - テスト・ドキュメント・分析イベント
2. `spec-flow:impact-scout` を観点ごとに **1 回のメッセージでまとめて並列に** 起動する。プロンプトには次を入れる。
   - `01-request.md` のパス
   - プロジェクトの前提メモ
   - 担当する観点
   - キーワード

   このエージェントが見つからなければ、`Explore` に、このプラグインの `agents/impact-scout.md` の本文を指示として渡す。
3. 結果をまとめる。重要な主張（「この画面が影響を受ける」）は、ファイルを開いて 2〜3 件確かめる。観点の間で矛盾があれば自分で確かめて解消する。
4. `02-impact.md` を書く。

```markdown
# 影響画面確認: <title>

## まとめ
（影響の大きさ、新規か既存の変更か、注意点を 3〜5 行で）
## 影響する画面
| 画面 | ルート / 入口 | 主なファイル | 影響 | 内容 |
（影響は 新規 / 変更 / 間接 のどれか）
## 影響する機能・API・データ
## 共通部品・横断的なもの（権限、設定、通知、ログ、i18n など）
## 関係する既存テスト
## リスク・注意点
## 調べたが影響がなかったもの
（網羅性の証拠として、見た場所と理由を残す）
## 調べきれなかったこと
```

ファイルの場所は `path:line` で書く。

## 3. 要件定義（メイン）

`01` と `02` から、**何を満たせばよいか**を書く。どう作るか（UI の形や実装方式）はここでは決めず、段階 4 に回す。

`03-requirements.md`:

```markdown
# 要件定義: <title>

## 概要
## 用語
## 機能要件
| ID | 要件 | 優先度 | 根拠 |
（優先度は Must / Should / Could。根拠は 01 のどの目的か、02 のどの影響か）
## 画面要件
（02 の影響する画面ごとに、何を表示・操作できる必要があるか）
## データ要件
## 非機能要件
（性能、権限・セキュリティ、互換性・移行、アクセシビリティ、ログ・計測のうち関係するものだけ）
## 受け入れ条件
- FR-1: Given … When … Then …
## 対象外
## 制約・前提
## 未決事項
```

未決事項が仕様を左右するなら、この段階で AskUserQuestion で聞いて埋める。

## 4. 機能案・UI案（サブエージェント）

1. `spec-flow:option-designer` を 1 つ起動する。プロンプトには次を入れる。
   - `01`〜`03` のパス
   - プロジェクトの前提メモ
   - 書き出し先 `docs/specs/<id>/04-options.md` と `docs/specs/<id>/mock/index.html`

   このエージェントが見つからなければ、`general-purpose` に `agents/option-designer.md` の本文を指示として渡す。
2. 戻ってきた `04-options.md` を読み、要件（Must）をすべての案が満たしているか、案どうしが本当に違うかを確かめる。足りなければ直す。
3. **モックを Artifact にする**：`local` が false で、このセッションに Artifact ツールがあれば、`mock/index.html` を Artifact として公開する。
   - 公開の手順と、ページの作りの決まりは、Artifact ツールの説明に従う。
   - 公開した URL を `progress.json` の `mock.url` と `04-options.md` の先頭に書く。
   - Artifact ツールがないか `local` が true なら、ファイルのパスを伝えるだけにする。
4. 承認をもらうときは、AskUserQuestion で **どの案で進めるか** も一緒に聞く（各案を選択肢に。組み合わせは Other で）。
   - 決まったら `progress.json` の `chosen` に書き、`04-options.md` の最後に「## 採用案」として、選んだ案と理由・調整点を足す。
   - そのうえで `options` を `approved` にする。

## 終わり

4 段階すべてが承認されたら、次を伝えて終える。

- 4 つの成果物のパスと、モックの URL
- 採用案
- 残っている未決事項

次の一歩（実装計画づくりなど）は提案だけにして、ユーザーが頼むまで実装しない。
