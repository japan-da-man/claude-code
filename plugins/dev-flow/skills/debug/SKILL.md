# debug: 原因を確かめてから直す

**原因が確かめられるまで、直さない。** 当てずっぽうの修正を重ねると、別の問題を隠す。

## 1. 症状をそろえる

- 何が起きたか、期待は何か、いつから・どの条件で起きるか。足りなければ尋ねる。
- エラーメッセージとスタックトレースは**全文**読む。最初の 1 行だけで判断しない。

## 2. 再現する

- 手元で再現するコマンド・テストを用意し、**実際に失敗するところを見る**。
- 再現できなければ、そこで止まって報告する（直したことにしない）。再現できない原因（環境差、データ、タイミング）を仮説として挙げる。
- 「前は動いていた」なら、`git log` / `git bisect` で壊れた変更を絞る。

## 3. 範囲を狭める

- 入力から失敗点までのどこで値や状態が期待とずれるかを、二分探索のように絞る（ログ、`print`、デバッガ、小さな再現コード）。
- 広く探す必要があるときは、サブエージェント `dev-flow:code-explorer` に任せる。

## 4. 仮説を立てて検証する

- 仮説は 1 度に 1 つ、**反証できる形**で書く（「X が null のはず」→ 確かめる）。
- 見て確かめたものだけを原因とする。確かめていないものは「推測」と書く。
- 仮説が外れたら、観察した事実を足して立て直す。

## 5. 直す

- 原因に対して、**最小の修正**をする。症状だけを隠す修正（例外を握りつぶす、リトライで誤魔化す）はしない。
- 再現テストを回帰テストとして残す（`dev-flow:tdd` の RED の要領）。
- 再現手順がもう失敗しないことと、既存テストが通ることを確かめる。

## 報告

```markdown
## 原因
<何が、なぜ起きたか。根拠は `path:line` とコマンド出力>
## 修正
<何を変えたか>
## 確認
<流したコマンドと結果>
## 残っていること
<確かめられなかったこと、似た箇所>
```
