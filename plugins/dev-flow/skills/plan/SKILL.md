# plan: 実装計画を立てて承認をもらう

コードを書く前に計画を作り、**承認されるまで実装しない**。

## 1. 入力を確かめる

- 引数が `docs/specs/<id>` なら、その中の `03-requirements.md` と、選ばれた案（`04-options.md`）を読む。
- そうでなければ、依頼文をそのまま入力とする。曖昧な点で**結果が変わるもの**だけを AskUserQuestion で尋ねる（調べれば分かることは尋ねない）。

## 2. 現状を調べる

関係するコードの場所が分からないときは、サブエージェント `dev-flow:code-explorer` に任せる（自分で何十ファイルも読まない）。調べたいこと、知りたい結論、見てほしい範囲を渡す。

確かめること:
- 変更する場所と、**既に同じことをしている既存コード**（あれば再利用する）
- 呼び出し元・呼び出し先
- 既存のテストと、テストの実行方法

## 3. 計画を書く

次の形で、チャットに出す（ファイルに残すのはユーザーが望んだときだけ）。

```markdown
## ゴール
<1〜2 文。完了の基準が分かるように>

## やらないこと
- …

## タスク
1. <タスク名> — 変更: `path` / 確認方法: <コマンドや観察できる結果>
2. …

## リスク・不明点
- …
```

守ること:
- 1 タスクは **1 回のコミットで意味が通る小ささ**（目安は 1 つの振る舞い、数ファイル）。
- 各タスクに**確認方法**を必ず付ける。確認できないタスクは分け直す。
- 先に作るものを前に置く（依存の順）。
- 必要になるまで作らない。既存コード・標準機能で足りるなら、新しく作らない。

## 4. 承認をもらう

計画を出したら**そこで止まり**、AskUserQuestion で「この計画で進める / 直す」を尋ねる。「直す」なら修正して再提示する。承認されたら、タスクを順に実装する（振る舞いを足すタスクは `dev-flow:tdd` の進め方に従う）。
