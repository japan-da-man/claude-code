# feature-master の設計

## 何のためのものか

機能マスタは、プロダクトの機能ごとに **どんな利用シーンを想定して作ったか** を、リポジトリの中に残すもの。次のときに読む。

- 既存の機能に付け足すとき: その機能で大事にしていることを壊さないか、前提を崩さないか
- 新しい機能を考えるとき: 既存の機能と利用シーンが重なっていないか、取り合いにならないか、前に見送った使い方ではないか

実装の記録ではない。画面・データ・コード・テストはコードを読めば分かり、手で書くとすぐ古くなるので持たない。コードから正しく読み取れない **意図** だけを持つ。

## 置き場所と形式

```
docs/features/
├── README.md      # 一覧と全体の前提。ほかのファイルから作る（手で直さない）
├── actors.md      # Actor の表
├── product.md     # 全体の前提
└── <id>.md        # 1 ユースケース 1 ファイル
```

1 機能 1 ファイルにするのは、PR の差分が機能ごとに分かれ、人が読みやすく、変更が重なりにくいから。`docs/specs/`（spec-flow の仕様）と並ぶ場所に置く。

### 機能の単位

**Actor がやりたいこと 1 つを 1 機能** にする（ユースケース単位）。画面単位にしないのは、1 つの画面に複数の意図が混ざり、利用シーンと対応しなくなるから。

### actors.md

```markdown
| ID | 名前 | 説明 |
| :- | :- | :- |
| user | 利用者 | 自分のタスクを管理する人 |
| system | システム | 時刻になると通知を出すなど、人の操作なしに動くもの |
```

`| ID |` で始まる表の行が Actor になる。ID は小文字の kebab-case。

### product.md

```markdown
# プロダクト

## 前提

- iPhone アプリとしてだけ使う
- 1 人でも、招待した相手とでも使える
```

すべての機能に当てはまる前提（使う人、端末、通信、言語など）を 1 か所に置く。機能ファイルの「前提」には、その機能だけの前提を書く。全体の前提を機能ファイルごとに写すと、前提が変わったときに全部を直すことになり、写し漏れも起きる（試したときは 29 機能に写され、写した数が機能ごとにばらばらだった）。

### 機能ファイル

```markdown
---
id: task-create
name: タスクを追加する
status: 提供中
actors: [user]
related:
  - id: task-list
    note: 一覧を見ていて、やることを思い出したときに追加する
---

## 概要

タイトルと期日（なくてもよい）を入れて、新しいタスクを登録する。

## 利用シーン

- 移動中にやることを思いついた → 忘れる前に、片手で素早く残したい

## 大事にしていること

- 思いついてから数秒で登録できること。必須の入力はタイトルだけにする

## 前提

- 1 人で、自分のタスクを管理する

## 想定していないこと

- 他の人にタスクを頼む（共有はしない。1 人で使う前提を崩すため）
```

機械で読むもの（ID・状態・Actor・関連機能）は frontmatter に、人が読む文は本文に分ける。

| 項目 | 必須 | 意味 |
| :- | :- | :- |
| `id` | ○ | ファイル名と同じ、小文字の kebab-case |
| `name` | ○ | 機能名。「〜する」の形 |
| `status` | ○ | `提供中`・`開発中`・`廃止予定`。作る前の機能も `開発中` で先に置ける |
| `actors` | ○ | 使う Actor の ID |
| `related` | | 利用シーンの中でつながる機能。`id` と、つながりを書く `note`。技術的な依存ではなく、利用者の流れでのつながり |
| `draft` | | `true` なら、意図をまだ人に確かめていない（init で推測のまま書いた） |
| `## 概要` | ○ | 何ができるか。1 行目が一覧に出る |
| `## 利用シーン` | ○ | 「状況 → したいこと」の箇条書き。この形に揃えると、新しい機能の利用シーンと並べて比べやすい |
| `## 大事にしていること` | | この機能で守りたい、利用者から見た体験。付け足しで壊してはいけないこと |
| `## 前提` | | この機能だけの、想定している使われ方の条件。新しい機能が全体の前提やこれを崩すなら、同じ前提を持つ機能すべてが影響の候補になる |
| `## 想定していないこと` | | あえて対象にしていない使い方と、その理由。見送った理由を知ったうえで、もう一度検討できる |

**大事にしていること は体験で、仕様のルールではない。** 「思いついてから数秒で登録できる」は体験、「招待コードは 1 回だけ使え、期限がある」はコードを読めば分かる仕様。コードから推測するとルールを書きがちなので、ルールの裏にある体験（「招待した相手だけが参加でき、知らない人にリストを見られない」）を書く。

frontmatter は、この形（値、`[a, b]`、`- 値` のリスト、`- id: …` と `note: …` の組のリスト）だけを読む小さなパーサーで読む。依存パッケージを入れないため。

## チェック（scripts/check.mjs）

| 種類 | 内容 |
| :- | :- |
| エラー | frontmatter が読めない／`id` がない・ファイル名と違う・kebab-case でない／`name` がない／`status` が決まった値でない／`draft` が真偽値でない |
| エラー | `actors` がない・`actors.md` にない Actor を指す／`actors.md` がない・表の ID の誤りと重複・名前がない／`product.md` がない |
| エラー | `related` の相手の機能ファイルがない・自分自身を指す |
| エラー | `## 概要` か `## 利用シーン` がない・空 |
| 警告 | `related` の `note` がない・重複／知らない見出し・重複／利用シーンが「状況 → したいこと」でない／知らない項目／使われていない Actor／機能ファイルの前提が全体の前提と同じ（補足の括弧と文末の「。」は除いて比べる） |
| 下書き | `draft: true` の機能の一覧 |
| 古い | `README.md` の一覧が、機能ファイルから作ったものと違う（エラーがあるあいだは比べない） |

エラーがあれば終了コード 1。警告・下書き・古い一覧では失敗にしない。

## スキル

- `init`: プロダクトごとに 1 回。コードとドキュメントから機能と Actor を洗い出し、区切り方・Actor・全体の前提を確かめる。次に **全機能の意図を推測で書き（`draft: true`）、選んだ機能だけ一問一答で確かめる**。ふだんのセッションで読まれるよう、CLAUDE.md か AGENTS.md に、そのファイルの言語で案内の節を足す（承認をもらってから）。
- `check`: チェックを実行して見せる。一覧が古ければ、確かめてから作り直す。

## 試した結果

### 1 回目（shoping-item-memo、2026-10-26）

Expo の買い物メモアプリ。29 機能・Actor 3 つ。区切り方と Actor は「このまま」で承認され、チェックもエラー・警告なしで通った。

- 機能ごとに 4 問を聞く流れは、2 機能目で「一旦、claude が仮で全機能を定義して」と打ち切られた。29 機能 × 4 問は重すぎる。→ 全部を下書きしてから、選んだ機能だけ確かめる流れにした。
- 全体の前提が機能ファイルごとに写され、写した数もばらばらだった。→ `product.md` に分け、繰り返しを警告にした。
- 推測した「大事にしていること」が仕様のルールになった（「招待コードは 1 回だけ使え、期限がある」）。→ 良い例・悪い例を init とひな形に書いた。
- CLAUDE.md がなく AGENTS.md（英語）があった。→ 案内の節を足す先の決め方と、言語を合わせることを書いた。
- 下書きが 28 件残った。確かめる手段がファイルを直接直すことしかないので、`update` には下書きを選んで確かめる使い方が要る。

## まだ作っていないもの

- `update`: 機能の追加・変更と、下書きの機能の確かめを一問一答で行う。今は機能ファイルを直接直し、`check` で確かめる。
- spec-flow との連携: 要求整理と影響調査で機能マスタを読み、仕様が決まったら機能ファイルを直す。
- `check.mjs` を対象のリポジトリに写して、CI で回すこと。
