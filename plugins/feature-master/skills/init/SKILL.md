# feature-master:init: 機能マスタを作る

引数: $ARGUMENTS

機能マスタは、**この機能はどんな利用シーンを想定して作ったか** を残すもの。あとで機能を付け足すときや、新しい機能を考えるときに、既存の機能との兼ね合いを確かめるために読む。実装の記録（画面・データ・コード・テスト）ではない。形式と項目の意味は `${CLAUDE_PLUGIN_ROOT}/DESIGN.md`。

0. 準備 → 1. プロダクトを知る → 2. 下書き → 3. 一覧を確かめる → 4. 意図を聞く → 5. 書く → 6. CLAUDE.md に案内を足す → 7. 承認とコミット、の順に進める。

質問は必ず **AskUserQuestion** で出す。本文に質問を並べない。1 回に出すのは、答えが前の答えに依存しない質問だけ（最大 4 問）。選択肢をつけ、おすすめは先頭にして「(Recommended)」を付ける。**調べれば分かること（どんな機能があるか、何ができるか）は質問せず、自分で調べる。** 聞くのは、コードからは正しく読み取れない **意図**（利用シーン・大事にしていること・前提・想定していないこと）と、機能の区切り方。

## 0. 準備

- 対象のリポジトリを決める。`git rev-parse --show-toplevel` を使い、引数にパスがあればそちらにする。以降のコマンドはそのパスで実行する（`cd <repo> && …`）。
- `docs/features/` に `actors.md` か機能ファイルがすでにあれば、作り直さずに終える。機能ファイルを直接直し、`/feature-master:check` で確かめるよう伝える。
- `git fetch -q origin` のあと `git status -sb` を見る（origin がなければ fetch は飛ばす）。origin より遅れていたら pull してよいか尋ねる。まだコミットしていない変更があれば、それを伝えて続けてよいか尋ねる（あとで書いた分と混ざるため）。

## 1. プロダクトを知る

次を読み、プロダクトが **誰の、どんな用事のためにあるか** と、**利用者から見てできること** をつかむ。

- README・`docs/`（`docs/specs/` があれば、機能ごとの仕様と、そこに書かれた要望の背景）・CLAUDE.md
- コード: 画面とその遷移、ルーティング、CLI のコマンド、公開している API、バックグラウンドの処理（通知、定期実行など）
- `git log --oneline -50` で、機能が足された順と、その言い方

リポジトリが大きければ、観点ごと（画面、API、バックグラウンドの処理など）に Explore のサブエージェントに分けて調べさせてよい。返してもらうのは「利用者から見てできること」の一覧と、根拠のファイル:行だけにする。

コードがない（これから作るプロダクトの）ときは、ここは飛ばし、2 の下書きを作らずに、3 で機能の一覧をインタビューで作る。

## 2. 下書き

次の 2 つを下書きにする（まだファイルには書かない）。

**Actor**: 機能を使う人や仕組み。人の役割（利用者、管理者、ゲストなど）と、人の操作なしに動くもの（`system`: 通知を出す、定期的に集計する、など）。ID は小文字の kebab-case の英語。

**機能**: ユースケース単位。**Actor がやりたいこと 1 つを 1 機能** にする（「タスクを追加する」「タスクを完了にする」）。画面単位にしない（1 つの画面に複数の機能があっても、1 つの機能が複数の画面にまたがってもよい）。機能ごとに次を下書きにする。

| 項目 | 書き方 |
| :- | :- |
| `id` | 小文字の kebab-case の英語（例: `task-create`）。ファイル名になる |
| `name` | 「〜する」の形。利用者の言葉で |
| `status` | 動くコードがあれば `提供中`。作りかけ・フラグで隠れているものは `開発中`、消す予定なら `廃止予定` |
| `actors` | 使う Actor の ID |
| 概要 | 何ができるかを 1〜3 文で。画面の名前・クラス名・実装の細部は書かない |
| 利用シーン | コードから推測した「状況 → したいこと」の候補 |
| `related` | 利用シーンの中でつながる機能と、そのつながり（`note`）。呼び出しやデータの依存ではなく、利用者の流れでつながるもの |

## 3. 一覧を確かめる

Actor と機能の一覧を表（id・機能名・Actor・概要）で見せてから、AskUserQuestion で次を聞く。

1. 機能の区切り方は合っているか（このまま／まとめたい機能がある／分けたい機能がある／抜けている機能がある）。直したいと答えたら、どれをどうするか続けて聞き、一覧を直して見せ直す。
2. Actor は合っているか（このまま／足りない／分けたい・まとめたい）。
3. プロダクト全体の前提（例:「1 人で使う」「オフラインでも使う」「件数は数十件まで」）。コードから推測した候補を multiSelect で出す。ここで決めた前提は、当てはまる機能すべての「前提」に書く。
4. 今は作っていないが、作る予定の機能があるか。あれば `開発中` として一覧に足す。

## 4. 意図を聞く

機能ごとに、1 回の AskUserQuestion で次の 4 問を出す。順番は、利用者がよく使う機能・中心になる機能からにする。

| 問 | 選択肢 |
| :- | :- |
| 利用シーン（multiSelect） | 推測した「状況 → したいこと」の候補 |
| 大事にしていること（multiSelect） | この機能で守りたい体験の候補（例:「思いついてから数秒で登録できる」）。「特にない」も入れる |
| 前提（multiSelect） | 3 で決めた全体の前提のうち当てはまるもの、この機能だけの前提の候補 |
| 想定していないこと（multiSelect） | あえて対象にしていない使い方の候補と、その理由（例:「共有はしない。1 人で使う前提のため」）。「特にない」も入れる |

- 候補はコードと 1 の調べから作る。推測であることが分かるように書き、選ばれなかった候補は書かない。ユーザーが「Other」で書いた言葉は、意味を変えずに「状況 → したいこと」などの形に整える。
- 5 機能ごとに、AskUserQuestion で「続ける／残りは下書きにする」を聞く。下書きにした機能は、推測の内容で書き、`draft: true` を付ける。ユーザーが途中で「もう十分」と言ったときも同じ。

## 5. 書く

1. ひな形を置く:

   ```bash
   node ${CLAUDE_PLUGIN_ROOT}/scripts/cli.mjs install <repo>
   ```

   `docs/features/` と、Actor の表のひな形 `actors.md` ができる。`template` に出る機能ファイルのひな形（`feature.md`）を Read で読む。
2. `actors.md` の表に、3 で確かめた Actor を書く。
3. 機能ごとに `docs/features/<id>.md` を、ひな形の形で書く。
   - ひな形の `<…>` と `<!-- … -->` は残さない。
   - `大事にしていること`・`前提`・`想定していないこと` は箇条書き。答えが「特にない」なら、その見出しごと消す（`概要` と `利用シーン` は必ず書く）。
   - `related` がなければ、`related:` の行ごと消す。つながりが双方にとって意味があるなら、両方のファイルに書く。
   - 4 で聞いた機能には `draft` を書かない。
4. 一覧を作り、確かめる:

   ```bash
   node ${CLAUDE_PLUGIN_ROOT}/scripts/cli.mjs index <repo>
   node ${CLAUDE_PLUGIN_ROOT}/scripts/cli.mjs check <repo>
   ```

   `index` が `errors` を返したら、機能ファイルを直してやり直す（エラーがあるあいだは一覧を作らない）。`check` の `warnings` も、下書きと Actor の使われ方の警告以外は直す。

## 6. CLAUDE.md に案内を足す

ふだんのセッションで機能マスタが読まれるように、リポジトリの `CLAUDE.md` に次の節を足してよいか、AskUserQuestion で尋ねる（足す（Recommended）／足さない）。`CLAUDE.md` がなければ、作ってよいかを尋ねる。すでに同じ内容の節があれば足さない。

```markdown
## 機能マスタ

`docs/features/` に、機能ごとの設計意図（利用シーン・大事にしていること・前提・想定していないこと）がある。一覧は `docs/features/README.md`。

- 機能を付け足すとき、新しい機能を考えるとき、仕様を書くときは、関係する機能のファイルを先に読む。前提や想定していないことと食い違う、または大事にしていることを損なうおそれがあれば、進める前にユーザーに伝える。
- 機能を足したり、意図が変わったりしたら、機能ファイルも直し、`/feature-master:check` で確かめる。
```

## 7. 承認とコミット

1. 一覧（`docs/features/README.md`）のパスと、下書きの機能があればその一覧を伝え、AskUserQuestion で「この機能マスタで承認する／直したい機能がある」を聞く。直したい機能があれば、どれをどう直すか聞いて直し、5 の 4 からやり直す。
2. `git status` で変わったファイルを確かめ、`docs/features/` と（足したなら）`CLAUDE.md` をコミットする。メッセージはリポジトリの書き方に合わせる（例: `Add the feature master: intent of each feature`）。push はしない（push するかユーザーに尋ねる）。

## 終わりに

次を短く伝える。

- 作ったもの（Actor の数、機能の数、そのうち下書きの数と ID）
- 下書きの機能は、機能ファイルを直接直して `draft: true` を消せばよいこと
- 守られているかは `/feature-master:check` で確かめられること
