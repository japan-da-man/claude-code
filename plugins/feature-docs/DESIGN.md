# feature-docs の設計

企画から公開までの成果物を **3 つに分けてリポジトリで管理し、PR のマージを承認にする** ためのプラグイン。人が確認するのは「要件」「設計と UI 案」「最終成果物」の 3 回だけで、その間はエージェントが進める。機能マスタはヘルプ AI のソースになる。

## 3 つの成果物

| 成果物 | 置き場所 | 性質 | 更新する PR | ヘルプ AI |
| --- | --- | --- | --- | --- |
| 企画・要件定義書 | `docs/requirements/REQ-xxxx-*.md` | 変更要求。承認後は status 以外を変えない | ① 要件の PR | 渡さない |
| 設計書（＋UI 案・トラッキング・全体図・ADR） | `docs/design/F-xxx-*.md` ほか | 機能ごとの今の設計（振る舞いと裏側） | ② 設計の PR | 渡さない |
| 機能マスタ | `features/F-xxx-*.yaml` | 今提供している機能の、利用者から見た事実 | ③ 最後の PR | 許可した項目だけ渡す |

時間の性質が違うので分ける。要件定義書は「その時点の変更要求」で、あとから書き換えると判断の履歴が消える（変えたいときは新しい要件定義書を起こして `supersedes`）。設計書は機能ごとに常に最新。機能マスタは実装と同時に更新し、計画中の機能を載せない（ヘルプ AI が未提供の機能を案内しないように）。

アクターと用語は `actors.yaml` / `glossary.yaml` に 1 か所で持ち、ID で参照する（表記ゆれを防ぐ）。

## 流れと状態

| # | ステップ | スキル | 要件定義書の status | 人 |
| - | - | - | - | - |
| 1 | 企画の受付 | （Issue など） | — | — |
| 2 | 要件定義（一問一答） | `requirements` | draft → approved | ① 要件の PR をマージ |
| 3 | 設計・UI 案・トラッキング | `design` | approved → designed | ② 設計の PR をマージ |
| 4 | 実装（統合ブランチに小さな PR を自動マージ） | `build` | designed | なし |
| 5 | 機能マスタ・ヘルプ・changelog | `finalize` | designed → implemented | ③ 最後の PR をマージ |
| 6 | ヘルプ用ナレッジの書き出し | CI（`export-help`） | — | なし |

status は PR の中で次の値にする。main にあるものはすべて承認済み、PR のブランチにしかないものは未承認、という状態になる。

設計の PR で、変える機能の設計書の `pending` に REQ の ID を付け、最後の PR で外す。`pending` がある間、設計書は実装より先の内容を含む。変える節には `> 未実装（REQ-xxxx）` を置き、実装役はそこを「これから作る内容」として読む。

## チェッカー（scripts/check.mjs）

アプリのリポジトリの `feature-docs/check.mjs` に写して、CI でもプラグインなしで動かす。依存はない。リポジトリに `yaml` パッケージが入っていればそれで読み、なければ機能マスタで使う範囲の YAML（マップ・リスト・`[a, b]`・引用符・`|` / `>`）だけを読む小さな読み込みを使う（アンカーや `{ }` は行番号つきで落とす）。

状態に応じて調べる（どの PR かは見ない。各ファイルの状態だけで決まるので、どの PR でも同じ規則で落とせる）。

- 要件定義書：approved 以降は必須の節・機能 ID・アクター。approved / designed で新規の機能が機能マスタにあれば誤り。designed は設計書の pending と UI 案（`ui: none` でなければ）。implemented は機能マスタへの反映と new_actors。
- 設計書：機能が機能マスタか要件定義書の新規にあること、pending の REQ が designed であること、tracking と ui のパス、必須の節。
- 機能マスタ：planned を載せない、裏側の項目（api・data・feature_flag・events・screens など）を載せない、beta 以上は利用者の文脈（アクター・JTBD・利用シーン・利用者の流れ）と要件定義書（implemented のもの）と設計書、ga はヘルプの項目と changelog、deprecated は終了日と代わり。導入前からある機能は `legacy: true`（要件定義書なし、設計書がなければ警告）。

## ヘルプ AI への書き出し（export-help）

機能マスタから、`status` が beta / ga で `help.visibility: public` の機能だけを、1 機能 1 Markdown に書き出す。**許可した項目だけ** を取り出す（拒否リストにしないので、機能マスタに項目が増えても漏れない）。見出し（H2）1 つが利用者の質問 1 つに当たるようにし（これは何？・使い方・できないこと・よくある質問…）、メタデータ（ID・状態・OS・プラン・バージョン・最終確認日・同義語）をフロントマターに置く。要件定義書・設計書・トラッキングプランは読まない。誤りがあるときは書き出さない。

## UI 案

作業場は Claude Design（デザインシステムは `/design-sync` でコードから取り込む）、正本はリポジトリ。確定した案をスタンドアロン HTML で `docs/ui/REQ-xxxx/` に置き、URL を README に残す。Claude Design を使えない環境では、スキルが HTML のモックを書く。出力は HTML なので、React Native などでは「見た目と意図」として読む。

## ほかのプラグインとの関係

- **spec-flow**：要望を `docs/specs/<id>/` に段階的にまとめる、承認つきの仕様づくり（成果物は 1 つの仕様の束）。feature-docs は、要件・設計・機能マスタを分けて正本として持ち続け、PR とチェッカーで整合を守る。どちらか一方を使う。
- **factory**：iOS アプリ向けに、仕様から裏のラインで実装・検証・判定・マージまで自動で回す。feature-docs の `build` は、人が最後の PR だけを見る前提で、統合ブランチに小さな PR を積む（プラットフォームを問わない）。
- **design-system**：あれば、`design` の UI 案と状態の表示、`build` の画面づくりはその決まりと部品に従う。
- **dev-flow**：あれば、`build` のタスクは `dev-flow:tdd` の進め方で作る。
