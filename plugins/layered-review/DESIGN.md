# layered-review の設計

エージェントが書くコードが増えると、人が 1 行ずつ読むレビューは追いつかない。かといって読むのをやめれば、バグを直す時間が増える。人の時間は「レビューにかける時間」と「入ったバグを直す時間」の両方で数える。片方だけ減らしても、時間は減らずに移るだけ。

そこで「誰かがコードを読んだか」を問うのをやめ、**「この変更で何が壊れうるか、それを捕まえるのは自動と人のどちらのチェックか」** を問う。1 つの関門ではなく、いくつもの層で受け止め、すり抜けたものは早く戻す。人の注意は、人にしかできないこと（作るべきかの判断、危険な領域、アーキテクチャ、検証結果の確かめ、責任）に取っておく。

元にしたのは、Claude Code のチームがコードレビューの運用を書いた記事。

## 層

| # | 層 | このプラグインでは |
| - | - | - |
| 1 | PR の前の検証 | `review`（引数なし）が `checks` を回して結果を見せてから、別のコンテキストのエージェントが差分を見る |
| 2 | AI のレビュー | `review` が観点別のエージェントで探し、別のエージェントの投票で確かめ、Important / Nit / Pre-existing に分ける |
| 3 | セキュリティのレビュー | 観点 C（セキュリティとデータ）として 2 に入れている。止める仕組みは GitHub のスレッドの解決（下） |
| 4 | 自動のチェック | CI（`layered-review.yml` と既存の CI）。PR テンプレートに「どう確かめたか・リスク・戻し方」 |
| 5 | リスクに応じた人の承認 | `check.mjs risk` が変更の中身で段階を決める。高リスクのパスは CODEOWNERS で人の承認を必須にする |
| 6 | 段階的に出す | 対象外（feature flag・EAS Update のチャンネル・段階的な公開は、アプリの側で持つ）。PR テンプレートの「戻し方」で、戻せるかを先に考えさせる |
| 7 | 早く気づいて戻す | 対象外（observability プラグインが持つ）。見逃したものは `eval add` でケースにする |

止める仕組み（スレッドが残っていたらマージできない、新しいコミットで承認を取り消す、Code Owners の承認を必須）は GitHub のブランチ保護にしかできないので、`init` は「人がやること」として渡す。

## リスク段階

**作者ではなく変更で決める。** 段階は 3 つ。

| 段階 | 条件 | レビューの深さ（既定） | 人の承認（既定） |
| - | - | - | - |
| high | `risk.high` のパスに 1 つでも当たる（名前を変えた元・消したファイルも見る） | deep | 作者以外（`high_needs_other: false` なら作者） |
| low | すべてのファイルが `risk.low`（文書・機能マスタなど） | quick | 作者（`auto_merge_low: true` なら不要） |
| standard | それ以外 | standard | 作者（`trusted_authors` にない作者なら作者以外） |

- 行数が `large_change_lines` を超えたら、段階は変えずにレビューを deep にする（大きい変更ほど見つかるものが多い）。
- `risk.high` は「理由: パス」で持つ。理由は報告と CODEOWNERS のコメントにそのまま出る。
- エージェントの承認は人の承認に数えない。エージェントが書いた変更は、動かした人が作者として責任を持つ。

1 人の開発では「作者以外の承認」が取れないので、`init` で 1 人を選ぶと `high_needs_other: false` になる。そのかわり high は deep で見て、作者がその結果を確かめる。

## レビュー（探す → 投票で確かめる → 分ける）

手順は `references/procedure.md`。

- **探す**：観点ごとに別のエージェント（`bug-hunter`）。quick は 1 人で A〜C、standard は A〜C を 3 人、deep は A〜E を 5 人。観点を分けると、同じ見方の重複が減り、違う観点から同じものが見つかればそれが強い手がかりになる。
- **確かめる**：別のエージェント（`verifier`）が、誰が見つけたかを知らずに、コードを読んで confirm / refute / unsure を付ける。standard と deep は 3 人で、2 つ以上の confirm で残す。critical だけは、confirm が 1 つで refute がなければ「確かめきれなかったこと」として残す（重い見逃しを投票で消さない）。
- **落とす**：書き方・フォーマット・命名だけの指摘。直す価値の小さい指摘は、エージェントが作者だと「直す → コミット → また見る」の往復を 1 回増やす。人なら 1 秒で無視できるものでも、エージェントには高くつく。
- **分ける**：`check.mjs classify` が、指摘の行が変更の中（追加した行・消した位置のそば）かを機械で決める。外なら Pre-existing（作者に直させない）。外でも、探した側が「この変更のせいで表に出た」と根拠を書いたものは introduced。
- **まとめる**：同じ種類のバグは 1 つの指摘にして、場所をすべて挙げる。1 か所ずつ直して、また指摘される往復を防ぐ。

## 収束

エージェントの作者とエージェントのレビュアーは、放っておくと終わらない（記事では、一晩で 50 回以上往復した PR があった。くり返し指摘されたものの約 6 割は、最初からあったコードだった）。そこで:

- 1 つの変更（ブランチか PR）でレビューを回すのは `review.max_rounds`（既定 3）回まで。超えたら止まり、直し方ではなく方針の見直しを勧める。
- 2 回目からは、前回見た head からの差分だけを見る。
- 前に出した指摘（`fp` で照らし合わせる）は出し直さない。前回の Important は、直ったかだけを確かめる。
- head が変わっていなければ、回さない。
- 記録は `<git のディレクトリ>/layered-review/state.json`（コミットしない）。`round stats` で、通るまでの平均の往復回数を見る。

`fp` は、パス・種類・題を正規化（大文字小文字・空白・句読点を無視）したハッシュ。行番号は入れない（直す途中で行がずれても同じ指摘と見なすため）。

## eval

**見逃したバグを正解にして、レビューの仕組みを変えるたびに全件で測る。** 変えたプロンプトが良くなったかは、感覚では分からない。

### ケース（`review/evals/cases/C-xxx-*.json`）

- **バグのケース**：バグを入れた変更（`introduced.base`…`introduced.head`）と、バグごとの場所（`head` の時点の `path`・`lines`）・重大度・種類・内容・きっかけ。元は revert・あとからの修正・インシデント。
- **問題のないケース**：あとから直されていない変更。何も言わないのが正解で、誤指摘を測る。
- **人が場所と内容を確かめたものだけ**（`verified_by`）。エージェントの下書きをそのまま正解にすると、レビューと同じ間違いを正解にしてしまう。

元の変更を元のコミットのまま取り出して（`git worktree`）レビューを再生する。公開のベンチマーク（Greptile など）も、修正の PR からバグを入れたコミットまでたどり、その差分を出し直して測っている。

### 判定

`eval-judge` が、正解のバグごとに見つけたか（**言い回しではなく原因が同じか** で、場所は前後 10 行ほどまで）と、指摘ごとの判定を付ける。

| 判定 | 意味 | 数え方 |
| - | - | - |
| `tp` | 正解のバグを言い当てた | 当たり |
| `real_unlisted` | 正解にないが本物のバグ | 当たりに数え、正解に足す候補として出す |
| `noise` | バグではないが、従っても害はない | 外れ |
| `harmful` | 従うとバグを入れる・正しいコードを壊す | 外れ。問題のないケースでの割合を別に出す |

LLM の判定は意味で照らし合わせられるが、ぶれる。だから正解は人が確かめたもので固定し、判定は指摘ごとに残して（`judgments/`）あとから人が監査できるようにする。

### 指標

| 指標 | 意味 |
| - | - |
| 重みつき recall | 見つけたバグの重みの合計 / すべてのバグの重みの合計。重みは既定で critical 4・high 2・medium 1・low 0.5（DoorDash の公開した評価と同じ） |
| critical / high の recall | 重いバグだけの recall。これが下がる変更は採らない |
| precision | （`tp` + `real_unlisted`）/ すべての指摘 |
| F1 | 重みつき recall と precision の調和平均 |
| 問題のない変更 1 回あたりの指摘・有害な指摘が出た割合 | 何もないところで黙っていられるか |

`compare` は、2 つの実行の差と、**見つけられなくなったバグ**（重い順）を出す。重みつき recall・重い recall が下がったか、問題のない変更で有害な指摘が増えたか、precision が 5 ポイント以上下がったら「悪化」として終了コード 1 を返す。

LLM の結果はぶれるので、採否を決める比較は `--repeat 3` で回す。同じケースを何回見つけたか（`rate`）で比べる。

### 実運用の信号（`review/outcomes.jsonl`）

指摘にどう応じたか（直した・却下・意図どおり・問題にしなかった）を残す。直した割合は precision の **代わりの指標** にすぎない（受け入れられたことと本物だったことは別）ので、eval とは混ぜずに `outcomes` で別に見る。却下や「問題にしなかった」が多い種類は、REVIEW.md の「指摘しないこと」に足す候補。

## チェッカー（scripts/check.mjs）

アプリのリポジトリの `review/check.mjs` に写して、CI でもプラグインなしで動かす。依存はない。設定・ケース・実行結果・対応結果はすべて JSON（YAML の読み込みを持たないため）。

パスの書き方は CODEOWNERS（gitignore）に近づけた。`/` を含まない名前はどの階層にも当たり、`/` を含むものはルートから、`/` で終わるものはその下すべて。`risk.high` から CODEOWNERS をそのまま作れるようにするため。

## 測らないこと

記事は、人の時間（PR あたりの人の承認数の中央値と p95、人のコメント数、人を待った時間）を減らしたい指標に、revert とインシデントの割合をガードレールにしている。これらは GitHub とインシデントの記録から測るもので、このプラグインは持たない。リスク段階を緩める（`auto_merge_low` など）のは、これらが悪化していないと分かってから。

## ほかのプラグインとの関係

- **dev-flow**：`review` は 1 人のレビュアーで手早く見る。layered-review は、段階・投票・収束・eval まで持つ。`checks` の結果が長ければ、dev-flow の `test-runner` に任せてよい。
- **usable-ui**：UI の使いやすさは usable-ui の `review`。layered-review はバグだけを見る。
- **feature-docs**：PR テンプレートと CI を両方入れるなら、テンプレートの項目を 1 つにまとめる。機能マスタ（`features/**`）は low に入れている。文書が実装と食い違うことは観点 B で見る。
- **observability**：インシデントの記録（`observability/incidents/`）は `eval add` の元になる。
- **factory**：factory の判定は満足度、layered-review はバグ。factory の裏のラインに、PR の前の層として `review` を挟むこともできる。
